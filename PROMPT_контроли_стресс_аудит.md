# Промпт агенту: стресс-аудит сетевой синхронизации вкладки «Контроли»

**Репозиторий:** `https://github.com/sledovatel61/porayonka.git` (ветка `main`)
**Приложение:** `porayonka-app/main.py`
**База:** коммит `0ea30d9` (main, раунд 28 + промпт раунда 29)
**Ветка агента:** `arena/audit-network-porayonka` (создать от `main`)

## Цель аудита

Проверить, насколько надёжно работает сетевая синхронизация вкладки «Контроли» в реальных боевых условиях: два и более администратора, пользователи, оффлайн-режим, конфликты, большие вложения, медленная/нестабильная сеть, одновременное редактирование, удаление/восстановление shared-файла.

Аудит должен либо подтвердить, что всё работает корректно, либо найти конкретные баги и дать рекомендации/фиксы.

## Архитектура сети (как сейчас)

- **Shared JSON**: общий файл `controls.json` в сетевой папке (например, `\\192.168.0.60\общая\Гайнутдинов\Porayonka workspace\controls.json`).
- **Polling**: каждые ~20–60 секунд приложение проверяет `mtime` shared-файла и перечитывает при изменении.
- **Запись**: свои изменения сохраняются сразу и локально, и в shared (атомарная замена через `.tmp` + `os.replace`).
- **Merge**: `merge_controls(local, shared)` — union по `id`, конфликт решает более новый `updated_at` (ISO, нормализуется через `datetime`).
- **Роли**: admin — полный доступ; user — видит только контроли, где он указан как исполнитель/ответственный пункта/контролёр.
- **Вложения**: копируются в `controls_attachments/<control_id>/<file>` рядом с shared JSON и локально в `%APPDATA%\porayonka\controls_attachments\<control_id>\<file>`.

## Что проверить

### 1. Конфликты при одновременном добавлении

**Сценарий:** два админа одновременно добавляют разные контроли. Оба offline, потом сеть появляется.

**Ожидаемо:** оба контроля присутствуют у обоих админов после синхронизации.

**Проверить:**
- Нет ли потерь данных?
- Сохраняются ли `id`, `incoming_number`, `tasks`, `attachments`?
- Не дублируются ли контроли?

### 2. Конфликт при одновременном редактировании одного контроля

**Сценарий:** админ A меняет `content`, админ B меняет `executors` одного и того же контроля. Оба сохраняют с разницей в несколько секунд.

**Ожидаемо:** должен победить тот, кто сохранил позже (`updated_at`). Данные проигравшего потеряются (last-write-wins — это известное ограничение).

**Проверить:**
- Правильно ли сравниваются `updated_at`?
- Не происходит ли слияния полей (поле A + поле B) — это было бы неожиданно и опасно?
- Что происходит, если `updated_at` совпадает в пределах секунды?

### 3. Offline-режим

**Сценарий:** админ работает без сети (shared недоступен), добавляет/изменяет контроли, потом сеть возвращается.

**Ожидаемо:**
- Локальные данные не теряются.
- При возврате сети происходит merge.
- Если shared-файл отсутствует/был удалён — приложение создаёт/восстанавливает его из локальных данных.

**Проверить:**
- Не перезаписывает ли локальный admin свои изменения пустым shared-файлом?
- Правильно ли работает `_load_initial` и seed shared?

### 4. Удаление и восстановление shared-файла

**Сценарий:** shared `controls.json` удалён во время работы приложения.

**Ожидаемо:**
- Приложение продолжает работать с локальными данными.
- При следующем сохранении shared-файл пересоздаётся.
- Вложения, добавленные другими, теряются (это ограничение), но локальные сохраняются.

### 5. Большие вложения

**Сценарий:** к контролю прикрепляется PDF/фото размером 10–50 МБ.

**Ожидаемо:**
- Копирование в shared не падает.
- UI не зависает (копирование не в UI-потоке).
- Предупреждение при >20 МБ.

**Проверить:**
- Что происходит, если копирование прерывается на полпути (сеть упала)?
- Остаётся ли битый `.tmp` файл?

### 6. Медленная/нестабильная сеть

**Сценарий:** shared-папка на медленном SMB, latency 500–2000 мс.

**Ожидаемо:**
- UI остаётся отзывчивым.
- Polling не падает с таймаутом.
- Если `mtime` не удалось прочитать — приложение переходит в offline-режим, а не паникует.

### 7. Множественные клиенты

**Сценарий:** 5 админов + 10 пользователей одновременно работают с shared.

**Ожидаемо:**
- Нет race condition при записи (`.tmp` + `os.replace` атомарны).
- Polling не создаёт слишком большой нагрузки на сеть.
- User-фильтры работают корректно (каждый видит только свои контроли).

### 8. Время на ПК

**Сценарий:** часы на ПК админа A спешат/отстают на 5+ минут.

**Ожидаемо:**
- `updated_at` может быть «из будущего» или «из прошлого».
- Merge должен быть детерминированным.
- Желательно предупреждение пользователю (это задача раунда 29, но аудит должен показать, насколько критично).

### 9. Алармы/уведомления

**Сценарий:** админ добавляет контроль с сроком «сегодня» для пользователя X.

**Ожидаемо:**
- Пользователь X получает уведомление через свой polling-цикл.
- Алармы не дублируются бесконечно.

### 10. Чат между пользователями (опционально, только оценка)

**Вопрос от пользователя:** реализуем ли чат с отправкой файлов/сообщений?

**Оценить:**
- Можно ли сделать поверх той же shared-папки (`messages.json` + polling)?
- Сколько это усложнит архитектуру?
- Нужен ли отдельный сервер/база?
- Какие будут ограничения в Flet 0.23.2 (UI, производительность)?
- Стоит ли включать в проект сейчас или отложить?

2. **Headless-тесты:**
   - Написать тесты, которые эмулируют несколько клиентов через временные APPDATA-папки и общий shared-каталог.
   - Проверить все сценарии выше.
   - Использовать `threading` для параллельных операций.

3. **Ручные сценарии (для пользователя):**
   - Подготовить пошаговый чек-лист, который пользователь может прогнать на двух ПК.

## Формат результата

В ветке `arena/audit-network-porayonka` должно быть:

1. **Отчёт** `docs/network_audit_report.md` с разделами:
   - Проверенные сценарии.
   - Найденные баги (серьёзность, шаги воспроизведения, файл/функция).
   - Рекомендации.
   - Оценка чата.

2. **Тесты** в `porayonka-app/tests/test_network_stress.py`:
   - Минимум 10 проверок (конфликты, offline, вложения, latency, время).
   - Все тесты должны проходить (`ALL OK`) — либо если найден баг, тест должен его воспроизводить и падать с понятным сообщением.

3. **Фиксы (если найдены и они малы/средние):**
   - Если баг критичный и фикс небольшой — сделать fix и тест.
   - Если баг большой (например, нужно переписывать архитектуру) — описать в отчёте и предложить раунд 30.
