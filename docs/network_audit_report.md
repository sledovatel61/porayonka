## 2. Найденные баги

### БАГ 1 — ВЫСОКИЙ (потеря данных): старт приложения выбрасывал локальные офлайн-правки

- **Файл/функция:** `ui/controls/controls_tab.py`, `_load_initial`.
- **Шаги воспроизведения:**
  1. Админ работает без сети, добавляет/правит контроли (локальный `controls.json` обновляется, запись в shared не удаётся).
  2. Закрывает приложение. Сеть возвращается.
  3. При следующем старте shared непустой → `state["controls"] = shared` **целиком**, локальные офлайн-контроли исчезают из таблицы.
  4. При любом следующем сохранении локальный файл перезаписывается уже без них — **безвозвратная потеря**.
- **Фикс:** при старте выполняется `merge_controls(local, shared)`; если локальные данные добавили контроли — результат сразу записывается обратно в shared.
- **Тест:** сценарии 1 и 10 (`startup merge`).

### БАГ 2 — ВЫСОКИЙ (молчаливая потеря записи при гонке): один tmp-файл на всех клиентов

- **Файл/функция:** `core/controls_data.py`, `write_shared_controls`.
- **Шаги воспроизведения:** два админа сохраняют одновременно (SMB). Оба пишут в
  один и тот же `controls.json.tmp`: второй открывает файл (усекает содержимое
  первого), первый делает `os.replace(tmp → p)`; второй продолжает писать в уже
  переименованный (несвязанный) файл. Запись второго **молча уходит в «никуда»**,
  хотя функция вернула `True` и клиент уверен, что сохранил.
- **Сопутствующее:** бэкапы в shared-папке создавались на КАЖДУЮ запись каждого
  клиента и никогда не подрезались (накопительный рост); штемпель с точностью до
  секунды — два клиента в одну секунду перетирали бэкап друг друга.
- **Фикс:** уникальный tmp-файл (`<имя>.<uuid>.tmp`) + атомарный `os.replace`;
  штемпель бэкапа с микросекундами; подрезка бэкапов до 5.
- **Тест:** сценарий 7 (4 потока × 5 записей: файл всегда валидный JSON, нет
  tmp-остатков, `.bak` ≤ 5 при последовательных записях).

### БАГ 3 — ВЫСОКИЙ (битые файлы вложений): оборванная копия подменяла хороший файл

- **Файл/функция:** `core/controls_data.py`, `copy_attachment_to_shared` /
  `copy_attachment_to_local` / `sync_attachments_from_shared`.
- **Шаги воспроизведения:** сеть падает на полпути копирования вложения 30 МБ в
  shared. Копия шла сразу под финальным именем — в shared остаётся «полуфайл»
  `scan.pdf`. `resolve_attachment` отдаёт shared-файл **раньше** локального —
  пользователь открывает обрезанный файл вместо полного.
- **Фикс:** копирование через уникальный tmp + `os.replace`; при сбое tmp
  удаляется — битого файла под финальным именем не бывает.
- **Тест:** сценарий 5 (имитация обрыва через подмену `shutil.copy2`).

### БАГ 4 — СРЕДНИЙ (зависание UI): копирование вложений в UI-потоке

- **Файл/функция:** `ui/controls/controls_tab.py`, `_on_attach_picked`.
- **Шаги воспроизведения:** прикрепление PDF 10–50 МБ по медленному SMB —
  `shutil.copy2` выполняется синхронно в обработчике события; интерфейс замирает
  на секунды–минуты.
- **Фикс:** файлы > 5 МБ копируются в фоновом потоке, применение результата —
  через `_post_to_ui` в UI-потоке (с защитой от смены карточки за время копии);
  мелкие копируются синхронно (поведение раундов 23/28 сохранено, headless-тесты
  детерминированы). Предупреждение >20 МБ показывается сразу.
- **Тест:** сценарий 5c (реальный обработчик пикера + файл 6 МБ).

### БАГ 5 — СРЕДНИЙ (зависание UI): сетевой опрос выполнялся в UI-потоке

- **Файл/функция:** `ui/controls/controls_tab.py`, `_background_loop` / `_poll_network`.
- **Шаги воспроизведения:** `get_shared_mtime`/`read_shared_controls` по SMB с
  latency 0.5–2 с (а при недоступном сервере — с таймаутами в десятки секунд)
  маршаллились в UI-поток — интерфейс замирал на время каждого обращения, раз в
  20–60 с.
- **Сопутствующее:** при пустом shared-файле `shared_mtime` не обновлялся —
  файл перечитывался целиком на каждом цикле опроса бесконечно.
- **Фикс:** I/O вынесен в фоновый поток (`_poll_network_io`), применение —
  в UI-поток (`_poll_network_apply`, результат передаётся аргументом); файл не
  перечитывается, если mtime не изменился; при пустом shared mtime принимается.
- **Тест:** сценарий 6 (счётчик чтений через monkeypatch + проверка индикатора).

### БАГ 6 — СРЕДНИЙ (недетерминизм merge между часовыми поясами)

- **Файл/функция:** `core/controls_data.py`, `_updated_sort_key`.
- **Шаги воспроизведения:** naive-ISO `updated_at` (их пишет `datetime.now()`
  каждого ПК) конвертировался в epoch в ЛОКАЛЬНОМ поясе машины: один и тот же
  shared-файл давал разные решения merge на ПК в разных поясах.
- **Фикс:** naive-ISO нормализуется как UTC. В одном поясе поведение не
  изменилось (все сдвиги одинаковы, порядок сохраняется).
- **Тест:** сценарий 8 (точное сравнение с ожидаемым epoch).

### БАГ 7 — НИЗКИЙ (локальный файл отставал от state после merge)

- **Файл/функция:** `ui/controls/controls_tab.py`, `_persist`.
- **Шаги:** merge-before-write записывал объединение только в shared; локальный
  `controls.json` оставался до-merge версией. При перезапуске с выключенной сетью
  контроли из shared пропадали из локальной копии.
- **Фикс:** после merge `save_controls(merged)` и локально.
- **Тест:** сценарий 11 (локальный файл == state == shared).

## 3. Подтверждено корректным (не баги)

- **LWW без слияния полей** — конфликт редактирования решается целиком по
  `updated_at`; «поля A + поля B» не смешиваются (сценарий 2). Совпавший
  `updated_at` (в пределах микросекунды) — локальная версия, детерминированно.
- **Офлайн → онлайн** — merge (не подмена), локальные правки дороже; пустой
  shared не затирает локальные данные; при отсутствии файла — seed из локальных
  (сценарии 3, 6).
- **Удаление shared во время работы** — приложение продолжает работать на
  локальных; следующее сохранение пересоздаёт файл (сценарий 4).
- **User-фильтры** — пользователь видит только свои контроли (исполнитель /
  ответственный пункта / контролёр), включая «фамильные» совпадения (сценарий 7b).
- **Алармы** — антиспам-журнал, интервалы (user 2 ч / админ 24 ч), «new» — один
  раз; повторный цикл не создаёт лишних диалогов (сценарий 9).
- **merge-before-write в `_persist`** — сохранение не затирает чужие изменения
  (сценарий 11).
- **Синк вложений** — вложения другого админа подтягиваются из shared локально
  (сценарий 12).

## 4. Известные ограничения (не исправлено; рекомендации)

1. **Нет tombstone для удалений.** «Удалить навсегда» и «Удалить все» не
   распространяются: удалённый навсегда контроль воскреснет у другого админа при
   merge (документировано в `merge_controls`). Особо опасен кейс «Удалить все»:
   админ, бывший офлайн, при следующем сохранении запишет свои данные поверх
   пустого shared (воскрешение всех контролей). Это осознанный компромисс
   «не терять локальные правки» vs «распространять удаление»; различить их без
   tombstone невозможно. **Раунд 30:** tombstones или маркер поколения файла.
2. **Гранулярность mtime.** На ФС с грубой гранулярностью (FAT32 — 2 с,
   отдельные SMB-конфигурации) два изменения в одну секунду могут быть пропущены
   одним циклом опроса (догонятся следующим — 20–60 с). **Рекомендация:** в
   сигнатуру «изменился ли файл» добавить размер или счётчик ревизии в JSON.
3. **Часы «из будущего».** Контроль с `updated_at` из будущего детерминированно
   выигрывает merge, пока часы не выровняются. **Рекомендация (подтверждает
   задачу раунда 29):** предупреждать пользователя при отклонении `updated_at`
   от системного времени > 5–10 мин.
4. **Запись остаётся синхронной в UI-потоке.** Сохранение карточки и мелкие
   операции записи по медленному SMB могут подтормаживать UI (опрос уже вынесен
   в фон). Полное решение — сетевой слой в worker-потоках с таймаутами; против
   «вечных» SMB-хенгов (open() без таймаута) нужны низкоуровневые меры.
   **Раунд 30.**
5. **Пустой shared при старте** трактуется как «новое хранилище» → seed из
   локальных. Удобно при первом включении сети, но конфликтует с «Удалить все»
   (см. п.1). Неразличимо без tombstone.

## 5. Оценка чата между пользователями

**Вопрос:** реализуем ли чат с отправкой файлов/сообщений поверх той же shared-папки?

- **Да, технически реализуемо:** `messages.json` + тот же polling (20–60 с) +
  atomic-write; файлы — в папке рядом с `controls_attachments`. Архитектура уже
  содержит все кирпичи (`read/write_shared_*`, `_poll_network_*`, антидубль,
  атомарные копии).
- **Усложнение:** ~2–3 новых модуля (модели, данные, UI-панель) + ~20–30 % к коду
  синхронизации. Наследуются ВСЕ текущие ограничения: LWW, задержка доставки
  20–60 с, конфликты одновременного редактирования, рассинхрон часов, отсутствие
  настоящих push-уведомлений (только опрос).
- **Отдельный сервер/база нужны**, только если требуются: мгновенная доставка,
  полная история с поиском, файлы > 50 МБ, уведомления при закрытом приложении,
  работа вне одной локальной сети. Для отдела из ~15 машин в одной сети это
  избыточно.
- **Flet 0.23.2:** лента чата реализуема, но автопрокрутка вниз — осторожно
  (кастомный `on_scroll` падает с `KeyError 'sd'/'dir'`, раунд 16 — использовать
  только нативный скролл); перерисовка ленты раз в 20–60 с приметна, но терпима;
  вложения — через существующий `FilePicker`.
- **Вердикт:** сейчас НЕ включать — сначала стабилизировать сеть (tombstones,
  п.4 раздела 4). Если делать — MVP на shared-папке без сервера, раунд 30+.

## 6. Ручной чек-лист на двух ПК (для пользователя)

Подготовка: на ПК1 (админ) включить «Сетевой режим» в настройках вкладки
«Контроли», указать общую папку `\\<сервер>\общая\...`, сохранить. На ПК2 (админ
или пользователь) указать тот же путь.

1. **Одновременное добавление:** на обоих ПК добавьте по контролю с интервалом
   < 30 с. Через 1–2 мин у обоих должны появиться оба контроля, без дублей.
2. **Одновременное редактирование одного контроля:** оба откройте одну карточку;
   один меняет «Содержание», второй — «Исполнители»; сохраните оба. Победит
   сохранивший позже — у обоих будет ОДНА версия целиком (не «смесь» полей).
3. **Offline:** на ПК1 выключите сеть (отключите кабель/сетевой адаптер),
   добавьте контроль. Индикатор «Сеть: нет связи». Верните сеть — через ≤ 1 мин
   контроль появится на ПК2, а на ПК1 надпись «Сеть: админ».
4. **Удаление shared-файла:** при работающем приложении удалите
   `controls.json` из общей папки. Приложение продолжает работать; после любого
   сохранения файл пересоздаётся (бэкап — рядом, подрезается до 5 шт.).
5. **Большое вложение:** прикрепите файл 10–50 МБ к контролю на ПК1. UI не
   «замерзает»; если файл > 20 МБ — появится предупреждение. На ПК2 файл
   появится после синхронизации (≤ 1 мин) и откроется целиком.
6. **Битая сеть:** на ПК1 отключите сеть на 2–3 мин, работайте, включите —
   никаких «зависаний» намертво; индикатор переключается «нет связи» ⇄ «Сеть».
7. **Уведомления:** на ПК2 (пользователь) добавьте контроль на ПК1 со сроком
   «сегодня» и исполнителем = ПК2. На ПК2 в течение ~1 мин появится уведомление
   (один раз), повтор — не чаще раза в день (аларм-диалог — каждые 2 ч, пока не
   исполнено).
8. **Время на ПК:** переведите часы ПК2 на 5 минут вперёд, сделайте правку —
   она будет выигрывать конфликты, пока часы не выровняются (известное
   ограничение; рекомендуется синхронизация времени по сети).
