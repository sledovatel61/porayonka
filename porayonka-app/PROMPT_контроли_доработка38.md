## 1. Подтверждённые полевые симптомы и первичный аудит

### 1.1. Контроли задваиваются у пользователя

Полевой тест пользовательской desktop-редакции под ФИО **«Миронович Д.В.»** на другом ПК показал множество пар визуально одинаковых контролей. На скриншоте, например, попарно повторяются:

- `Иссоп-216-193-26`;
- `Иссоп-216-5006-25`;
- `ВХСОП-9848-25`;
- `Иссоп 216-1996-25`;
- `вхсоп-4186-26(дсп/266)`;
- `Иссоп-216-194-26`.

У пар совпадают не только входящие номера, но и содержание, исполнители, контролёр и сроки. Так быть не должно.

Текущий `core/controls_data.py::merge_controls()` делает union **только по `id`**. Если логически одна запись исторически получила разные UUID (повторный импорт, старый локальный кэш, прежняя миграция), обе остаются. Ещё опаснее: `ui/controls/controls_tab.py::_load_initial()` при `len(merged) > len(shared)` пишет union обратно в shared независимо от edition. Read-only пользователь не должен публиковать устаревший локальный кэш и загрязнять общий файл.

### 1.2. Обе Win7 Web-редакции установились, но не запускаются

Админская и пользовательская web-сборки на реальной Windows 7 падают одинаково:

Это **не** прежняя ошибка отсутствующего `api-ms-win-core-path-l1-1-0.dll`: Python уже стартовал и дошёл до импорта `pydantic_core`.

На машине сборки на момент аудита стояли незакреплённые транзитивные версии:

```text

flet        0.23.2
fastapi     0.141.1
```

`requirements.txt` фиксирует только `flet==0.23.2` и `openpyxl==3.1.5`, поэтому web runtime со временем изменился. Текущий Rust extension `_pydantic_core.pyd` несовместим с Win7 по используемым API. Добавление ещё одного hidden import эту ошибку не исправит.

### 1.3. После деинсталляции остаются файлы

Во всех четырёх `.iss` отсутствует `[UninstallDelete]`. Установщики создают после установки как минимум `edition.json.bak`, а приложение создаёт `%APPDATA%\porayonka\...`; эти файлы Inno автоматически не считает установленными и полностью не удаляет.

### 1.4. Вложение фактически копируется, но не видно сразу

После выбора фото/PDF в новой карточке файл добавляется, но строка/миниатюра не появляется сразу. Она становится видна только после сохранения, закрытия и повторного открытия карточки.

В `controls_tab.py` уже есть `_apply_attach_result()` и headless-сценарий 13, который утверждает обратное. Значит, тест не воспроизводит живой Flet 0.23.2 event/diff (особенно фоновой путь для файлов >5 МБ), либо обновляется не тот mounted control. Нужна диагностика реального UI, а не ещё один комментарий «исправлено».

### 1.5. Excel сейчас не заменяет весь список, но гарантий недостаточно

`core/controls_exporter.py::import_from_excel()` получает существующие записи, пропускает точное совпадение `incoming_number` и возвращает только новые. UI затем append-ит `parsed`. То есть сейчас это добавочный импорт, а не полная замена.

Но сравнение входящего номера не нормализовано, нет безопасного обновления существующей записи, а тесты не доказывают сохранение её `id`, `attachments`, локальных/shared-файлов, пунктов и других richer-полей. Это надо исправить и формально покрыть.

## 2. P0: устранить дубли без потери данных и без повторного заражения shared

### 2.1. Сначала установить источник дублей

Добавить диагностическую функцию/утилиту (без вывода персональных данных в публичные логи сверх необходимого), которая для local/shared базы показывает:

- одинаковые `id`;
- разные `id` с одинаковым нормализованным бизнес-ключом;
- источник и `updated_at` каждой версии;
- расхождения полей, пунктов и вложений.

Проверить минимум три источника: shared `controls.json`, локальный кэш пользователя и Excel-импорт. Не изменять реальные данные до создания backup.

### 2.2. Разделить семантику admin и user

- **User edition — строго read-only не только в UI, но и на уровне сети.** Когда shared доступен, он является авторитетным snapshot: пользователь читает его, синхронизирует вложения в локальный кэш и сохраняет локальный кэш только для offline-чтения. Пользователь не вызывает `write_shared_controls()` ни при старте, ни polling, ни закрытии.
- Когда shared недоступен, user показывает последний локальный кэш.
- После восстановления связи user заменяет/обновляет кэш authoritative shared-данными и не возвращает stale local-only записи в сеть.
- Admin сохраняет текущую offline/online merge-семантику, включая сохранность независимых новых записей, но получает защиту от логических дублей.

Edition брать из `core/edition.py`, а не доверять унаследованным `network_role`/`network_user` из appdata.

### 2.3. Безопасная логическая дедупликация и одноразовое лечение существующей базы

Разработать явный нормализованный business identity/fingerprint. Требования:

- нормализовать регистр, Unicode, NBSP/пробелы и типовые разделители входящего номера;
- не считать все записи с пустым номером одним контролем;
- не схлопывать разные реальные контроли только из-за похожего номера: использовать дополнительные стабильные признаки (дата поступления/инициатор/содержание) и консервативные правила;
- одинаковый валидный `id` остаётся главным identity для обычного LWW merge;
- для доказанных дублей с разными UUID выбрать canonical record детерминированно (полнота данных, наличие вложений, `updated_at`, стабильный tie-break);
- **объединить**, а не выбросить, уникальные `attachments`, tasks/milestones и значимые заполненные поля;
- если canonical `id` меняется, атомарно перенести/скопировать файлы из `controls_attachments/<loser_id>` в `<canonical_id>`, разрешить коллизии имён без перезаписи и переписать относительные пути;
- сделать backup local/shared JSON и папок вложений до первой миграции;
- миграция должна быть идемпотентна и не создавать новые дубли после повторных запусков;
- одновременно не менять отдельно оговорённую tombstone-семантику обычного удаления без отдельного теста.

Если полностью автоматическое схлопывание неоднозначной пары небезопасно, не удалять её молча: вывести admin-only отчёт/предпросмотр и дать подтверждение. Для точных пар, как на полевом скриншоте, лечение должно быть автоматическим и проверяемым.

### 2.4. Тесты P0 для дублей

Добавить сценарии минимум для:

1. user с чистым appdata + shared: нет дублей, shared не записывается;
2. user со stale local записью (другой UUID, те же бизнес-данные) + shared: одна строка, stale запись не выгружается;
3. shared уже содержит два разных UUID одной точной записи: admin-лечение оставляет одну;
4. у обоих дублей разные вложения и пункты: после лечения всё доступно у canonical записи, файлы физически целы;
5. два похожих, но реально разных контроля не схлопываются;
6. повторный запуск миграции ничего больше не меняет;
7. параллельная синхронизация нескольких admin не возвращает дубль.

## 3. P0: реально рабочие Web-сборки для Windows 7

### 3.1. Не маскировать `_pydantic_core` ещё одной DLL

Нужен воспроизводимый Win7 build profile. Исследовать и подтвердить совместимую с **Flet строго 0.23.2** связку web-зависимостей. Предпочтительные направления исследования:

1. закреплённая совместимая связка FastAPI/Starlette/Pydantic, не использующая несовместимый новый `pydantic-core` (например, Pydantic v1, если Flet 0.23.2 это допускает);
2. если это невозможно — сборка web-редакций совместимым Python toolchain, который реально запускается на Win7, с соответствующими wheels;
3. только как доказанный вариант — конкретная более старая версия `pydantic-core`, которая реально импортируется на Win7.

Не угадывать версии. Сверить metadata зависимостей, импорт `flet.fastapi`, запуск uvicorn, работу websocket-сессии и PyInstaller frozen runtime. Desktop Win10/11 сборки не должны получить случайный downgrade, если ему нужен отдельный профиль.

### 3.2. Зафиксировать зависимости и toolchain

- Создать отдельный version-pinned файл для Win7 web build (имя на усмотрение, например `requirements-win7-web.txt`) и использовать его в обоих web build scripts.
- Build-скрипт должен печатать и сохранять manifest: версия Python, разрядность, версии Flet/FastAPI/Starlette/Pydantic/PyInstaller и SHA256 итогового exe.
- Сборка должна идти в чистом отдельном venv/profile, а не зависеть от случайно обновлённого глобального окружения.
- Не повышать Flet выше 0.23.2.
- Проверки spec на static dirs `flet/web`, `flet/fastapi` и необходимые hidden imports сохранить.
- Проверить, нужен ли текущий `api-ms-win-core-path-l1-1-0.dll` выбранному Python; если нужен — оставить проверку SHA256. Не выдавать этот стаб за решение ошибки `_pydantic_core`.
- Рассмотреть `upx=False` для web exe/native extensions, если UPX влияет на загрузку, и подтвердить результат тестом.

### 3.3. Улучшить запуск и диагностику

- `start_web_win7.bat` не должен слепо открыть браузер через 4 секунды, если сервер уже упал. Дождаться доступности `http://127.0.0.1:8555` с разумным timeout; при провале показать путь к логу.
- Сохранять startup log в `%APPDATA%\porayonka\error.log` или отдельный ASCII-safe лог до импорта FastAPI/Pydantic, чтобы import-time crash не терялся.
- Обработать занятый порт понятным сообщением или безопасным выбором/проверкой порта.
- Не закрывать/не дублировать процесс сервера и браузер при повторном запуске.

### 3.4. Приёмка Win7

На реальной **Windows 7 SP1 x64** проверить обе установки с нуля:

- user Web запускается, браузер получает HTTP 200, websocket/Flet UI подключается;
- admin Web запускается с admin UI;
- user остаётся read-only и привязан к заданному ФИО;
- обе версии читают сеть и вложения;
- повторный запуск не создаёт второй сервер;
- лог не содержит `_pydantic_core`, missing procedure, HTTP 500 или missing web root;
- запуск после перезагрузки работает.

Приложить в отчёт OS version, manifest версий, SHA256 exe, фрагмент успешного startup log и результаты ручных шагов. Проверка только на Win10 compatibility mode не равна проверке Win7.

## 8. P1: ежедневное резервное копирование

Текущий `_make_backup()` создаёт лишь 3/5 копий JSON **перед перезаписью**. Это не ежедневный полный backup и не защищает все данные/вложения.

Реализовать ежедневный backup без заморозки UI:

### 8.1. Локальный snapshot

- Не чаще одного успешного backup за календарный день, но проверять при старте и во время долгой работы (приложение может жить в трее несколько дней).
- Snapshot должен включать все пользовательские JSON (`departments`, zonal, templates/settings/edition, controls) и `controls_attachments`.
- Не включать сам каталог backups рекурсивно, temp/lock-файлы и бесконечно растущие логи.
- Писать сначала во временный каталог/архив, затем атомарно публиковать; добавить manifest с датой, версией схемы и списком файлов/размеров (желательно SHA256 для критичных JSON).
- При частичной ошибке не помечать день успешным и не удалять предыдущий валидный snapshot.
- Retention сделать ограниченным и документированным (разумно 30 ежедневных копий; согласовать с объёмом вложений).
- Backup не должен запускаться одновременно несколькими Flet sessions web-процесса: lock процесса/файла.

### 8.2. Shared backup

Так как authoritative controls и scans лежат в UNC workspace, только admin должен раз в день создавать централизованный snapshot shared `controls.json` + `controls_attachments` в отдельном каталоге внутри workspace (например, `backups/YYYY-MM-DD`), с межпроцессным lock и retention. User никогда не создаёт и не удаляет shared backups.

Не блокировать UI на время большой копии. Не копировать открытый JSON в полузаписанном состоянии; использовать существующие атомарные гарантии/lock. Сбой сети не ломает локальную работу и отражается в ASCII-safe диагностике.

### 8.3. Restore и проверяемость

Минимум документировать и протестировать восстановление в temp-каталог. Желательно добавить admin-only просмотр статуса: дата последней успешной локальной/shared копии и путь, без опасной автоматической перезаписи рабочей базы.

Тесты: once-per-day, новый день, retention, partial failure, concurrent calls, отсутствие рекурсии, наличие attachments, offline shared, user не пишет shared.

## 9. P1: безопасный incremental Excel import/upsert без потери вложений

Импорт не должен заменять всю таблицу. Требуемая семантика:

- новые логические контроли добавляются;
- точные неизменившиеся дубли пропускаются;
- существующие логические контроли при необходимости обновляются данными Excel **in place**, сохраняя canonical `id`;
- `attachments` существующей записи и физические файлы никогда не очищаются из-за отсутствия/пустого поля в импортируемом Excel;
- локальные richer-поля, которых нет в обычной таблице (tasks, milestones, archive metadata, comments и т.п.), не стираются пустыми значениями;
- полный round-trip sheet с тем же `id` также не дублирует запись;
- сравнение входящего номера использует ту же нормализацию/business identity, что защита сети от дублей;
- одинаковые номера внутри самого импортируемого файла не добавляются дважды;
- операция создаёт backup до применения и по возможности коммитится атомарно;
- preview явно показывает статистику `новые / обновляемые / без изменений / конфликты / ошибки`, а не только `imported/skipped`;
- при конфликте неоднозначного соответствия не перетирать запись молча.

Обязательно добавить тест:

1. существующая запись `id=A` имеет два attachment path и реальные файлы;
2. Excel содержит обновлённые поля этой записи и одну новую запись;
3. после импорта старая запись всё ещё `id=A`, оба attachment path/файла доступны, новые значения применены по описанным merge-правилам;
4. новая запись имеет уникальный id;
5. повторный импорт того же файла идемпотентен и не меняет количество;
6. shared merge после импорта не создаёт старую и импортированную копии.
