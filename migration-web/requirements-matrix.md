## R01. Создание, просмотр и редактирование контроля

**[Код] Фактическое поведение.** Единая точка — `create_controls_tab`
(`ui/controls/controls_tab.py:441`); новая карточка — `_add_control → _open_detail(None)`
(`:5142`, `:2603`), просмотр/правка — клик по строке таблицы (`_build_row`, `:1455` —
`on_click=lambda e, c=ctl: _open_detail(c)`). Набор полей: вх. №, дата поступления,
инициатор (dropdown + инлайн-добавление), содержание, исполнители (мультивыбор), «за кем
контроль», тип, периодичность, «Следующая дата», «Конечная дата», комментарий, пункты,
промежуточные точки, вложения (`_open_detail`, `:2646–2860`).

Обязательным фактически является ОДНО поле — входящий номер: пусто → `error_text =
"Введите номер"` и выход без сохранения (`_save_detail`, `:3710–3717`). Дата поступления при
пустом значении подставляется автоматически «сегодня» + toast
(`:3750–3762`) — раньше здесь был тихий return. Остальные поля опциональны.

Даты текстом нигде не вводятся: только собственный русский календарь-сетка
(`ui/controls/russian_calendar.py:25+`, `_open_global_cal` `:2158`), выбор дня или «Сегодня».
Кнопки «Очистить» у полей даты в карточке нет — **[Код]** установленную дату нельзя снять из
UI, только заменить другой.

Сохранение перезаписывает объект ЦЕЛИКОМ (`:3800–3815`), затем `_persist` (`:708`) —
`save_controls` + (если сеть и не user-редакция) merge-before-write, лечение дублей и
`write_shared_controls`. Слияния полей двух редакторов нет.

При открытии существующей карточки админом берётся файловый lock в общей папке
(`:2607–2625`, `core/control_locks.py:112`); чужой активный lock → диалог, карточка НЕ
открывается; «мёртвый» (>10 мин, `:22`) перезахватывается; touch каждые ~60 с
(`_poll_locks_and_attachments` `:5295`). user-редакция lock не создаёт.

**Пограничный пример (синтетический).** Вх. № `ВХСОП-7001-26`, дата поступления пустая,
срок выбран 15.03.2026, затем пользователь передумал. Ожидаемо — снять срок; фактически —
нет: сохранится 15.03.2026 либо nothing при «Отмена».

**Целевое поведение.** Поля и смысл 1-в-1; серверная валидация: `incoming_number` непустой
(после нормализации), `receive_date` обязательна при создании (иначе явная ошибка, а не
самовольная дата — **[Владелец]**), даты принимаются в `YYYY-MM-DD` и `DD.MM.YYYY`; у каждой
даты — «Очистить». Права и `revision` проверяет сервер (R12).

**Намеренные отличия.** (1) автоподстановку даты поступления заменить явной ошибкой либо
оставить как opt-in **[Владелец]**; (2) текстовый ввод дат и очистка; (3) вместо lock-файлов —
`revision` + 409 (`decisions.md` D-02).

**Этап:** W02 (контракт), W03 (правила), W04 (форма).
**Проверка приёмки:** `POST /controls` без `incoming_number` → 422, в БД ничего; `PUT` с
`due_date: null` поверх значения → в БД NULL; `31.02.2026` → 422 с указанием поля; две
сессии открыли одну карточку, вторая сохраняет позже → 409, её несохранённый ввод сохранён
(R22).

## R02. Все поля `Control` без потерь

**[Код]** Модель — `core/controls_models.py:362–386` (22 поля), `to_dict` `:387`,
`from_dict` `:414–438`. `from_dict` читает только известные ключи — **[Код]** любой
посторонний ключ в `controls.json` теряется при первой перезаписи, молча.
`from_dict` также «лечит»: отсутствующий `id` → новый `uuid4()` (`:416`), пустой
`control_type` → `once` (`:423`), `period_days` → 7 (`:424`), пустые `created_at/updated_at`
→ «сейчас» (`:436–437`): повреждённые значения не помечаются, а подменяются.
`_heal_missing_ids` (`core/controls_data.py:182–212`) при загрузке назначает id отсутствующим
записям: сначала из общего префикса папки вложений (`_attachments_prefix` `:169–180`), иначе
новый uuid, и сразу сохраняет файл (иначе uuid перевыдавался бы каждый запуск и вложения
отвязывались вновь).

**Пограничный пример.** `"id": null, "attachments": ["7f0c…/скан.pdf"]` → id станет `7f0c…`
(связь сохранится). `"id": null, "attachments": []` → новый uuid, «прежняя» запись
идентифицировать нельзя. **[Код]**

**Целевое поведение.** Полный mapping — `field-mapping.md`. Миграция обязана хранить
исходный JSON записи (`control_legacy_raw` или эквивалент), ничего не «улучшать»;
неизвестные/дефектные значения выводятся в отчёт. Существующие UUID сохраняются;
«выдуманный» uuid допускается только там, где legacy уже его выдал, и помечается.

**Этап:** W02 (схема), W07 (миграция).
**Проверка приёмки:** для каждой записи — сверка «legacy JSON → БД → полный Excel-экспорт»
по всем 22 полям + полям пунктов/точек; пустые значения остались пустыми; число записей
совпадает; отчёт содержит список всех «исцелений» с причинами.

## R03. Пункты задания (`ControlTask`)

**[Код]** `core/controls_models.py:119–155` (`id`, `title`, `assignees`, `due_date`,
`is_done`, `done_date`, `comment`). Источники: карточка (черновик `detail_state["tasks"]`,
`:2860–3010`) и парсер содержания при импорте (`parse_content_tasks` `:232–305`).
Порядок = позиция списка; поля `order` нет **[Код]**.

При сохранении карточки: пункт с пустым `title` НЕ сохраняется (`:3766–3769`) — удаление
тихое; существующие пункты сохраняют `task_id` (`:3779`), новые получают `uuid4()`;
`done_date` сохраняется (раньше терялась — раунд 19). Ответственные пунктов автоматически
добавляются в исполнители контроля (только добавление; ручное снятие не откатывается) —
`_sync_exec_from_tasks` `:2731–2755`. Перед пересборкой списка значения снимаются из
виджетов в черновик (`_harvest_task_drafts` `:2841–2859`), иначе перестройка затирала
выбранных ответственных (исторический баг раунда 21).

**Пограничный пример.** Пункты: «п. 1» (Романов Р.Р., 10.03.2026), «пункт без названия» с
датой 12.03.2026, «п. 3» (Левченко Л.Л.). После сохранения в контроле два пункта, дата
«пустого» потеряна без предупреждения. **[Код]**

**Целевое поведение.** Таблица `control_task` с `ordinal`, стабильным `id`, валидацией
`title` (пустой → 422 с указанием индекса), `assignees` — ссылки `person_id` (R11).
`done_date` ставится/снимается только вместе с `is_done`, на сервере.

**Этап:** W02/W03 (сущность и правила), W04 (редактор).
**Проверка приёмки:** создать 5 пунктов, удалить 2-й, добавить новый → порядок
1,3,4,5,new; `id` выживших не изменились; `is_done` + дата → `done_date`; снятие → NULL;
`title: ""` → 422 и состояние не изменилось.

## R04. Промежуточные сроки (`ControlMilestone`)

**[Код]** `core/controls_models.py:336–360` (`id`, `date`, `note`, `is_done`). Секция
«Промежуточные точки» доступна для обоих типов контроля (`milestones_col.visible = True`,
`:3020`; привязка только к «постоянному» снята — комментарий `:2817–2833`). Строка без даты
И без примечания не сохраняется (`:3781–3783`).
**Критично:** при каждом сохранении создаётся `ControlMilestone(id=str(uuid4()))`
(`:3784`) — идентификатор точки НЕ стабилен, внешние ссылки и история изменений точки
невозможны. `next_milestone` (`:458–463`) определена, в UI не вызывается **[Код]**; участие
точек в расчёте — только через `effective_due_date` (`:441–456`).

**Пограничный пример.** `due_date=01.03.2026`, точки 15.02 и 20.02 → `effective_due_date`
= 15.02, статус по нему, сохранённый `due_date` остаётся 01.03 (его правит только
`sync_due_after_tasks`, который смотрит на пункты). После сохранения карточки id обеих точек
меняются. **[Код]**

**Целевое поведение.** Отдельная таблица со стабильным `id` + `ordinal`; отметка точки
исполненной НЕ переносит общий срок автоматически (как в legacy); явный перенос — только по
решению **[Владелец]**.

**Этап:** W02/W03/W04.
**Проверка приёмки:** создать 3 точки, отметить 1-ю исполненной, изменить примечание → id
всех трёх стабильны; `date=None, note=""` → не создаётся; пустая дата при непустом
примечании легальна.

## R05. Разовый/периодический, `period_days`, `due_date`, `end_date`

**[Код]** `ONE_TIME="once"`, `PERIODIC="periodic"` (`core/controls_models.py:11–12`).
`period_days` — целое число ДНЕЙ; пресеты UI: 1, 7, 30, 91, 182, 365 и «Свой интервал»
(`ui/controls/controls_tab.py:216–226`); обратное отображение — по точному совпадению дней,
иначе «custom» (`_period_key` `:242–247`). «Ежемесячно» = ровно 30 дней, «ежеквартально» =
91, «каждые полгода» = 182, «ежегодно» = 365 — **[Код]** это НЕ календарные единицы.
Значение по умолчанию — 7 (`core/controls_models.py:372`). «Свой интервал» — `max(1, int(…))`
с падением на 7 при невалидном вводе (`:2799–2806`).

Подсказка «Следующие: …» = `due + period_days·i`, i=1..3 (`_refresh_cycle_hint`
`:2808–2815`) — только текст, в модель не пишется.

`end_date`:
- у периодического — «до какой даты действует»; `end_date < today` → статус `COMPLETED`
  (`core/controls_models.py:502–516`); `end_date == today` завершённым НЕ считается;
- у разового — «срок разового контроля» (смысл колонки H Excel, раунд 18), при этом поле в
  карточке СКРЫТО (`end_box.visible = … == PERIODIC`, `:2788`), но значение сохраняется
  (раунд 22: сохранение карточки больше не стирает `end_date` у разового, `:3808`).

«Переключение в разовый очищает `end_date`» — **не подтверждается кодом**: `_on_type_change`
(`:2817–2833`) меняет только видимость, `_save_detail` пишет
`c.end_date = detail_state["end_date"]` при любом типе **[Код]**. Формулировка R05 в
`02-requirements.md` противоречит legacy → расхождение зафиксировано (`decisions.md` D-12,
`risk-register.md` RISK-19).

Автоматического переноса срока при завершении/исполнении периода НЕТ: `_do_complete` (`:4350`)
ставит `done/done_date` и архивирует; `_extend/_do_extend` удалены (комментарий
`:4344–4348`) **[Код]**.

**Пограничный пример.** `periodic`, `period_days=30`, `due=10.01.2026`, `end=01.03.2026`,
сегодня 05.03.2026 → `completed` (не `overdue`). При `end=10.03.2026` → `overdue`. **[Код]**

**Целевое поведение.** Сохранять «N дней» буквально (миграция не пересчитывает 30 дней в
месяц). Тип, период, `due_date`, `end_date` — отдельные поля; подсказка следующих дат
считается по тому же правилу. Явное «продлить срок» — только по решению **[Владелец]**.

**Этап:** W03 (правила), W04 (форма), W07 (миграция `period_days` как есть).
**Проверка приёмки:** 30 дней ≠ календарный месяц (`due=31.01.2026` + 30 → `02.03.2026`);
`end == today` → не `completed`; переключение типа — поведение зафиксировано тестом
(сохраняется ИЛИ очищается — по решению); `due=29.02.2028` + 1 день → `01.03.2028`.

## R06. Статусы срока

**[Код]** Семь статусов `overdue, today, soon, in_progress, done, none, completed`
(`core/controls_models.py:15–21`), подписи/цвета `:592–611` (в UI действует другая палитра —
`ui/controls/glass_theme.py:16–46`; расхождение отмечено в `ui-outline.md` §0).
`deadline_status` (`:502–530`): `done` → `DONE`; периодический и `end_date < today` →
`COMPLETED`; далее по `effective_due_date` → `<` OVERDUE, `==` TODAY, `≤ soon_days` SOON,
иначе IN_PROGRESS; ни одной даты → `NO_DATE`. Персональный `user_deadline_status`
(`:565–590`) идентичен, но `None` → **`IN_PROGRESS`**, а не `NO_DATE`.

**Пограничные случаи [Код]:**
- `soon`: `(due - today).days <= max(0, soon_days)` → при 3 днях: через 3 дня SOON, через 4
  — IN_PROGRESS;
- `done=True` даёт `DONE` независимо от просроченных дат и истёкшего `end_date` (проверка
  `done` первая);
- все пункты исполнены и `due_date` не заполнен → `NO_DATE`; заполненная просроченная
  `due_date` → `OVERDUE`.

**Целевое поведение.** Тот же алгоритм — единственная реализация на сервере + зеркальные
клиентские тесты. «Сегодня» — по поясу организации (предложение `Europe/Moscow`, **[Владелец]**,
`decisions.md` D-05).

**Этап:** W03.
**Проверка приёмки:** таблица границ (сегодня/±1/±soon/±(soon+1), 29.02.2028, `end` =
сегодня/вчера, все пункты исполнены, только исполненные + одна неисполненная точка) —
admin- и user-режимы.

## R07. Исполнение пункта пересчитывает ближайший общий срок

**[Код]** `sync_due_after_tasks` (`core/controls_models.py:465–500`). Вызывается:
(1) при сохранении карточки (`ui/controls/controls_tab.py:3813`); (2) при подтверждении
диалога «Исполнен пункт» (`:3928–3930`, там же синхронизируется черновик, чтобы «Сохранить»
не откатил сдвиг).

Правила: (1) пунктов нет → ничего; (2) неисполненных пунктов нет → ничего (контроль ждёт
закрытия); (3) `due_date` пуста ИЛИ равна дате исполненного пункта и не встречается среди
неисполненных → `min(неисполненные)`; (4) у РАЗОВОГО `end_date < max(неисполненные)` →
поднимается до `max(неисполненные)`, ручная дата позже пунктов сохраняется; (5) у
периодического `end_date` не меняется никогда.
`due_date`, не совпадающая с датой исполненного пункта, не трогается — «ручная» дата

### Архив и периодичность

**S-08 (R09) — «исполнен» против «восстановлен».** Завершён 10.02.2026 (auto-archive

**S-09 (R05, R06) — периодический без конечной даты + «месяц».** `periodic`,

(«Удалить все» + офлайн-админ) закрывается архитектурно.
