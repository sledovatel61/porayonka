## 2. Матрица R01–R24

### R01 — Создание, просмотр, редактирование контроля; обязательные поля; русский ввод дат

**Факт [К][З].** Карточка открывается `_open_detail(ctl)` (`controls_tab.py:2603`); для новой — `_open_detail(None)`
из `_add_control` (5142). Сохранение — `_save_detail` (3707):
- обязателен только **входящий номер**: при пустом поле ставится `error_text = "Введите номер"` и выход без записи (3710–3717);
- **«Дата поступления» фактически не обязательна**: если пустая, при сохранении подставляется сегодня
  и показывается тост ««Дата поступления» была пустой — проставлена автоматически» (3750–3762, дубль 3819–3821).
  Метка поля при этом содержит `*` (`_field_with_label("Дата поступления *")`, ~4022) — расхождение «звёздочка есть, проверки нет»;
- **русский ввод дат с клавиатуры отсутствует**: поле даты — это `ft.Text` (не `TextField`) внутри контейнера,
  клик открывает русский календарь (`ui/controls/russian_calendar.py:86-120`, `create_russian_date_field`).
  Отображение `DD.MM.YYYY`, хранение ISO `YYYY-MM-DD` (`controls_models.py:26-38`);
- порядок сохранения: поля → пункты → точки → `sync_due_after_tasks(c)` (3824) → если `due_date` пустая,
  подставляется `effective_due_date` (3825–3828) → замена/добавление в `state["controls"]` → `_persist` (3834).

**Пограничный пример [З].** Новая карточка: номер пуст, дата поступления пуста, скан прикреплён.
Ожидание legacy: запись НЕ создаётся, поле номера подсвечено, дата не подставляется (выход до этой ветки).

**Целевое поведение [П].** Серверная валидация: `incoming_number` обязателен (trim, длина ≤ 120),
`receive_date` обязательна для **новых** записей (в legacy она «молча» становилась сегодня — это не требование,
а обходной путь; см. расхождение D-01). Даты вводятся и клавиатурой (`DD.MM.YYYY`, `DD.MM.YY`), и календарём;
формат хранения — `DATE` без времени. Ошибка валидации возвращается с указанием поля, запись не создаётся.

**Намеренное отличие [П].** (1) клавиатурный ввод дат; (2) явная ошибка вместо автоподстановки сегодняшней даты;
(3) валидация на сервере, а не только в форме.

**Этап.** W02 (контракт/валидация) + W03 (операции) + W04 (форма).

**Приёмка.** POST с валидным примером → 201 и запись в БД; POST с пустым номером → 422, в БД ничего не появилось,
в ответе имя поля; PUT с `receive_date = null` у существующей записи → 422 (или явное решение владельца сохранить
legacy-поведение). Дата `29.02.2028` принимается, `31.02.2026` отклоняется.

### R02 — Все поля Control без потерь

**Факт [К][З].** 22 поля (`controls_models.py:362-440`): `id, incoming_number, receive_date, initiator, content,
executors, controller, control_type, period_days, due_date, end_date, done, done_date, comment, tasks, milestones,
attachments, archived, archived_at, archive_reason, created_at, updated_at`.
`to_dict`/`from_dict` симметричны для всех полей; полный список совпадает с `02-requirements.md` **[К]**.
Особенности `from_dict` (415–440):
- `id = d.get("id") or str(uuid.uuid4())` — **пустой/отсутствующий id молча заменяется новым UUID при каждом чтении**;
  в сохранённых данных это лечится `_heal_missing_ids` (`controls_data.py:182-212`) с немедленной записью (102–110);
- `period_days` по умолчанию **7**;
- `created_at`/`updated_at` при отсутствии — `datetime.now()` (локальное время без часового пояса) **[З: H]**.

**Пограничный пример [З].** JSON-запись `{"incoming_number":"ВХ-1"}` без `id/created_at/updated_at`:
`Control.from_dict` выдаёт случайный UUID и «сейчас» в обоих timestamps; два последовательных вызова дают **разные** id.

**Целевое поведение [П].** Все 22 поля переносятся 1:1 (см. `field-mapping.md`). `created_at`/`updated_at` —
`timestamptz` в UTC; при миграции берётся legacy-значение, а не «сейчас». Пустой legacy-id не заменяется
новым UUID на лету: запись попадает в отчёт миграции и получает id только из детерминированного manifest.

**Намеренное отличие [П].** Отказ от «лечения» id при чтении: любая подстановка id — только воспроизводимым
mapping-файлом (требование `02-requirements.md` §«Правила с повышенным риском»).

**Этап.** W02 (схема), W07 (миграция и сверка).

**Приёмка.** Сверка «legacy JSON → БД → контрольный экспорт» по всем 22 полям для 100 % записей,
включая пустые значения; отдельный отчёт по записям с пустым/дублирующимся id; повторный прогон миграции
не меняет ни одного id.

### R03 — Пункты (ControlTask): id, описание, исполнители, срок, исполнение, дата исполнения, комментарий

**Факт [К].** Модель: `controls_models.py:119-160` (`id, title, assignees, due_date, is_done, done_date, comment`).
В карточке пункт — «плашка» (`_build_single_task_card`, ~2881): заголовок (`hint="Пункт"`), срок через общий
календарь, inline-мультивыбор ответственных (`_build_inline_multi`, 2002), чекбокс «исполнено»,
комментарий. Поведение:
- чекбокс «исполнено» в черновике ставит `done_date = сегодня`, снятие — обнуляет (2905–2912);
- при сохранении **id пункта сохраняется** (`task_id` из живой модели, 3779) — регресс раунда 19 закрыт;
- пункт с пустым заголовком при сохранении **отбрасывается** (3768–3775) — молчаливая потеря черновика пункта;
- иконка `DRAG_INDICATOR` (2932) **декоративна**: обработчиков перетаскивания нет — порядок пунктов
  меняется только порядком добавления/удаления **[К]**;
- отдельный админский диалог «Исполнение пунктов задания» (`_open_task_done_dlg`, 3873) — мультивыбор пунктов
  и одна дата исполнения на все выбранные; работает с живой моделью, затем `sync_due_after_tasks(ctl)` (3936);
- исполнители контроля автоматически дополняются ответственными пунктов (`_sync_exec_from_tasks`, ~2728;
  при импорте — `controls_exporter.py:795-799`).

**Пограничный пример [П].** Пункты: п.1 (срок 31.08, исполнен 11.08), п.10 (срок 28.08, не исполнен),
п.3 (срок 31.08). `due_date` контроля = 28.08. После исполнения п.10 → `sync_due_after_tasks` сдвигает
`due_date` на 31.08 (минимум неисполненных) **[З: D1/D2]**.

**Целевое поведение [П].** Пункт — отдельная сущность `control_task` со стабильным `id`, явным полем порядка
(`position`), FK на контроль и на людей (`person_id`), а не строками ФИО. Пустой заголовок → ошибка валидации,
а не молчаливое удаление. Перетаскивание для порядка — опционально, но порядок обязан сохраняться и после
перезагрузки.

**Намеренное отличие [П].** (1) явный `position` вместо порядка массива; (2) назначения через `person_id`;
(3) запрет молчаливого выбрасывания пункта с пустым названием.

**Этап.** W02 (схема), W03 (операции), W04 (UI).

**Приёмка.** Создать контроль с 3 пунктами и 2–3 ответственными в каждом → перезагрузить → порядок, id,
исполнение и даты совпадают; повторное изменение пункта не создаёт новый id; пункт с пустым названием
не сохраняется и даёт понятную ошибку.

### R04 — Промежуточные сроки (ControlMilestone): id, дата, примечание, исполнение

**Факт [К][З].** Модель: `controls_models.py:336-359` (`id, date, note, is_done`).
Влияние на общий срок: `effective_due_date` (441) учитывает минимум среди **неисполненных** точек;
`next_milestone` (458) возвращает ближайшую неисполненную. Секция «Промежуточные точки» видна всегда
(`milestones_col.visible = True`, 2997).

**Критический факт [К][З]: identity точки НЕ сохраняется.** При сохранении карточки каждая точка
пересоздаётся с новым UUID: `new_miles.append(ControlMilestone(id=str(uuid4()), ...))` (`controls_tab.py:3784`);
черновик точки хранит только `{"date_ref", "note", "is_done"}` (3040, 3015) — поля `id` в нём нет вообще.
Следствия: (а) любая ссылка на milestone извне (журнал, уведомления, будущие связи) теряет смысл после каждого
сохранения; (б) порядок точек определяется только порядком в массиве. Точка без даты **и** без примечания
при сохранении отбрасывается (3782–3783).

**Пограничный пример [З].** Контроль без `due_date` с одной неисполненной точкой на вчера:
`effective_due_date` = дата точки, `deadline_status` = `overdue`. Если точку отметить исполненной —
`effective_due_date` = `None`, статус = `none` («Без срока»).

**Целевое поведение [П].** `control_milestone` со стабильным `id` (сохраняется при любом обновлении),
`position`, FK на контроль. Влияние на общий срок — то же правило (минимум неисполненных), реализованное
в одном серверном модуле, а не в трёх местах.

**Намеренное отличие [П].** Стабильный id точек — исправление legacy-дефекта, а не изменение бизнес-правила.

**Этап.** W02 (схема), W03 (правило срока), W04 (UI), W07 (миграция: legacy-id точек сохраняются как есть,
несмотря на их «одноразовость» — см. `field-mapping.md` §4).

**Приёмка.** Добавить 2 точки, сохранить, изменить одну, сохранить ещё раз → id обеих точек не изменились;
исполнение точки меняет общий срок по правилу минимума; точка без даты и без текста не создаётся.

### R05 — Разовый/периодический, period_days, due_date, end_date

**Факт [К][З].** `control_type` ∈ {`once`, `periodic`} (`controls_models.py:12-13`). `period_days` по умолчанию 7.
В карточке выбор периодичности — список `_PERIOD_LABELS` (`controls_tab.py:216-227`):
ежедневно 1, еженедельно 7, ежемесячно **30**, ежеквартально **91**, каждое полугодие **182**, ежегодно **365**,
«Свой интервал» → `max(1, int(...))` (2800–2807). Подсказка «Следующие: …» считает 3 даты
`base + period_days*i`, где `base = due_date или сегодня` (`_refresh_cycle_hint`, 2808–2816) — **это только
отображение, в данные ничего не пишется**.

**Автоматического переноса срока периодического контроля в коде нет [К][З].** После исполнения
(`done`/исполнение пункта) `due_date` периодического контроля не сдвигается на `due_date + period_days`:
единственные места, меняющие `due_date`, — `_save_detail` (3825–3828), `sync_due_after_tasks` (465) и импорт Excel.
Изобретать автоперенос в новой системе нельзя без отдельного решения владельца **[Р]**.

**`end_date` у разового контроля сохраняется [К].** `_save_detail` пишет `c.end_date = detail_state["end_date"]`
независимо от типа (3812–3814, комментарий раунда 22). При этом поле «Конечная дата» **скрыто** для разового
типа (`_on_type_change`: `end_box.visible = is_per`, 2817–2821) — то есть у разового контроля может быть
`end_date`, который пользователь не видит и не может очистить, не переключив тип. Этот `end_date`:
- используется как «срок разового контроля» в Excel-колонке H (`control_type_text`, `controls_exporter.py:90-103`);
- сдвигается `sync_due_after_tasks`, если он раньше последнего неисполненного пункта (494–497) **[З: D3/D4]**;
- **не влияет** на статус разового контроля (`COMPLETED` вычисляется только для `periodic`, 507–510).

**Расхождение с планом (D-02) [К].** `02-requirements.md` R05 требует: «переключение в разовый очищает end_date».
Код делает обратное (осознанно, раунд 22). Требуется явное решение владельца: сохранить legacy-поведение
(end_date разового = «срок разового контроля», видимый в Excel H) или очищать. Рекомендация агента: **сохранить**
и сделать поле видимым/редактируемым для обоих типов, иначе ломается Excel-совместимость (R15/R16).

**Пограничный пример [З].** `periodic`, `period_days=30`, `end_date` = вчера, `due_date` = +5 дней, `done=False`
→ статус `completed` («Завершён») и у admin, и у user, хотя контроль не исполнен и срок в будущем.

**Целевое поведение [П].** `period_days` — `int ≥ 1` (0 недопустим), `end_date` — nullable;
для `periodic` статус «Завершён» при `end_date < today`; для `once` `end_date` трактуется как «срок разового
контроля» и отображается в карточке. Переключение типа не стирает данные молча: очистка `end_date` — явное
действие пользователя, подтверждённое в UI.

**Этап.** W02 (схема), W03 (правила), W04 (UI), W05 (Excel H).

**Приёмка.** Периодический контроль без `end_date` допустим; с `end_date` в прошлом → «Завершён»;
переключение periodic→once сохраняет `end_date` (или очищает — по решению владельца, зафиксированному в
`decisions.md`); `period_days=0` отклоняется сервером; «30 дней» не превращается в календарный месяц
ни в расчётах, ни в подписях.

### R06 — Статусы overdue/today/soon/in_progress/done/completed/none

**Факт [К][З].** `deadline_status(control, soon_days=3)` (`controls_models.py:502-524`), порядок проверок:
1. `done` → `done`;
2. `periodic` и `end_date < today` → `completed`;
3. `effective_due_date` = `None` → `none`;
4. `< today` → `overdue`; `== today` → `today`; `≤ soon_days` → `soon`; иначе `in_progress`.

Границы, измеренные зондом при `soon_days=3` **[З]**: −1 день → `overdue`; 0 → `today`; +1 → `soon`;
+3 → `soon`; +4 → `in_progress`; без срока → `none`; при `soon_days=0` +1 день → `in_progress`.
`today = date.today()` — **локальные часы клиента** (в новой системе — серверный часовой пояс, см. `decisions.md`).
Метки и цвета: `STATUS_LABELS`/`STATUS_COLORS` (587–611).

**Пограничный пример [З].** 29.02 високосного года как `due_date` парсится корректно (`date.fromisoformat`);
контроль с `due_date = 2028-02-29` в день 2028-02-28 → `soon` (1 день), 2028-03-01 → `overdue`.

**Целевое поведение [П].** Тот же порядок правил, но «сегодня» — серверная дата в согласованном часовом поясе
(предложено Europe/Moscow, **[Р]**); `soon_days` — серверная настройка. Статус считается на сервере и для списка,
и для счётчиков, и для экспорта одним модулем.

**Намеренное отличие [П].** Клиентские часы не влияют на статус.

**Этап.** W03 (правила), W06 (уведомления).

**Приёмка.** Таблица граничных дат (−1/0/+1/+3/+4, `soon_days` 0 и 3, `none`, `completed`, `done`,
високосный год) сверяется с legacy-поведением на фиксированной дате «сегодня» (инъекция даты в тестах).

### R07 — Исполнение пункта пересчитывает ближайший общий срок

**Факт [К][З].** `sync_due_after_tasks(control)` (`controls_models.py:465-497`). Правила, подтверждённые зондом:

| № | Вход | Результат [З] |
|---|---|---|
| D1 | `due_date` равна дате **исполненного** пункта и не встречается среди неисполненных | сдвиг на `min(неисполненные)` |
| D2 | `due_date` пустая, пункты есть | проставляется `min(неисполненные)` |
| D3 | `once`, `end_date` раньше `max(неисполненные)` | `end_date` сдвигается на `max(неисполненные)` |
| D4 | `once`, ручная `end_date` **позже** пунктов | не трогается |
| D5 | все пункты исполнены | даты не меняются (контроль ждёт закрытия) |
| D6 | `periodic`, `end_date` раньше пунктов | `due_date` сдвигается, `end_date` **не трогается** (ветка только для `once`) |
| — | пунктов нет | функция выходит сразу (472–474) |

Вызывается в двух местах: `_save_detail` (3824) и диалог исполнения пунктов (3936).
Исполненные пункты в расчёте `effective_due_date` **не участвуют** (450–453).

**Пограничный пример [З].** D3: `once`, `end_date = due_date = +2 дня`, п.10 (+2 дня) исполнен, п.1 (+8 дней) нет
→ после `sync_due_after_tasks` обе даты = +8 дней.

**Целевое поведение [П].** Перенести функцию 1:1 в серверный модуль доменной логики (с указанием источника),
вызывать в транзакции исполнения пункта и сохранения карточки. Не расширять правила молча
(в частности, не добавлять сдвиг `end_date` для `periodic` — в legacy его нет).

**Этап.** W03.

**Приёмка.** Шесть сценариев D1–D6 как тест-кейсы с фиксированной датой; результат побайтово совпадает
с legacy-функцией (сравнение на одинаковых входах).

### R08 — Индивидуальный срок и статус пользователя

**Факт [К][З].** `user_effective_due_date(control, user_name)` (`controls_models.py:532-563`):
1. пустое имя → общий `effective_due_date` (admin-вид);
2. минимум дат **неисполненных** пунктов, где `name_matches(user_name, assignee)`;
3. своих пунктов нет → общий срок, **только если** пользователь совпадает как исполнитель (`executors`)
   или как контролёр (`controller`) (556–561);
4. иначе `None` (562).

`user_deadline_status` (565–587): `done` → `done`; `periodic` с истёкшей `end_date` → `completed`;
`None` → **`in_progress`** (не `none`!, 581–582); далее как в общем статусе.

Измерено зондом **[З]**:

| № | Ситуация | Дата | Статус user | Статус admin |
|---|---|---|---|---|
| B1 | чужой пункт просрочен, свой пункт +10 дней | своя (+10) | `in_progress` | `overdue` |
| B2 | **свои пункты исполнены**, чужой просрочен, пользователь входит в `executors` | общая (вчерашняя) | **`overdue`** | `overdue` |
| B3 | своих пунктов нет, пользователь — только `controller` | общая | `overdue` | `overdue` |
| B4 | своих пунктов нет, не исполнитель и не контролёр | `None` | `in_progress` | `overdue` |
| B5 | пустое имя (admin) | общая | — | `overdue` |

**Ответ на вопрос промпта «что происходит, если свои пункты исполнены, но есть чужие»:** если пользователь
остался в `executors`/`controller` — он получает **общий** срок и, следовательно, **чужую просрочку** (B2/B3).
Полностью «чужие» просрочки не показываются только когда пользователь не связан с контролем (B4).
Это не дефект, а фактическое правило; переносить нужно его, а не идею из названия функции.

**Сопоставление ФИО — фамильное и небезопасное [К][З].** `name_matches` (89–117):
точное совпадение → True; **фамилия как подстрока** → True; похожесть слова ≥ 0.80 (Левенштейн) → True;
фамилия короче 3 символов не матчится. Измерено:
- `Иванов Иван Иванович` vs `Иванов Пётр Сергеевич` → **True** (однофамильцы неразличимы);
- `Иванов И.И.` vs `Иванова Мария Петровна` → **True** (подстрока «иванов» входит в «иванова» — разные фамилии!);
- `Петров П.П.` vs `Петроф П.П.` → True (опечатка);
- `Ли А.Б.` vs `Ли` → False (короткая фамилия).

**Целевое поведение [П].** Личный срок считается по `person_id` назначений пункта, а не по строке ФИО.
Правила fallback (своих пунктов нет → общий срок для исполнителя/контролёра; иначе «нет личного срока»)
сохраняются дословно. `name_matches` допускается **только** как инструмент миграционного сопоставления
и поиска по справочнику — **никогда** для авторизации и не для определения «свой/чужой» в рантайме
(требование `02-requirements.md`).

**Намеренное отличие [П].** (1) идентичность по `person_id` вместо фамильного совпадения;
(2) статус «В работе» при отсутствии личного срока сохраняется как есть (не унифицировать с «Без срока»).

**Этап.** W02 (идентичность), W03 (правила), W04 (отображение), W07 (миграционное сопоставление ФИО).

**Приёмка.** Сценарии B1–B5 как тесты; отдельный тест «однофамильцы»: два разных человека с одной фамилией
— каждый видит только свои пункты; тест «Иванов/Иванова» — разные люди, срок не пересекается.

### R09 — Завершение, архив (done/deleted), восстановление, окончательное удаление

**Факт [К].**
- «Контроль исполнен» → `_open_done_dialog` (4360) с выбором даты → `_do_complete` (4350):
  `done=True`, `done_date=выбранная дата`, `updated_at=now`, **и сразу `archive_control(ctl, "done")`** (4355).
  То есть исполнение = done + архив с причиной `done`; отдельного «исполнить без архивации» в UI нет;
- «В архив» из карточки → `_delete_detail` (3847) с подтверждением → `archive_control(ctl, "deleted")` (3855);
- `archive_control` (`controls_data.py:831-838`): `archived=True`, `archived_at=now`, `archive_reason=reason`,
  `updated_at=now`;
- «Восстановить» → `_restore` (4420) → `restore_control` (839–848): сбрасывает **только**
  `archived/archived_at/archive_reason` и `updated_at`. **`done` и `done_date` сохраняются** —
  восстановленный «исполненный» контроль остаётся исполненным и в списке имеет статус `done` **[К]**;
- «Удалить навсегда» → `_delete_forever` (4431): `delete_all_attachments(ctl.id, settings)` (локально и в shared)
  + удаление из списка + `_persist`. Подтверждение — диалог, без ввода слова;
- «воскрешение»: `merge_controls` (1170–1199) — union по id, побеждает больший `updated_at`;
  удалённый навсегда контроль, живой в shared, **возвращается** (оговорка в docstring 1191–1195;
  подтверждено `docs/network_audit_report.md` §4.1). Tombstones нет;
- права: `_restore`/`_delete_forever`/`_do_complete` блокируются только по `edition_user`
  (4354, 4423–4424, 4363–4364) — см. R12.

**Пограничный пример [П].** Админ исполнил контроль (done+архив `done`), затем «Восстановить» →
контроль возвращается в активные со `done=True`, `done_date` прежней, `archive_reason=""`.
Статус — «Исполнено». Очистить исполнение в legacy можно только повторным редактированием карточки
(чекбокса «снять исполнение» в карточке нет — `_save_detail` не пишет `done/done_date` из формы **[К]**:
поля `done`/`done_date` в `_save_detail` не присваиваются, значит значение сохраняется от `ctl`).

**Целевое поведение [П].** Три отдельные операции: `complete` (done + дата, без обязательной архивации —
или с ней, по решению владельца **[Р]**), `archive(reason)`, `restore`, `purge` (окончательное удаление
с файлами, только админ, только после архива, с записью в журнал). Восстановление возвращает
`archived=false` и **очищает причину**, но не трогает `done/done_date` (как в legacy); снятие исполнения —
отдельная явная операция с аудитом. Удаление не «воскресает»: вместо union-merge — серверная БД
и журнал событий (см. `decisions.md`).

**Намеренное отличие [П].** (1) нет воскрешения удалённого; (2) окончательное удаление требует архива и
двойного подтверждения + запись в аудит; (3) «исполнить» и «архивировать» — различимые операции в журнале.

**Этап.** W03 (операции), W04 (UI), W07 (миграция архива).

**Приёмка.** Исполнить → в архиве с причиной `done` и датой; восстановить → активен, `done` сохранён,
причина пуста; архивировать как `deleted` → восстановить → причина пуста; окончательное удаление недоступно
для записи вне архива; удалённая запись не появляется ни у одного клиента; все действия видны в журнале
с актором и временем; user получает 403 на каждую из операций прямым запросом.

### R10 — Поиск, фильтры, сортировка, диапазон дат, счётчики, сброс

**Факт [К][З].** Состав панели фильтров (`controls_tab.py:1636-1660, 1900-1950`):
поиск (`hint="Поиск по содержанию, номеру…"`), выпадающие «Все статусы / Все типы / Все инициаторы /

Логика `_filtered` (966–1046):

  в user-режиме (953–961);
- диапазон дат сравнивается с `_due_of`; записи **без срока не отсекаются** (проверка выполняется только
  при `dd is not None`, 1017–1028) — то есть «С/По» не скрывает бессрочные;
- инициаторы сравниваются каноническими группами (`initiator_filter_group`/`canonical_initiator_group`),
  переименованный кластер матчится по канону исходного;
- «Прочие» (`FILTER_OTHER`) — ни один исполнитель/контролёр не совпал ни с одним человеком **полного**
  справочника (992–1010);
- поиск — подстрока (lower) по `incoming_number, content, initiator, controller, due_date, executors, titles пунктов`
  (1030–1033); `comment`, `milestones`, `end_date`, `receive_date` в поиск **не входят** **[К]**;
- сортировка: ключ по умолчанию `due` (`state["sort_key"] = "due"`, 548), клик по заголовку меняет
  ключ/направление (`_sort_by`, 1214); для `num` используется позиция в `_visible_base()` (1036–1040);
- исполненные принудительно опускаются вниз в активном режиме (стабильное разбиение, 1043–1046).

**Пагинации нет [К].** `_rebuild_table` (1457) строит по виджету на каждую видимую строку; при 10 000 записей
это 10 000 строк дерева. Постраничность — новая функция.

**Счётчики [К][З].** `_counts` (1483) считается по `_visible_base()` — то есть учитывает роль и режим
(активные/архив), но **не учитывает** поиск и выпадающие фильтры: при выбранном фильтре «Инициатор = ГУК»
плитки показывают числа по всем видимым записям.

**Позиция и фильтры не сохраняются [К].** В настройках живут только `col_widths`, `card_width/height`,
`refs_width/height`; `state["search"]/f_*/sort_*` — только в памяти вкладки.

**Целевое поведение [П].** Серверная пагинация (по 50), серверные фильтры/сортировка со стабильным
tie-breaker (`due_date NULLS LAST, id`), счётчики считаются **по тому же запросу**, что и список
(включая фильтры) — это уточнение плана, а не legacy-поведение; фильтры, сортировка и страница
сохраняются в URL/профиле пользователя; диапазон дат включает записи без срока только при явном выборе
«Без срока» **[Р]**.

**Намеренное отличие [П].** (1) пагинация; (2) счётчики учитывают фильтры; (3) сохранение позиции/фильтров;
(4) поиск дополняется `comment`/`receive_date` (или остаётся как в legacy — решение владельца).

**Этап.** W03 (серверная выборка), W04 (UI), W01 (объём/скорость на 10 000 записей).

**Приёмка.** 10 000 синтетических записей: страница 50 строк ≤ 1 с (p95) на целевом Win7; счётчики равны
числу строк полного запроса с теми же фильтрами; фильтр «Прочие» и канонические инициаторы дают те же
наборы, что legacy на том же датасете; возврат из карточки сохраняет страницу, поиск и прокрутку.

ролевые (`get_executor_names`/`get_controller_names`, 507–520), **фильтры — полный справочник без ролей**

Операции справочника: `add_extra_person` (652, снимает скрытие), `remove_extra_person` (687),
`rename_person` (523: базовое ФИО → добавить новое в `extra_people` и скрыть старое в `hidden_people`;
роли переезжают), `remove_person` (566), `set_person_roles` (489). Инициаторы: `DEFAULT_INITIATORS` (19–24,
7 значений) + `custom_initiators`, каноническая кластеризация `canonical_initiator_group` (717–766:
«ГУК С.» → «гук», склейки разбиваются через запятую), `rename_initiator` (593, `init_renames`),
`remove_initiator` (624, `hidden_init_groups`), `initiator_filter_options/group` (768–813).
UI справочников — `_open_references` (4613–5025): две секции («Исполнители / контролёры» с чипами «И»/«К»
и «Инициаторы»), инлайн-добавление/переименование/удаление; доступно только не-user-редакции (4615–4617).

**Ключевой факт для миграции [К].** Справочник людей **не синхронизируется** по сети: в общей папке лежат
только `controls.json`, `controls_attachments/`, `.locks/`, `backups/` (`_parse_shared_path` 1201,
`_shared_dir` 1134, `control_locks.py:36-43`, `backup.py:289-297`). `zonal_criminalists.json` и
`controls_settings.json` — локальные файлы каждого ПК. Значит на разных машинах справочник может различаться,
а контроли ссылаются на людей **строками ФИО**, а не id.

**Пограничный пример [З].** Переименование человека: `rename_person("Иванов И.И.", "Иванов Иван Иванович")`
для базового ФИО добавляет новое в `extra_people`, старое — в `hidden_people`, роли переезжают;
старые контроли продолжают хранить строку «Иванов И.И.» и матчатся через `name_matches` — назначения не ломаются.

**Целевое поведение [П].** Сущность `person` (`id` UUID, `full_name`, `short_name`, `is_active`, роли) —
единая серверная, назначается один администратор. Назначения в контролях — только через `person_id`.
Переименование/деактивация человека меняют справочник, но не переписывают историю назначений;
исторические строки ФИО сохраняются в `legacy_raw` для сверки. Однофамильцы — разные `person`,
различаются по полному ФИО и (при наличии) по должности/отделу **[Р: кто ведёт справочник]**.

**Намеренное отличие [П].** (1) `person_id` вместо строки; (2) отказ от дедупликации по фамилии —
две записи с одной фамилией сосуществуют; (3) справочник людей отделён от зональной вкладки
(она остаётся в legacy) — двусторонней синхронизации нет.

**Этап.** W02 (схема/справочники), W03 (операции), W04 (UI), W07 (миграция ФИО → person_id).

**Приёмка.** Переименовать человека → старые контроли показывают новое имя, назначения не потеряны;
деактивировать → в фильтрах и новых назначениях не предлагается, в старых записях остаётся;
два однофамильца → каждый видит только свои пункты; прямой запрос справочника без авторизации → 401/403.

### R12 — User читает только назначенные ему контроли; admin управляет

**Факт [К][З].** Ограничение доступа в legacy реализуется **на клиенте** и зависит от **редакции сборки**,
а не от учётной записи:
- `edition_user = is_user_edition()` (`controls_tab.py:478`) → read-only: `_save_detail` (3708),
  `_add_control` (5143), `_import` (4505), `_delete_all` (5069), `_delete_forever` (4432),
  `_open_references` (4615), `_pick_attach` (3697), `_open_done_dialog` (4363), `_open_task_done_dlg` (3884)

  в карточке поля и кнопки вычищаются обходом дерева (`_iter_tree_parents`, 57–87; применение ~4282–4290);
- **роль из настроек (`network_role`) записи не ограничивает [З].** Зонд тулбара: при `network_role="user"`
  в admin-редакции кнопки «Добавить контроль», «Импорт Excel», «Справочники» присутствуют и видны
  (скрыта только «Удалить все», `visible=(network_role == "admin")`, 5155). `_persist` (708) пишет в shared
  для всех, кроме `edition_user` (709–716);
- **user без ФИО видит всё [З].** `_visible_base` (937) фильтрует по `_mine` только при

  до выбора ФИО — зонд показал 0 строк) **[З]**;
- **«свои» определяются без контролёра [К][З].** `_mine` (914–936) проверяет `executors` и `assignees` пунктов

  и исполнитель ВХ-2 → видит только ВХ-2. При этом `control_belongs_to` (`controls_notify.py:30-42`)
  контролёра учитывает → расхождение между списком и алармами (см. R20, дефект D-03);
  `docs/network_audit_report.md` §3 утверждает, что user-фильтры учитывают контролёра — **код этого не делает**;
- **локальный кэш user-редакции содержит ВСЕ контроли [К].** `_load_initial` (800–820) и `_apply_shared_update`
  (5377–5410) в user-режиме пишут авторитетный shared-снимок в локальный `controls.json`
  (`save_controls(view)`) «для офлайн-чтения». Любой локальный пользователь может открыть
  `%APPDATA%\porayonka\controls.json` и прочитать чужие контроли;
- **web-режим Win7 раздаёт скачанные копии без авторизации [К].** `_download_attach` (3324–3387) в web-режиме
  копирует файл в `FLET_ASSETS_DIR/downloads` и открывает URL `/assets/downloads/<имя>`; сервер слушает
  `0.0.0.0`: Win7-лаунчер принудительно добавляет `--host 0.0.0.0 --port 8555` (`main_web.py:71-77`),
  а `main.py --web` по умолчанию слушает `127.0.0.1:8555` и принимает `--host` из аргументов (`main.py:554-558`).
  Имя файла — исходное (с суффиксом `_1` при коллизии),
  то есть угадываемое;
- пароль админа (`ui/admin_gate.py`) **отключён** в раунде 34 (`main.py:52-72`), а его хеш —
  `base64(sha256(соль|пароль))` с жёстко зашитой солью (`core/edition.py:538-552`) и поддержкой
  plaintext-поля `password` (562–571). Как механизм авторизации не годится.

**Пограничный пример [З].** Два контроля: ВХ-1 (контролёр — пользователь, исполнитель — другой),
ВХ-2 (исполнитель — пользователь). User-редакция с ФИО пользователя: в списке только ВХ-2,
но аларм по сроку может прийти и по ВХ-1.

**Целевое поведение [П].** Единая серверная учётная запись → `person_id` → роль `admin|user`.
Политика доступа применяется в запросах к БД (фильтр выборки) и к каждому объекту:
список, карточка, счётчики, поиск, файлы, экспорт, события обновления, справочники.
User видит контроли, где он исполнитель контроля, ответственный пункта **или контролёр**
(расширение относительно legacy-`_mine` — требуется подтверждение владельца **[Р]**, так как меняет объём видимых данных).
Локальных кэшей с чужими данными нет; скачивание — только через авторизованный endpoint.

**Намеренное отличие [П].** (1) серверная авторизация вместо редакции exe; (2) роль не выбирается клиентом;
(3) `controller` включён в «свои» (или явно не включён — решение владельца); (4) никаких чужих данных
на клиентском диске и в статике.

**Этап.** W02 (политика доступа), W03 (применение в выборках), W04 (файлы), W05 (экспорт/скрытые листы),
W08 (аудит IDOR).

**Приёмка.** Прямые запросы от user A к карточке/файлу/экспорту/счетчику user B → 403/404 без утечки
существования; анонимный запрос → 401; отключённый аккаунт → 401 и завершение сессий;
user с пустой идентичностью не существует как состояние системы; скачивание файла по URL без cookie-сессии → 403.

### R13 — PDF/изображения и обязательный скан нового ручного контроля

**Факт [К].** Скан-гард — в `_save_detail` (3724–3748), только для `is_new`:
перебираются `detail_state["attachments"]`, принимается файл с расширением `.pdf/.png/.jpg/.jpeg`,
который **физически существует** (`resolve_attachment` → shared, затем локально; fallback `attachment_abs`).
При провале — красная подсказка «Прикрепите скан задания (PDF или изображение)» (`_set_scan_hint`, 4114)
и тост с той же формулировкой; сохранение прерывается, карточка остаётся открытой.
Разрешённые расширения и порог предупреждения — `ATTACHMENT_ALLOWED_EXT`/`ATTACHMENT_WARN_MB = 20`
(`controls_data.py:46-47`); `allowed_extensions=["pdf","png","jpg","jpeg"]` в вызове пикера (3699).

**Исключения гарда [К]:** (1) существующие (исторические) контроли — редактируются без скана;
(2) импорт Excel — скан не требуется (`import_plan`/`_preview_import` гард не вызывают; в предпросмотре
лишь показывается счётчик «Без скана: N», 4558–4563); (3) user-редакция — ничего не создаёт;
(4) в таблице активные записи без вложений помечаются пилюлей «Без скана» только у админа
(`_no_scan38`, 1305–1332: `not attachments and not archived and not done and not edition_user`).

**Гард клиентский [К].** Проверка выполняется в обработчике кнопки; отдельного серверного контроля нет
(сервера нет). Файл считается готовым, если он уже опубликован в shared/локально — прерванная загрузка
не считается (см. R14, `_copy_batch` reason `"error"`).

**Пограничный пример [П].** Новая карточка, приложен `scan.docx` → гард не проходит (расширение не из списка);
приложен `scan.pdf`, но публикация в shared упала с reason `"error"` → файл не прикреплён,
гард не проходит, вложение не появляется в модели.

**Целевое поведение [П].** Скан-гард — **серверный**: операция создания контроля отклоняется (422),
если к запросу не привязан опубликованный файл допустимого типа. Проверка типа — по содержимому
(magic bytes/MIME), а не только по расширению; размер ограничен; прерванная/незавершённая загрузка
сканом не считается. Исключения (исторические записи, импорт Excel) сохраняются и явно документируются.

**Намеренное отличие [П].** Серверная проверка содержимого файла вместо проверки имени на клиенте.

**Этап.** W03 (гард), W04 (загрузка файлов), W05 (освобождение импорта).

**Приёмка.** Создание контроля без опубликованного файла → 422 и понятная ошибка; с `scan.pdf` → 201;
с файлом `.pdf`, внутри которого HTML → отклонён; повторный POST с тем же ключом идемпотентности
не создаёт второй контроль и не требует второй файл; редактирование исторической записи без скана разрешено;
импорт Excel без сканов проходит, но помечает записи «Без скана».

### R14 — Вложения: добавить, увидеть сразу, скачать/открыть, удалить

**Факт [К][Т].** Относительный путь вложения — `<control_id>/<имя файла>` (`copy_attachment_to_local` 963,
`copy_attachment_to_shared_ex` 986). Хранение: локально `%APPDATA%\porayonka\controls_attachments\<id>\`,
в сети `<shared>\controls_attachments\<id>\`. Чтение — `resolve_attachment` (1066): **сначала shared, потом локально**.
- атомарность: `_copy_atomic` (923) — tmp + `os.replace` с ретраями при Windows-sharing ошибках
  (`_win_sharing_error` 863: PermissionError/WinError 5/32/33), `_try_unlink` (881), `_sweep_stale_tmp` (908, 10 мин);
- причины отказа: `copy_attachment_to_shared_ex` возвращает `"ok" | "offline" | "error"`;
  локальный фолбэк — **только** при `"offline"` (`_copy_batch`, 3508–3556); при `"error"` вложение
  не прикрепляется вовсе;
- крупные файлы (> 5 МБ, `_ATTACH_ASYNC_MB` 309) копируются в фоновом потоке, > 20 МБ — предупреждение;
  завершение — `wait_attach_jobs`/`attach_jobs_pending` (324–360) **[Т: stress 5c]**;
- «видно сразу»: `_apply_attach_result` (3559) перестраивает панель и сохраняет модель;
  обработчик пикера переподписывается с `unsubscribe` (`_ensure_file_picker`, 248–282) — регресс «13 копий» закрыт;
- **антидубль по ИМЕНИ файла**: `_filter_new_attach_files` (371–390) отбрасывает файлы, чьё имя уже есть
  среди вложений, и дубли внутри одного события; `_attach_event_is_duplicate` (285) гасит повторные
  result-события в окне 3 с. Следствие: **другой файл с тем же именем добавить нельзя** — будет тост
  «Файл уже прикреплён». Суффикс `_1/_2` (`_unique_filename`, 1043) срабатывает только при коллизии
  на диске (например, при переносе папок дублей в `_move_attachment_files`, `controls_dedup.py:283-347`);
- открытие: `_open_attach` (3458) → `os.startfile`/`open`/`xdg-open`; при отказе — диалог с путём и
  «Открыть папку» (3240–3285). Скачивание: `_download_attach` (3324) → desktop `FilePicker.save_file`
  → `_on_dl_saved` (3409) байт-в-байт tmp+replace → кнопка становится «Открыть»; web-режим →
  копия в `/assets/downloads/` (см. R12);
- удаление: `_confirm_remove_attach` → `delete_attachment` (1083, локально + shared);
  «Удалить навсегда» → `delete_all_attachments` (1106, `rmtree` обеих папок);
- отмена **новой** несохранённой карточки удаляет скопированные за сессию файлы (`_hide_detail`, 2464–2477);
- предпросмотр изображений: `_open_preview`/`_thumb_for` (~3080–3200) **[К, детально не исследовано — Н]**;
- догрузка из shared локально: `sync_attachments_from_shared` (1315); выгрузка локальных в shared:
  `sync_local_attachments_to_shared` (1391, только не-user-редакция, `_poll_locks_and_attachments` 5295).

**Пограничные примеры.**
1. **[З/Т]** Один и тот же файл выбран дважды подряд в течение 3 с → второе событие гасится, копия одна.
2. **[К]** Два **разных** файла с именем `scan.pdf` → второй отброшен по имени, пользователь видит
   «Файл уже прикреплён»; в карточке остаётся первый.
3. **[К]** Обрыв сети на середине копии 30 МБ → tmp удалён, под финальным именем битого файла нет,
   вложение не прикреплено.

**Целевое поведение [П].** Файлы — вне публичной статики; чтение/скачивание только через авторизованный
endpoint с проверкой права на контроль. Загрузка: временный объект → проверка типа/размера → публикация →
привязка к записи (компенсация при сбое, сборка сирот). Имя хранения генерирует сервер; исходное имя
(включая кириллицу) хранится в метаданных и возвращается в `Content-Disposition`.
**Разные файлы с одинаковым исходным именем — два разных вложения** (идентичность по `attachment_id`,
а не по имени); побайтово одинаковые дубликаты при миграции схлопываются по SHA256 с сохранением обеих ссылок.
«Открыть» = просмотр серверной копии или скачивание; приложение не утверждает, что знает локальную папку.

**Намеренное отличие [П].** (1) одноимённые разные файлы разрешены; (2) нет локальных копий и
«открытия скачанного файла» как состояния; (3) доступ к файлу проверяется сервером.

**Этап.** W04 (загрузка/скачивание), W07 (миграция файлов и сверка SHA256), W08 (аудит).

**Приёмка.** Байт-в-байт и SHA256 совпадают с источником; кириллическое имя скачивается корректно;
два разных файла с одним именем сосуществуют; обрыв загрузки → нет частичного файла и нет записи;
повтор запроса не создаёт копию; чужой `attachment_id` по прямой ссылке → 403; смена карточки во время
загрузки не теряет файл; удаление записи удаляет/помечает файлы по принятому правилу.

### R15 — Excel «как в таблице» и полный round-trip

**Факт [К][Т].** `ControlsExcelExporter.export(controls, filepath, soon_days, full, user_name)`
(`controls_exporter.py:127-260`). Структура листа «Контроли»: строка 1 — объединённый заголовок
`TABLE_TITLE` (A1:J1, зелёный, Times New Roman 36), строка 2 — `TABLE_HEADERS` (10 колонок, 26–41),

(через `short_name`, через запятую), G за кем контроль (`short_name`), **H «Разовый / постоянный»**,

кратные 7 → «каждые N нед.»; иначе «каждые N дней»).
**I** = `due_iso`: в admin-виде `ctl.due_date or effective_due_date`, в персонализированном —

Подсветка: жёлтая в I **только** при `overdue`/`today` (238–240), зелёная в J при `done` (242–243);
высота строки считается по длине содержания/исполнителей (245–251).

**Полный режим** добавляет скрытый лист `_controls_full` (`FULL_SHEET` 53, `_write_full_sheet` 262–298)

**Потери полного режима [К]:** в скрытый лист **не попадают** `created_at`, `updated_at`, `archived_at`;
`archived/archive_reason` записываются, но строк архивных контролей в листе нет (экспорт только `active`),
то есть `archived="1"` фактически не встречается. Round-trip «полного» файла поэтому восстанавливает запись
без исходных timestamps (`_from_full_row`, 930–964: `created_at/updated_at` получают значения по умолчанию
= «сейчас»).

**Пограничный пример [З].** `periodic`, `period_days=91`, `end_date=+40 дней` → H = `«26.10.2026 далее ежеквартально»`;
обратный разбор: `parse_excel_date(H)` = None → `parse_periodicity` находит «ежекварт» → (`periodic`, 91),
регулярное выражение `\d{1,2}\.\d{1,2}\.\d{4}` достаёт `end_date` → round-trip точен.
Для `period_days=45`: H = «каждые 45 дней» → parse → 45 (точно). Для `period_days=60`: «каждые 2 месяца» → 60 (точно).
**Неточность:** H = «постоянный» (ручная запись в таблице) → (`periodic`, **7**) — «постоянный» без уточнения
превращается в еженедельный (`parse_periodicity`, 326–356, правило 340).

**Целевое поведение [П].** Оба режима сохраняются 1:1 (заголовки, ширины, цвета, автофильтр, форматы дат,
подсветка только overdue/today). Скрытый лист расширяется `created_at/updated_at/archived_at`
и включается **только** для записей, доступных экспортирующему (см. R16). Round-trip полного режима
обязан восстанавливать все поля без потерь.

**Намеренное отличие [П].** (1) скрытый лист содержит timestamps; (2) экспорт формирует сервер,
а не клиент; (3) «постоянный» без периода не превращается молча в 7 дней — строка попадает в отчёт
«требует уточнения» **[Р]**.

**Этап.** W05.

**Приёмка.** Побайтовое сравнение структуры с эталоном (заголовок A1:J1, шапка во 2-й строке, ширины,
цвета, автофильтр, `DD.MM.YYYY`); round-trip полного режима: экспорт → импорт → все 22 поля совпадают,
кроме явно перечисленных; H/I соответствуют правилам выше на 20 синтетических комбинациях (once/periodic × с датами/без).

### R17 — Excel preview/upsert

**Факт [К][Т].** `import_plan(filepath, existing)` (`controls_exporter.py:611-717`) возвращает
`{"new", "updates", "unchanged", "conflicts", "errors", "full_format"}`.
Сопоставление: сначала по `id` из скрытого листа, затем по **нормализованному** вх. номеру
(`normalize_incoming_number` из `controls_dedup`). Случаи:
- id найден → целевая запись, `ctl.id = row_id` (round-trip);
- номер найден, кандидат один → upsert; кандидатов несколько → **конфликт** «несколько записей с таким номером»;
- номер уже обработан в этом файле → конфликт «номер повторяется внутри файла»
  (кроме случая, когда тот же id уже есть — тогда `unchanged`);
- расчёт изменений выполняется на **deepcopy** цели (`probe`), рабочая запись не мутируется до подтверждения.

`_apply_row_to_existing` (529–610) — правила слияния: скаляры обновляются только непустыми значениями;
`attachments` — union, **никогда не очищаются**; `tasks`/`milestones` заменяются только непустыми списками
(сравнение по `(title, due_date, is_done)` / `(date, note, is_done)`); `comment`, архив-метаданные и
`incoming_number` канонической записи не переписываются; `done` только ставится, не снимается;
`updated_at` обновляется при любом изменении.
`_row_to_control` (736–855): строки без вх. номера пропускаются (`_parse_import_rows`, 492);
содержание разбирается на пункты (`parse_content_tasks`), «голые» фамилии уточняются двумя проходами
(`resolve_task_assignees` по колонке «Исполнитель», затем по справочнику людей — **с чтением локальных
настроек**: `load_settings()`/`get_all_people_names()` внутри импорта, 790–795);
колонка H разбирается комбинированно (дата → `end_date` + `once`; иначе эвристика + дата из текста);
I → `due_date` (fallback `end_date`); J → `done`/`done_date`, неразбираемый текст уходит в
`comment = "исполнено (по импорту): <текст>"` (822–831).
`_overlay_visible_row` (856–928) накладывает видимые колонки поверх данных скрытого листа:
пустые ячейки ничего не меняют, изменённое содержание перечитывается вместе с пунктами.

**Предпросмотр в UI** — `_preview_import` (`controls_tab.py:4513-4612`): сводка
«Найдено / Новые / Обновляемые / Без изменений / Конфликты / Ошибок / Без скана / Формат»,
до 20 строк новых, до 20 обновляемых (с именами изменённых полей), до 10 конфликтов.
Перед применением — `backup_file_now(get_controls_file(), purpose="import")` (4570–4574);
новым записям id присваивается немедленно (4576–4585).

**Дефект распознавания шапки (D-04) [К][З].** В `_parse_import_rows` (458–482) словарь индексов создаётся как
`{i: None for i in range(len(TABLE_HEADERS))}` = ключи 0..9, ветки `elif` заполняют только ключи 1..9,
а проверка `has_full_headers = all(col_idx[i] is not None for i in range(10))` включает **ключ 0**,
который не заполняется никогда → условие всегда ложно → всегда срабатывает «упрощённый маппинг»
`col_idx = {i: i ...}`, то есть **колонки читаются по позиции, а не по заголовку**. Заявленная в комментариях
устойчивость к порядку/названию колонок фактически не работает. Практическое следствие: файл с переставленными
колонками или с дополнительной колонкой слева импортируется неверно (и, возможно, молча).
Тесты этого не ловят, потому что готовят файлы в эталонном порядке **[З: воспроизведено логикой, прогон
с реальным xlsx не выполнялся — openpyxl доступен, но отдельный кейс с переставленными колонками
в существующих тестах отсутствует]**.

**Целевое поведение [П].** Импорт: загрузка файла → серверный разбор → план (новые/обновляемые/без изменений/
конфликты/ошибки) с владельцем, сроком действия, SHA256 файла и версиями затрагиваемых записей →
подтверждение → транзакционное применение. Сопоставление колонок — **по заголовку** (с явным fallback
и сообщением, если шапка не распознана), а не по позиции. Устаревший план (изменились версии записей)
не применяется молча. Backup — проверяемый snapshot БД+файлов **до** применения; если backup не удался,
применение не начинается.

**Намеренное отличие [П].** (1) исправление D-04 (сопоставление по заголовку); (2) план привязан к версиям
записей и хэшу файла; (3) импорт не читает «локальные настройки пользователя» — справочник людей серверный.

**Этап.** W05, W07 (механизм snapshot/restore).

**Приёмка.** Категории плана совпадают с ожиданиями на синтетическом наборе (новые/обновляемые/без изменений/
конфликты/ошибки); повторное применение того же плана идемпотентно; id и вложения существующих записей
сохранены; richer-поля не стёрты пустыми ячейками; файл с переставленными колонками импортируется верно
или отклонён с понятной ошибкой; backup создан до применения, восстановление из него проверено.

`resolve_task_assignees` (307–333) подставляет полную форму **только при единственном** совпадении фамилии

**Намеренное отличие [П].** Автоподстановка полной формы ФИО становится **предложением** с подтверждением,

**Этап.** W03 (модуль разбора), W05 (использование в импорте).

**Приёмка.** Оба legacy-формата + 6 негативных кейсов (пункт без даты, отсутствие маркеров, «ОПК п. 1»,

нераспознанный текст не удаляется.

### R19 — Дубликаты по нормализованному входящему номеру

**Факт [К][З][Т].** `normalize_incoming_number` (`controls_dedup.py:48-67`): NFKC + NBSP/U+202F → пробел

**пустой номер → None** (дедуп не применяется).

режим `move_files=False` — «сухой» (для чтения/user), `True` — физический перенос папок вложений
(`_move_attachment_files`, 283: коллизии получают `_1/_2`, побайтово одинаковые копии удаляются и снимаются
со ссылок). Порядок результата стабилен: canonical занимает позицию первого вхождения группы.
Идемпотентность подтверждена зондом **[З: F]** и тестом **[Т: round38 dedup38, 7 сценариев]**.

перед записью в shared (`_persist`, 743–752), «сухой» — в любом просмотре (`_dedupe_view`, 781–792).

Измерено **[З: F]** (дополнительный зонд нормализации, синтетические строки):
`"ВХСОП-123-456-27"`, `"вхсоп 123 - 456-27"`, `"ВХСОП\u00a0123/456/27"`, `"вхсоп__123_456_27"`,
`"ВХСОП 123\u2011456\u201127"` (неразрывное тире), `"  вхсоп-123-456-27  "` → **один** нормализованный ключ

коллизий и решения владельца (требование `02-requirements.md`). Автоматическое слияние в обычном сохранении
запрещено: диагностика (список групп, кандидаты, различия) + план слияния, утверждённый админом,
в отдельной транзакции, с сохранением истории «кто с кем слит и почему».

**Намеренное отличие [П].** Отказ от автоматического «лечения» при каждом сохранении/старте

**Этап.** W03 (диагностика), W05 (импорт), W07 (миграционное слияние по утверждённому плану).

**Приёмка.** Нормализация совпадает с legacy на наборе из ≥ 30 синтетических написаний;
пустые номера не объединяются; диагностика выдаёт те же группы, что `diagnose_duplicates` на том же датасете;
слияние выполняется только по подтверждённому плану, вложения и пункты не теряются, повтор слияния идемпотентен.

**Намеренное отличие [П].** (1) серверный журнал вместо локального на ПК; (2) один согласованный критерий
«свой контроль» для списка и уведомлений (устранение D-03); (3) честное объявление ограничений браузера;
(4) лента пропущенных уведомлений при возврате.

не уведомляет; `done`/архив исключены; интервалы 2 ч/24 ч соблюдаются по серверному времени;
отзыв доступа прекращает уведомления; журнал показывает пропущенное после возвращения;

**Пограничный пример [Т].** Сценарии round38: «копия раз в сутки», «новый день → новая копия»,
«retention», «частичный сбой не засчитывает день», «конкурентные вызовы», «без рекурсии в backups/»,
«вложения в копии», «offline не ломает локальную копию», «user не пишет shared-копию»,

retention ~30 успешных суточных копий, копия на отдельный носитель, уведомление о сбое,

**Этап.** W05 (snapshot перед импортом), W07 (backup/restore/эксплуатация), W08 (репетиция восстановления),

### R22 — Обновление при открытии и во время работы

**Факт [К][Т].** Фоновый цикл `_background_loop` (5245–5294): `sleep(20)` → сетевой I/O
(`_poll_network_io`) → `sleep(40)` → уведомления/алармы/lock-и/вложения через UI-поток;
итоговый период опроса сети ≈ 60 с, резервные копии перепроверяются ≈ раз в 30 минут.
`_poll_network_io` (5482–5511): `get_shared_mtime`; если mtime не изменился и сеть в порядке — выход
(файл не перечитывается); иначе чтение и передача в UI-поток.
`_poll_network_apply` (5512–5552): mtime `None` → индикатор «Сеть: нет связи»; возврат из офлайна →
`_on_network_back` (5412: merge, локальные правки дороже; в user-режиме — замена авторитетным снимком);
пустой shared → mtime принимается, данные не затираются; **открыта карточка** → изменения копятся в
`pending_shared` и показывается диалог «Данные на сервере изменились» (один раз на открытие,
`_show_shared_conflict_dialog`, 5341–5376) с выбором «Обновить» (карточка **закрывается без сохранения**)
или «Позже»; карточка закрыта → `_apply_shared_update` (5377) с тостом.
При закрытии карточки накопленное применяется `_apply_pending_on_close` (2401–2436, merge + `_persist`).
Индикатор связи: «Локально» / «Сеть: админ|пользователь · HH:MM:SS» / «Сеть: нет связи» (`_update_sync_ui`, 884–913).
Дополнительно — lock-файлы редактирования (`core/control_locks.py`): `<shared>\.locks\<id>.lock`
с `{"user","machine","since"}`, stale 10 мин, «подогрев» раз в минуту (`refresh_locks`, `_poll_locks_and_attachments`
5295–5327), чужой активный lock → диалог «редактируется …» (`_show_lock_dialog`, 2503–2602).
Предупреждение о расхождении часов — `check_time_skew` (`controls_data.py:1341`) против порога
`TIME_SKEW_WARN_SEC = 1800` (1338) с диалогом (5842–5887).

**Пограничный пример [К].** Админ A открыл карточку и печатает длинный комментарий; админ B сохранил
изменение того же контроля. Через ≤ 60 с A видит диалог «Данные на сервере изменились»; «Обновить» →
карточка закрывается, **введённый комментарий теряется**; «Позже» → A сохраняет свою версию,
и побеждает тот, чей `updated_at` новее (LWW, `merge_controls`).

**Целевое поведение [П].** Лёгкий авторизованный опрос версии/курсора изменений раз в 15–30 с
(интервал фиксируется в W01): новые/изменённые/архивные/удалённые записи отражаются без F5;
опрос не скачивает всю базу и не пересоздаёт страницу; поиск, прокрутка и **редактируемая форма сохраняются**;
при изменении открытой карточки — индикатор новой версии и предложение сравнить, а не автоперезапись;
при конфликте версий — 409 и сохранённый ввод; возврат фокуса вкладке вызывает проверку свежести;
ошибка → backoff, видимый статус связи и время последнего успешного обмена. Lock-файлы не нужны:
конфликт решается через `revision`.

**Намеренное отличие [П].** (1) `revision`/409 вместо LWW по часам клиента; (2) несохранённый ввод
не теряется при обновлении; (3) нет lock-файлов в общей папке; (4) событийная модель вместо чтения
целого файла по mtime.

**Этап.** W06 (обновления), W04 (поведение формы при конфликте), W02 (revision/409).

**Приёмка.** Два клиента: изменение на втором видно не позднее интервала опроса + 5 с; открытая форма
не затирается; при одновременном сохранении один получает 409, его текст сохранён в форме и может быть
применён заново; отзыв доступа очищает карточку; разрыв соединения → статус «нет связи» + backoff,
после восстановления данные догоняются без дублей; скрытая вкладка обновляется сразу после возврата фокуса.

размер панелей, звук) — хранятся на сервере в профиле пользователя; (3) служебные журналы — серверные.
`network_*`, UNC-путь, `edition` и парольные артефакты в новую систему **не переносятся**
(требование `02-requirements.md` R24 и `01-architecture.md`).

**Намеренное отличие [П].** (1) нет клиентских настроек сети и роли; (2) чтение настроек не пишет их;
(3) «скрытые» ключи (`alarm_enabled`, `hidden_*`, `*_log`) становятся явными сущностями.

**Этап.** W02 (схема настроек/профиля), W03 (серверные), W04 (персональные), W07 (миграция справочников).

**Приёмка.** Изменение `soon_days` админом меняет статусы у всех пользователей; персональные настройки
не влияют на других; ни один endpoint не принимает `network_role`/`network_user` от клиента;
миграция справочников переносит `extra_people`/`hidden_people`/`person_roles`/`init_renames`/
`hidden_init_groups`/`custom_initiators` без потерь (сверка по количеству и составу).
