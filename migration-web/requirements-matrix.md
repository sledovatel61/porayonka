## 1. Матрица

### R01. Создание, просмотр, редактирование контроля; обязательные поля; русский ввод дат

- **Фактическое поведение.** Карточка — overlay поверх таблицы, открывается кликом по строке
  (`controls_tab.py:2603 _open_detail`) или кнопкой «Добавить контроль» (`:5142 _add_control`,
  только admin-редакция). Единственное жёсткое поле при сохранении — «вх. №»: пусто →
  `incoming_field.error_text = "Введите номер"` и выход без записи (`:3707 _save_detail`, строки
  3709–3716). «Дата поступления» при пустом значении **подставляется автоматически** = сегодня, с
  тостом-предупреждением (`:3750–3761`) — раньше был тихий отказ. Тип контроля, периодичность,
  срок, дата исполнения — без проверки связности (`:3809–3825`).
  Даты **нельзя ввести текстом**: единственный способ — собственный русский календарь
  (`ui/controls/russian_calendar.py:86 create_russian_date_field`, `:328 create_russian_calendar_expanded`,
  месяцы `MONTHS_RU`, неделя с Пн). Отображение — `дд.мм.гггг` (`controls_tab.py:229 _display_date`),
  хранение — ISO `ГГГГ-ММ-ДД` строкой (`controls_models.py:362 Control`, комментарий шапки файла).
  Валидации формата нет: любое не-ISO значение молча читается как «даты нет»
  (`controls_models.py:28 parse_date` → `None`) `[выполнено: due_date="29.02.2027"` → `None]`.
- **Источник.** `porayonka-app/ui/controls/controls_tab.py:2603, 3707, 5142`;
  `porayonka-app/core/controls_models.py:28, 362`; `porayonka-app/ui/controls/russian_calendar.py`.
- **Пограничный пример.** Синтетика: контроль «ВХ-П-1», `receive_date=null`, `due_date="31.02.2026"`.
  Legacy: дата поступления становится сегодня, `due_date` сохраняется в JSON как битая строка,
  статус считается как «без срока» (`NO_DATE`), в Excel колонка I пустая.
- **Целевое поведение.** Обязательные поля проверяются сервером (номер, дата поступления, тип);
  битая дата — ошибка 422 с русским текстом, запись не меняется. В UI дата вводится и клавиатурой
  (`дд.мм.гггг`), и календарём; нормализация в ISO на сервере.
- **Намеренное отличие.** Автоставление «сегодня» вместо отказа — сохраняем как поведение, но
  показываем поле подсвеченным как изменённое `[предложение]`.
- **Этап.** W03 (правила/валидация), W04 (форма).
- **Проверка приёмки.** Тест API: `POST /api/controls` без `incoming_number` → 422 и 0 строк в БД;
  с `receive_date="31.02.2026"` → 422; с `due_date="29.02.2028"` → 201 (високосный). E2E: ввод
  «05.09.2026» с клавиатуры сохраняет `2026-09-05` и отображает `05.09.2026`.

### R02. Все поля Control без потерь

- **Фактическое поведение.** Модель — 21 поле (`controls_models.py:362–385`); сериализация
  `to_dict`/`from_dict` (`:387, :414`) сохраняет все 21, включая пустые строки и `null`-даты;
  неизвестные ключи в JSON **теряются** (`from_dict` читает только свой список).
  Единственный канал «richer»-переноса — скрытый лист `_controls_full`, и он **не включает**
  `created_at`, `updated_at`, `archived_at` (`controls_exporter.py:262 _write_full_sheet`, список
  заголовков `:269–273`, `sheet_state="hidden"` на `:268`) → при повторном импорте времена
  пересоздаются «на сейчас»
  `[выполнено: `_from_full_row` вернул created_at/updated_at = дата импорта, archived_at = None]`.
- **Источник.** `porayonka-app/core/controls_models.py:362–439`; `porayonka-app/core/controls_exporter.py:262–273, 718–734, 930–964`.
- **Пограничный пример.** Контроль с `comment=""`, `archived=true`, `archived_at="2026-08-10T09:00:00"`,
  `period_days=0`. Legacy-экспорт в «полном» режиме его вообще не пишет (см. R15: экспорт фильтрует
  `not c.archived`), то есть архивные записи из Excel не переносимы и `period_days=0` не
  отличается от отсутствующего значения.
- **Целевое поведение.** Полный mapping «поле → сущность» в `field-mapping.md`; пустое значение
  (`""`) и отсутствие значения (`null`) различаются там, где legacy их различает; неизвестные
  поля исходного JSON сохраняются в `legacy_raw` (JSONB) и выводятся в отчёт миграции, а не
  выбрасываются.
- **Намеренное отличие.** В новой системе поля `created_at/updated_at` серверные и не участвуют в
  «историческом» round-trip Excel; для сверки при миграции они переносятся отдельным каналом
  (импорт-план W07), а не через Excel.
- **Этап.** W02 (схема), W07 (миграция и сверка).
- **Проверка приёмки.** Скрипт сверки: для 100% записей сравнение `legacy JSON → БД → контрольный
  экспорт JSON` по всем 21 полям, включая пустые/нулевые; отчёт объясняет каждое расхождение.
  Отдельно: «неизвестное поле» (`{"foo": 1}` в исходном JSON) присутствует в `legacy_raw` после
  миграции.

  Исполнение пункта отмечается двумя путями: чекбокс в карточке (только после «Сохранить») и
  диалог «Исполнен пункт» с мультивыбором и общей датой, который пишет сразу в живую модель и
  вызывает пересчёт срока (`:3873–4005 _open_task_done_dlg` → `sync_due_after_tasks(ctl)` на `:3936`).
  Исполнители пунктов автоматически добавляются в `executors` контроля, но **не удаляются** оттуда
  при снятии галки (`:2728–2757 _sync_exec_from_tasks`).
- **Источник.** `porayonka-app/core/controls_models.py:119–156`;
  `porayonka-app/ui/controls/controls_tab.py:2847–2975, 3769–3820, 3873–4005`.
- **Пограничный пример.** Пункт «п. 9.3» с `due_date=null`, `is_done=true`, `done_date=2026-05-01`:
  в общий срок не попадает (у `effective_due_date` фильтр `parse_date(...) is not None`), статус

- **Целевое поведение.** `control_task` — отдельная сущность с явным `position` (int), `revision`
  на уровне контроля, операции добавления/изменения/исполнения/удаления — отдельные транзакции с

- **Намеренное отличие.** Уход от «полной замены списка» к точечным командам; порядок — поле, а не
  индекс массива. Требует подтверждения `[решение владельца]` (объём: не меняет смысл, меняет API).
- **Этап.** W02 (схема), W03 (операции), W04 (UI).
- **Проверка приёмки.** Тест: два админа открыли контроль; первый добавил пункт, второй удалил
  другой пункт → оба изменения присутствуют (или второй получает 409), потерянных пунктов нет.

### R04. Промежуточные сроки (milestones)

- **Фактическое поведение.** `ControlMilestone` — `id, date, note, is_done` (`controls_models.py:336–341`),
  **нет** `done_date`, автора, порядка. Даты неисполненных точек участвуют в общем сроке
  (`:441 effective_due_date` — `min(свои пункты, точки, due_date)`), но **не** участвуют в
  пользовательском сроке (`:532 user_effective_due_date` смотрит только `tasks`) `[выполнено:
  просроченная точка делает контроль «Просрочено» для админа и «В работе» с другой датой для
  исполнителя пункта]`. `sync_due_after_tasks` их игнорирует (`:465`).
  Секция «Промежуточные точки» в используемой карточке доступна и для разовых (`controls_tab.py:2997
  milestones_col.visible = True`, раунд 5), в неиспользуемой карточке — только для периодических
  (`ui/controls/control_card_modal.py:485, 735`).
- **Источник.** как выше; отображение в списке — до 2 ближайших неисполненных точек под датой
  (`controls_tab.py:1358–1370`).
- **Пограничный пример.** Точка `date=null, note="жду материалы"`: при сохранении остаётся (`:3039–3043`
  добавление, `:3780–3786` — строка не выбрасывается, если есть `note`), но на срок не влияет.
  Просроченная точка и `due_date` в будущем → админ видит «Просрочено», игрок — «В работе».
- **Целевое поведение.** `control_milestone` сущностью, поля `due_date, note, is_done, done_date,
  position, author`; единое правило: либо точки участвуют в персональном сроке так же, как пункты,
  либо явно не участвуют — **выбрать одно** `[решение владельца]`. Базовое предложение: участвуют,
  только если точка назначена на пользователя (появляется поле `assignees`), иначе влияют лишь на
  общий срок.
- **Намеренное отличие.** Различие «общий/персональный» перестаёт быть случайным следом реализации.
- **Этап.** W03 (правила), W04 (UI), W07 (миграция: `done_date` отсутствует → `null`).
- **Проверка приёмки.** Табличный тест на фиксированное «сегодня»: точка вчера + пункт через 20
  дней → статус «Просрочено» (общий) и «В работе» (персональный) согласно выбранному правилу;
  после `done` точки срок контроля пересчитывается без ручного редактирования.

### R05. Разовый/периодический, `period_days`, `due_date`, `end_date`

- **Фактическое поведение.** Тип — строка `"once" | "periodic"` (`controls_models.py:11–12`).
  `period_days: int = 7` — **интервал в днях, не календарный месяц**: 30 дней («ежемесячно»),
  91 («ежеквартально»), 182 («каждое полугодие»), 365 («ежегодно») (`controls_tab.py:216–227
  _PERIOD_LABELS`; подпись `_period_label` в `controls_exporter.py:74`) `[выполнено:
  `_period_label(30)` → «ежемесячно», `(91)` → «ежеквартально»]`.
  **Автоматического переноса срока нет**: ни одна функция legacy не сдвигает `due_date` на
  `period_days` (поиск по `timedelta(days=` даёт только календарь и `sync_due_after_tasks`); после
  истечения срока периодический контроль висит «Просрочено», пока админ не поменяет дату вручную
  `[выполнено: periodic, due=today-40, end_date=None → статус overdue, due_date остался
  2026-08-07]`. `end_date` для периодического — «последняя дата»: `end_date < today` →
  `COMPLETED` («Завершён»), дальнейшие статусы не считаются (`controls_models.py:502–530`).
  Смена типа в используемой карточке **не очищает** `end_date` у разового (`controls_tab.py:3813
  c.end_date = detail_state["end_date"]`, сознательный раунд 22 — колонка H Excel хранит именно её);
  у неиспользуемой карточки — очищает (`control_card_modal.py:702`). Формулировка
  `02-requirements.md` «переключение в разовый очищает end_date» **не соответствует** активной
  карточке `[код]`.
- **Источник.** `porayonka-app/core/controls_models.py:11–12, 371–374, 465–530`;
  `porayonka-app/ui/controls/controls_tab.py:2758–2812, 3809–3825`; `porayonka-app/ui/controls/control_card_modal.py:684–702`.
- **Пограничный пример.** Периодический, `period_days=30`, `due_date=сегодня`, `end_date=сегодня`:
  сегодня статус «Сегодня», завтра — «Завершён» (несмотря на просроченный срок), в архив сам не
  уходит; `due_date` остаётся «вчерашним».
- **Целевое поведение.** Хранить `period_days` как интервал в днях (без «календарного месяца»).
  Правило перехода периода — отдельное, явно принятое: (А) полностью как legacy (срок двигает
  человек), (Б) серверный «закрыть период» — по нажатию, с записью в журнал и новой `due_date =
  закрытая дата + period_days`. **Никогда не придумывать автоперенос по умолчанию.** `[решение
  владельца]`
- **Намеренное отличие.** Вариант Б — новое поведение, требует явного решения; при варианте А
  отличие только в том, что «сегодня» берётся с сервера.
- **Этап.** W03.
- **Проверка приёмки.** Тесты с фиксированным «сегодня»: `period_days=30` от `2026-01-31` →
  следующая дата `2026-03-02` (30 дней, а не «конец февраля»); `end_date` вчера → `completed` и
  отсутствие в алармах; переключение `periodic → once` сохраняет `end_date` (как legacy) или
  чистит его — ровно так, как принято решением.

### R06. Статусы overdue/today/soon/in_progress/done/completed/none

- **Фактическое поведение.** Семь статусов + подписи/цвета (`controls_models.py:15–21, 592–610`).
  Считываются на лету от `date.today()` **той машины, где выполняется код** (`:502 deadline_status`,
  `:565 user_deadline_status`) — клиентские часы определяют «сегодня» `[код]`. Порог `soon_days`
  берётся из настроек (см. R24). «Без срока» (`NO_DATE`) есть в статусной модели и в сортировке,
  но **нет** в выпадающем фильтре статуса (`controls_tab.py:1643 status_filter_dd`) и **нет**
  счётчика (`:1577 counter_defs` — только Все/Просрочено/Сегодня/Скоро/В работе/Исполнено);
  «Завершён» тоже без счётчика `[код]`.
- **Источник.** `porayonka-app/core/controls_models.py:14–21, 502–590`; `porayonka-app/ui/controls/controls_tab.py:1483, 1577, 1643`.
- **Пограничный пример.** `soon_days=3`, срок завтра → `SOON`; срок ровно через 4 дня →
  `IN_PROGRESS`; `due_date` отсутствует, есть просроченный пункт → `OVERDUE` (срок =
  `effective_due_date`), то есть «Без срока» только когда нет ни своей даты, ни пунктов, ни точек.
- **Целевое поведение.** Тот же набор, но «сегодня» — серверная дата по часовому поясу
  организации (предложено Europe/Moscow), статус считается на сервере и приходит в списке, чтобы
  фильтры/счётчики/алармы/экспорт не разошлись.
- **Намеренное отличие.** Статус — поле ответа API, а не клиентский расчёт.
- **Этап.** W02 (контракт), W03 (расчёт), W04 (отображение).
- **Проверка приёмки.** Табличные тесты на фиксированную дату: границы `dd = today`, `today+1`,
  `today+soon_days`, `today+soon_days+1`, `end_date` вчера/сегодня/завтра, 29.02.2028, 31.12;
  сверка «фильтр = счётчик = строка = экспорт» на одном наборе из 5 записей.

### R07. Исполнение пункта пересчитывает ближайший общий срок

- **Фактическое поведение.** `sync_due_after_tasks` (`controls_models.py:465–500`) вызывается при
  сохранении карточки (`controls_tab.py:3824`) и в диалоге «Исполнен пункт» (`:3936`). Правила:
  `due_date` равная дате исполненного пункта и не встречающаяся среди неисполненных → сдвиг на
  `min(неисполненные)`; `due_date` пусто при наличии пунктов → `min(неисполненные)`; для разового
  `end_date` раньше `max(неисполненные)` → поднимается до `max`; **если все пункты исполнены —
  даты не трогаются** (ожидается закрытие контроля) `[выполнено: all-done → due_date не изменился,
  статус остался overdue по старой дате]`. Ручная дата, не совпадающая с датой исполненного пункта,
  сохраняется. Исполненный пункт никогда не участвует в расчёте (фильтр `not t.is_done`).
- **Источник.** `porayonka-app/core/controls_models.py:465–500`; вызовы:
  `porayonka-app/ui/controls/controls_tab.py:3824` (сохранение карточки),
  `:3936` (диалог «Исполнен пункт», `:3873–4005`), `:2812` (пересборка плашки срока).
- **Пограничный пример** `[выполнено]`. Пункты: п.1 `31.08` (исполнен), п.10 `28.08` (исполнен),
  п.2 `28.08` (**не** исполнен), `due_date=28.08`. Сдвига **нет**: условие требует
  «`due_date` ∈ дат исполненных **и** ∉ дат неисполненных», а `28.08` ещё «жив» в п.2 → контроль
  остаётся просроченным по 28.08. Тот же набор, но п.2 перенесён на `31.08`: `28.08 ∈ done`,
  `28.08 ∉ pending` → `due_date` сдвигается на `min(pending)=31.08`. Раздельно проверено: все
  пункты исполнены → `due_date`/`end_date` не меняются; `end_date` разового раньше
  `max(pending)` → поднимается до `max(pending)`; ручная `end_date` позже пунктов сохраняется.

- **Проверка приёмки.** 6 табличных кейсов (пустой due, «протухший» due, разделённая дата, все

### R08. Индивидуальный срок и статус

- **Фактическое поведение.** `user_effective_due_date(control, user_name)`
  (`controls_models.py:532–563`): минимум по **неисполненным пунктам**, где пользователь указан в
  `assignees`; если своих пунктов нет — общий `effective_due_date` **только** если пользователь в
  `executors` контроля или он `controller`; иначе `None`. При `None`
  `user_deadline_status` (`:565–590`) возвращает `IN_PROGRESS` («В работе»), а не `NO_DATE` —
  специально, чтобы «чужие» просрочки не попадали в «Просрочено» `[выполнено: Сидоров с пунктом
  через 20 дней в просроченном контроле → его срок 2026-10-06, статус in_progress]`.
  Сопоставление — **фамильное/нечёткое**: `name_matches` (`:89–117`): точное совпадение, подстрока
  фамилии, либо расстояние Левенштейна ≥ 0.80 `[выполнено: name_matches("Иванов Иван Иванович",
  "Иванова А.А.") → True; name_matches("Орлов Иван Юрьевич", "Орловых П.П.") → True]`.
  Это приёмка
  видимости, но как **авторизация** оно неприменимо (см. `field-mapping.md`).
  В списке срок показывается персональный, а в tooltip добавляется общий
  (`controls_tab.py:1351–1357`); в user-редакции статус/фильтры/счётчики/алармы идут по
  персональной ветке (`:953 _status_of`, `:958 _due_of`, `:1483 _counts`).
- **Источник.** как выше + `controls_tab.py:914 _mine`, `:937 _visible_base`.
- **Пограничный пример.** См. сценарии S01–S04 в §3.
- **Целевое поведение.** Персональный срок считается на сервере от `person_id` пользователя, а не
  от строки ФИО; `assignees` пунктов хранят ссылки на людей. Статус «Без срока» vs «В работе» —
  сохранить legacy-различие или унифицировать: базовое предложение — сохранить («В работе»),
  зафиксировать решением `[решение владельца]`.
- **Намеренное отличие.** Нечёткое совпадение ФИО исчезает из контура доступа; остаётся только как
  подсказка при ручном сопоставлении справочника.
- **Этап.** W02 (идентичность), W03 (расчёт), W04 (отображение).
- **Проверка приёмки.** Матрица: {свои просроченные, свои будущие, только чужие просроченные,
  все свои исполнены, чужие + общий исполнитель, только контролёр} × {список, счётчики, алармы,
  экспорт} дают одинаковый ответ. Отдельный тест: два однофамильца не путаются.

### R09. Завершение контроля, архив done/deleted, восстановление, окончательное удаление

- **Фактическое поведение.** «Контроль исполнен» → диалог с датой (по умолчанию сегодня) →
  `_do_complete` (`controls_tab.py:4350–4358`): `done=True`, `done_date`, **сразу**
  `archive_control(ctl, ARCHIVE_DONE)` (`core/controls_data.py:831`) → `archived=True`,
  `archived_at=now`, `archive_reason="done"`, `updated_at=now`. То есть «исполнено» = «в архиве»,
  в активном списке запись не видна.
  «Удалить» в карточке активного контроля → подтверждение → `archive_control(..., ARCHIVE_DELETED)`
  (`:3847–3872`). В архиве колонка «Тип» становится «Причина» с подписью
  «Исполнен · дд.мм.гггг» / «Удалён · …» (`:239 _reason_label`, `:1330–1338`).
  «Восстановить` (`:4420 _restore` → `controls_data.py:839 restore_control`) снимает только
  `archived/archived_at/archive_reason`; `done/done_date` **не сбрасываются** `[код]` → возвращённый
  «исполненный» контроль активен, но со статусом «Исполнено», вне алармов (`controls_notify.py:47`
  фильтрует `done`) и без UI-способа снова сделать его неисполненным.
  «Удалить навсегда» (`:4431 _delete_forever`): `delete_all_attachments(ctl.id, settings)` —
  рекурсивное удаление папок локально и в shared (`controls_data.py:1106`), затем запись уходит из
  списка. Tombstone нет: `merge_controls` документированно «воскрешает» удалённое из shared
  (`controls_data.py:1170–1180`) `[код]`.
- **Источник.** строки выше; диалоги `_open_done_dialog` `:4360`, `_delete_detail` `:3847`,
  футер карточки архива `:4207, :4210`.
- **Пограничный пример.** Контроль «ВХ-П-9» исполнен 10.08.2026 → в архиве; восстановление →
  активен, `done=True`, `done_date=2026-08-10`, счётчик «Исполнено» +1, в алармах не участвует.
- **Целевое поведение.** Архив — состояние записи + причина + автор + время (журнал), восстановление
  = явная команда с выбором: «вернуть как есть» или «вернуть в работу» (снимает `done`). Окончательное
  удаление — только admin, с подтверждением по номеру, обязательно фиксируется в аудите; при
  серверной БД «воскрешение» невозможно, но нужно правило судьбы вложений (см. риск R-10).
- **Намеренное отличие.** Раздельные «исполнен» и «в архиве» становятся возможными (в legacy они
  склеены); требует подтверждения `[решение владельца]`.
- **Этап.** W03 (операции), W04 (UI), W08 (репетиция откатов).
- **Проверка приёмки.** E2E: «исполнить → архив → восстановить → вернуть в работу» с проверкой
  флагов на каждом шаге; «удалить навсегда» → записи нет, вложения недоступны, в аудите есть;
  повторное «удаление» уже удалённого → 404, а не 500.

### R10. Поиск, фильтры, сортировка, диапазон дат, счётчики, сброс

- **Фактическое поведение.** Один блок фильтров: поиск; статус; тип; инициатор; исполнитель;
  контролёр; «С:»/«По:»; «Сбросить фильтры»; переключатель «Активные/Архив»
  (`controls_tab.py:1636–1745`, `_reset_filters :1732`). `_filtered` (`:966–1046`):
  сравнение статуса — по персональному статусу в user-режиме; инициатор — по канонической группе
  (`controls_data.py:717`); исполнитель — `executors` **плюс** `assignees` пунктов; «Прочие» = ни
  одно имя не матчится с полным справочником; диапазон сравнивается с **эффективным сроком**
  (`_due_of`), а не с датой поступления; поиск — подстрока по `incoming_number, content, initiator,
  controller, due_date, executors, title` пунктов (регистронезависимо).
  Сортировка: клик по заголовку (`:1214 _sort_by`), ключи `num, incoming, receive, initiator, type,
  status, due` — **любые другие ключи падают в ветку «по сроку»** (`:1018–1042 _sort_val`), поэтому
  сортировка по «Содержанию», «Исполнителям», «За кем контроль» фактически сортирует по дате
  `[код — дефект]`. Ключ `num` сортирует по индексу в исходном списке (`base.index(ctl)`), а
  колонка «№» — просто порядковый номер строки (`:1265 _build_row`, `enumerate`), идентификатором
  записи не является. Исполненные всегда приклеены вниз (вне зависимости от направления) в
  активном режиме (`:1043–1046`).
  Счётчики (`:1483 _counts`) считаются по `_visible_base()` — то есть **без** учёта поиска,
  диапазона и остальных фильтров, только роль+режим (активные/архив). Пагинации нет: `_rebuild_table`
  (`:1457`) строит все строки сразу `[код]`.
- **Источник.** строки выше.
- **Пограничный пример.** Фильтр «Сегодня» + дата-диапазон «С: 01.01.2026 По: 31.01.2026» →
  счётчик «Сегодня» показывает число за весь январь независимо от диапазона; в списке — пересечение.
- **Целевое поведение.** Один серверный запрос источника данных: список, счётчики и экспорт считаются
  по одному фильтру и одним правам; пагинация порциями (предложено 50); сортировка — только по поддерживаемым
  столбцам — с детерминированным tie-breaker; диапазон — явно указанным полем (`due` или `receive`,
  `[предложение]` — по сроку, как legacy, с подписью в UI).
- **Намеренное отличие.** Счётчики перестают быть «глобальными»; «№» строки не является номером
  контроля — в UI предлагается показывать номер строки страницы, а идентификатором остаётся вх. №.
- **Этап.** W02 (контракт), W03 (запросы), W04 (UI).
- **Проверка приёмки.** Тест: счётчик == `count` того же SQL-фильтра; сортировка по каждому
  доступному столбцу устойчива при перезагрузке; страница 2 сохраняет фильтр/поиск; «№» не
  используется как ссылка.

### R12. User читает только назначенное; admin управляет; защита прямых запросов

- **Фактическое поведение.** Разграничение **не** авторизация. Роль и ФИО берутся из локальных

  **не** учитывает `controller`, но `_visible_base` применяет фильтр только при непустом
  `network_user`: роль `user` + пустое ФИО = весь список `[код]`. Парольный вход админ-редакции

- **Источник.** строки выше.
- **Пограничный пример.** Синтетика: user с пустым `network_user` видит чужие контроли и может

- **Целевое поведение.** Серверная сессия (cookie HttpOnly/Secure/SameSite + CSRF), роли `admin`/`user`,

- **Этап.** W01 (стенд с доступом), W02 (аккаунты/политика), далее все этапы.
- **Проверка приёмки.** Матрица доступа: {аноним, user A, user B, admin, отключённый} ×

  попадают в счётчики/экспорт; тест «прямой ссылкой» на файлах.

### R13. Скан-гард новых контролей; PDF/изображения

- **Фактическое поведение.** При сохранении **новой** карточки требуется хотя бы одно вложение с
  расширением `.pdf/.png/.jpg/.jpeg`, физически разрешимое (`resolve_attachment` или
  `attachment_abs`), иначе — подсказка в секции «Скан задания» + error-тост + отказ
  (`controls_tab.py:3720–3747`). Исторические записи и импорт Excel не проверяются (`is_new`); в
  предпросмотре импорта считается «Без скана: N» (`:4558–4563`). В строке активного неархивного
  неисполненного контроля без вложения показывается пилюля «Без скана» (`:1305`). Конкретный
  кортеж разрешённых расширений `ATTACHMENT_ALLOWED_EXT` (`core/controls_data.py:47`) **нигде не
  применяется** (grep: только объявление) `[код]`; проверка — только расширение в имени + фильтр
  диалога выбора. Размер не ограничивается, только предупреждение > 20 МБ
  (`ATTACHMENT_WARN_MB = 20`, `controls_tab.py:3652`).
- **Источник.** строки выше.
- **Пограничный пример.** Синтетика: файл `Скан.pdf.exe` (имя с двойным расширением) — проходит
  проверку? Нет: `fn38.endswith((".pdf",".png",".jpg",".jpeg"))` проверяет хвост имени, `.exe` не
  пройдёт; а `Отчёт.pdf` с MIME `application/x-sh` — пройдёт, содержимое не смотрят `[код]`.
- **Целевое поведение.** Серверная валидация при загрузке: белый список MIME + магические байты,
  лимит размера, переименование в серверный ключ, запрет inline-отдачи HTML/SVG; скан-гард — то же
  правило, что в legacy: только при создании контроля; для редактирования исторических записей —
  не блокировать.
- **Намеренное отличие.** Расширение → содержимое; лимит размера вместо предупреждения (число —
  `[решение владельца]`, `[предложение]` 25 МБ).
- **Этап.** W04 (файлы).
- **Проверка приёмки.** API: создать контроль без upload_id → 422; с upload_id чужого пользователя
  → 403; с подменённым MIME (`file --mime` ≠ расширение) → 415/422; редактировать исторический
  контроль без вложения → 200.

### R14. Вложения: добавить, сразу увидеть, скачать/открыть, удалить

  `имя_1.ext` (`:1043 _unique_filename`).

  _attach_event_is_duplicate`), файл с уже прикреплённым **именем** не копируется повторно

  `[код]`.
- **Источник.** строки выше; `docs/network_audit_report.md` §§ БАГ 3, 4.
- **Пограничный пример.** Два разных файла с именем `Скан.pdf` в одном контроле → второй сохраняется

  байт-идентичные копии удаляются (`core/controls_dedup.py:265 _same_bytes`).
- **Целевое поведение.** Загрузка — временный объект → проверка → публикация → привязка (одна
  операция, ключ идемпотентности); хранение — серверный ключ + исходное имя + размер + SHA256 +

  диске»; сборщик сирот с TTL; компенсация при сбое (неатомарность БД+ФС — осознанно).
- **Намеренное отличие.** Отказ от desktop-механики «файл скачан и лежит в такой-то папке»
  (зафиксировано в `01-architecture.md`, требует подтверждения `[решение владельца]`).
- **Этап.** W04.
- **Проверка приёмки.** Байт-в-байт + SHA256 после round-trip; кириллица в имени; два файла с
  одинаковым именем; обрыв загрузки (модель не ссылается на unpublished); повторный POST с тем же
  idempotency-key → 1 объект; сбой БД после публикации → сирота убран сборщиком; чужой upload_id

- **Этап.** W05.
- **Проверка приёмки.** Round-trip теста-набора (разовый с `end_date`, периодический 91 с
  `end_date`, периодический без `end_date`, исполненный, архивный): H/I совпадают, пустые поля не

### R16. User-экспорт и admin-экспорт с фильтром исполнителя

- **Фактическое поведение.** Персонализация включается так (`controls_tab.py:4460–4475`): user-редакция
  → `settings["network_user"]`; admin с выбранным **конкретным** исполнителем в фильтре → это ФИО;
  «Все»/«Прочие» → общий вид. В `export(...)` при непустом `user_name` колонка I =
  `user_effective_due_date`, подсветка = `user_deadline_status` (`controls_exporter.py:127–136, 183–197`); жёлтая заливка **только** `OVERDUE`/`TODAY` (SOON не подсвечивается, `:235–236`),
  зелёная — `done` (`:238–239`). Остальные колонки (содержание, исполнители, контролёр, комментарий)
  не персонализированы. Скрытый лист пишется из того же списка, поэтому чужих записей в user-экспорт
  не попадает `[код]`.
- **Источник.** строки выше; корневой `AGENTS.md` §5 (инвариант «user_effective_due_date», подсветка
  только OVERDUE/TODAY).
- **Пограничный пример.** Синтетика: админ фильтрует «Исполнитель = Иванов И.И.», `due_date` контроля
  просрочен по чужому пункту → в файле колонка I показывает дату пункта Иванова (будущая),
  подсветки нет; при фильтре «Все» — дата просрочки и жёлтая заливка.
- **Целевое поведение.** «Экспорт как список»: сервер строит xlsx из того же запроса и той же роли;

  в user-экспорт физически не попадают чужие строки и скрытые листы с чужими данными.
- **Намеренное отличие.** Экспорт — серверная операция с правами и лимитом, а не запись в
  произвольную папку пользователя.
- **Этап.** W05.
- **Проверка приёмки.** Разбор сгенерированного файла тестом: колонки I/H/подсветка = ожидания по
  матрице R08; user-экспорт не содержит чужих `incoming_number` (в т.ч. на скрытом листе); размер
  ограничивается (страница/максимум строк — `[предложение]`: 10 000 строк).

- **Фактическое поведение.** `import_plan` (`controls_exporter.py:611–716`) сопоставляет: сначала

  (`core/backup.py:388`), затем присвоение `id` новым записям и `_persist`. Проверки
  «не изменились ли данные с момента плана» и срока годности плана нет `[код]`.
- **Источник.** строки выше.
- **Пограничный пример.** Файл со скрытым листом, где у двух строк одинаковый `incoming` →
  `_read_full_sheet` (`:718–735`) строит словарь по номеру и **теряет** одну из записей
  `[код]`.
- **Целевое поведение.** Двухфазный импорт с серверным состоянием: `POST /imports` (upload + план)
  → `GET /imports/{id}` (план, срок действия, список изменений по полям) → `POST /imports/{id}/apply`

- **Намеренное отличие.** «Слепое» применение заменяется версионированием; richer-поля сохраняются
  (как в legacy), изменения показываются пофайлово, а замена списков пунктов не затирает
  исполнение `[предложение]`.
- **Этап.** W05.
- **Проверка приёмки.** Тесты: план unchanged → 0 записей; изменённая ячейка → ровно нужные поля;
  пустые ячейки не стирают tasks/вложения; конфликт (2 записи с номером) → 0 изменений;

  **отдельно**: изменение даты пункта в Excel не снимает `is_done` и не стирает `done_date`/
  `comment` и `id` остальных пунктов (регресс найденного поведения legacy).

### R18. Распознавание пунктов из старого содержания

- **Фактическое поведение.** `parse_content_tasks` (`controls_models.py:232–305`) поддерживает два
  формата: цепочка «ФИО п.3 к 05.05.2026, п.5 к 05.09.2026» (владелец цепочки — ближайшее
  полное ФИО до маркера) и inline «п. 2 - Зайцев 01.05.2026, п. 6 Орлов, Литвинов -
  16.02.2026, п. 8 - 30.07.2026» (несколько «голых» фамилий, пункт без исполнителя допустим).
  Пункт без «к <дата>» задачей не считается; если ни одного пункта со сроком нет — содержание
  возвращается без изменений `[выполнено: «Нужен отчет по ОПК п. 1 без срока» → (без изменений, 0
  задач)]`. Номер пункта — `\d+(\s*[.,]\s*\d+)*[а-яa-z]?` (`:189–191`), т.е. «9.3», «5б», «5,6»;
  дата DD.MM.YY(Y) (`:194–197`). Ответственные разрешаются к канону TWO-проходом: сначала по колонке
  «Исполнитель», затем по справочнику людей, и только при **единственном** кандидате по фамилии
  (`:307 resolve_task_assignees`); новые имена добавляются в `executors` контроля
  (`controls_exporter.py:793–797`).
  **Риск:** при успехе содержание переписывается — вырезается регион от первого до последнего
  consumed-спана (`controls_models.py:298–304`), т.е. из текста исчезают и ФИО, и любые слова внутри
  региона `[выполнено]`:
  · «Распоряжение 12/34-р от 15.01.2026 Литвинов Э.А. п.3 к 05.05.2026, п. 5 к 05.09.2026» →
    содержание «Распоряжение 12/34-р от 15.01.2026» (ФИО исчезло), задачи п.3/п.5 на «Литвинов Э.А.»;
  · «Отчёт п. 1 к 01.05.2026 ВАЖНАЯ ОГОВОРКА СРОК ДО 01.05 п. 2 к 01.06.2026» → содержание
    «Отчёт»: **всё, что стояло между первым и последним распознанным пунктом, удалено**.
- **Источник.** строки выше; `controls_exporter.py:765–800`.
- **Пограничный пример.** «п. 8 - 30.07.2026» (без исполнителя) → задача создаётся с пустым
  `assignees`; «ОПК п. 1» — не задача; «п.3к05.05.2026» (слитно) — маркер не матчится из-за
  обязательного разделителя `[код — пробел между «п.» и числом/«к» и датой требуется]`.
- **Целевое поведение.** Тот же парсер переносится как чистая функция с тестами; **исходный текст
  содержания сохраняется** (`content_original` / `legacy_raw`), а распознанные пункты не переписывают
  его молча; нераспознанный текст остаётся в содержании (как legacy, но дополнительно — флаг
  «требует ручной разбор»).
- **Намеренное отличие.** «Не чистим содержание автоматически» — содержимое становится
  неизменяемым оригиналом + отдельным текстом `[предложение]`.
- **Этап.** W05 (парсер), W07 (применение при миграции).
- **Проверка приёмки.** Табличные тесты на 6 эталонных строках (оба формата, смешанный, без дат,
  слитный, «п. 9.3», многоточие) — ожидаемые `title/due_date/assignees` + инвариант:
  `content_original` содержит исходную строку целиком.

### R19. Дубликаты по нормализованному входящему номеру

- **Фактическое поведение.** `normalize_incoming_number` (`controls_dedup.py:48–67`): NFKC +
  casefold + все варианты тире → `-`, `/ \ | _` и пробелы → `-`, схлопывание повторных `-`
  `[выполнено: «ИСС 12 - 34-26» == «исс-12-34-26», пустой номер → ""]`. `business_key`
  (`:86–101`) = (номер, `receive_date`, канон инициатора, SHA1(нормализованное содержание)[:12]);
  **пустой номер → None → запись никогда не участвует в слиянии**. Выбор canonical (`:141`):
  есть вложения → полнота полей → свежее `updated_at` → меньший `id`.
  `merge_duplicate_group` (`:170–263`) объединяет: вложения union по относительному пути, пункты
  union по `id`/ключу содержания, точки union по ключу, исполнители union, пустые скаляры
  добираются, `done` принимается от исполненного дубля, `created_at` — самое раннее,
  `updated_at` — сейчас. `dedupe_controls` (`:349–458`) сначала union по `id` (LWW), затем группы;
  `move_files=False` — «сухой» режим для read-пути (`controls_tab.py:781 _dedupe_view`), `True` —
  при записи admin (`:742–751`) и на старте при наличии дублей (`:834–866`), предварительно делая
  `migration_backup` с маркером `.migration_dedup38_done` (`core/backup.py:405`).
  Диагностика `diagnose_duplicates`/`diagnostics_report` (`:472, :508`) — только ID и номера.
- **Источник.** строки выше.
- **Пограничный пример.** Две записи с равным номером, но разной `receive_date` (01.02 и 02.02) →
  `business_key` разный → **не** сливаются (консерватизм подтверждён кодом).
- **Целевое поведение.** При миграции — диагностика и план слияния (кто канонический, что
  объединяется, судьба файлов); в рантайме — предупреждение о дубле при сохранении (номер уже
  занят), **без** автоматического слияния; разрушительное слияние — отдельная admin-операция с
  подтверждением и аудитом.
- **Намеренное отличие.** «Лечение при каждом чтении» (legacy) заменяется явными операциями;
  UNIQUE на номер — только после разбора коллизий `[решение владельца]`.
- **Этап.** W03 (диагностика/предупреждение), W05 (импорт), W07 (миграция).
- **Проверка приёмки.** Повторный запуск плана → 0 изменений (идемпотентность); записи с пустым
  номером не слиты; файл после слияния существует и скачивается; отменённое слияние не оставляет
  «полуперенесённых» папок.

### R20. Уведомления

- **Фактическое поведение.** Два независимых контура, оба в фоновом цикле вкладки
  (`controls_tab.py:5245 _background_loop`, цикл ≈ 20 с + poll + 40 с → ≈ 60 с):
  1. **Персональные** (`:5553 _check_my_notifications`, только при `network_enabled`, роли `user` и
     непустом ФИО): (а) «новый контроль для меня» — ключ `<id>:new`, один раз; (б) смена статуса на
     `OVERDUE/TODAY/SOON` по **своим** пунктам (`user_deadline_status`) с антиспамом
     `_should_notify` (ключ `<id>:<status>`, не чаще раза в день на статус)

     `notify_log` подрезается до 30 дней при сохранении настроек (`:310 prune_notify_log`)

     Формат — звук `winsound.MessageBeep` + SnackBar-тост (`:5328, :173`).
  2. **«Злой» аларм** (`:5690 _check_deadline_alarms` → `core/controls_notify.py`):
     статусы `OVERDUE/TODAY`, активные, не `done`; для user — только контроли, «принадлежащие»
     человеку по правилу `control_belongs_to` = контролёр **или** исполнитель **или** ответственный
     пункта (`:30–41`) — то **шире**, чем `_mine` в списке (R12); интервал повтора user 2 ч, admin
     24 ч (`:20–25`) `[выполнено: 1 ч 59 мин → не сработал, 2 ч 01 мин → сработал]`; журнал
     `alarm_log` (ISO-метки, 30 дней, `:87`); звук — `assets/pig.mp3` через Windows MCI
     (`ui/sound_alert.py:1–60`), плюс balloon из системного трея в web-режиме
     (`controls_tab.py:5720–5730`); модалка «СРОК КОНТРОЛЯ!» со списком до 10 + «…и ещё N»
     (`:5617`). Отдельно — тост при росте числа просроченных (`:5596 _poll_notifications`).
  Оба контура работают **только при живом процессе приложения** и «завязаны» на Windows-специфику
  (winsound/MCI/tray). Виды уведомлений legacy, которые надо перечислить явно:
  `new_control_personal`, `status_change(overdue|today|soon)`, `deadline_alarm_modal`,
  `overdue_count_toast`, `tray_balloon`, `save/export/import toasts`, `sync_state indicator`,
  `shared_conflict_dialog`, `lock_dialog`, `time_skew_warning` (`:5842`).
- **Источник.** строки выше.
- **Пограничный пример.** См. S04 (фигурирует расхождение «alarms шире списка»).
- **Целевое поведение.** Лёгкий серверный контур: события «наступил срок»/«изменён контроль»
  доставляются в браузер (polling + Web Notifications, если доступны), без дублей между вкладками
  (один журнал на сервере, а не в настройках конкретного ПК), `done/archived` исключены,

  браузере, фоновый запуск, tray.
- **Намеренное отличие.** Перенос журнала на сервер и отказ от guarantees при закрытом браузере —
  требует подтверждения `[решение владельца]`.
- **Этап.** W06.
- **Проверка приёмки.** Тест: два открытых окна одним пользователем → не два уведомления;
  «сегодня» → одно событие в день; `done` → тишина; пользователь-контролёр без назначенных пунктов
  ведёт себя согласно выбранному правилу доступа (см. R12/R08), и это правило **одно** для списка,
  счётчиков, алармов и экспорта.

### R21. Backup, восстановление, журнал действий

- **Фактическое поведение.** Ежедневные копии (`core/backup.py:34–52, 211–386`): локальный полный
  снапшот 6 JSON + `templates/` + `controls_attachments/`, атомарная публикация, `manifest.json`
  (дата, версия схемы, файлы/размеры/SHA256 критичных JSON), retention 30, маркер `.last_local_ok`,
  межпроцессный lock; shared-снапшот — только admin (`:310–375`); `backup_file_now` перед применением
  импорта; `migration_backup` перед первым лечением дублей; `restore_local_snapshot` — копирование
  в **отдельный** каталог, вручную (`:482–501`). Кроме того `_make_backup` перед каждой перезаписью
  JSON: `.bak.<stamp>` с подрезкой до 3 (локально) / 5 (shared) (`core/controls_data.py:132–160`).
  UI-видимость — только tooltip индикатора синхронизации у admin (`controls_tab.py:898–905`).
  **Журнала действий как сущности нет**: история — только `created_at/updated_at`, `notify_log`,
  `alarm_log` и ASCII-логи (`core/crash_log.py`, `error.log`). Отдельного контроля целостности
  файлов при старте нет (SHA256 складывается в manifest, но не сверяется) `[код]`.
- **Источник.** строки выше.
- **Целевое поведение.** pg-based backup (dump + файловое хранилище) по расписанию, проверка
  контрольных сумм, восстановимость на изолированном стенде; `audit_log` — обязательная сущность
  (актёр, время, объект, изменение, причина) без паролей и содержимого сканов; UI-просмотр журнала
  для admin.
- **Намеренное отличие.** Вместо «3–5 откатных файлов» — режимные копии + непрерывный журнал;
  восстановление — тестированная процедура, а не ручное копирование папки.
- **Этап.** W02 (аудит), W07 (backup/restore runbook), W08 (репетиция восстановления).
- **Проверка приёмки.** Восстановление на отдельной БД из копии, датированной «до» изменений:
  количество записей/вложений и SHA256 выборки совпадают; в аудите видны все операции этапа;
  сбойная копия не помечена успешной.

### R22. Обновление при открытии и во время работы

- **Фактическое поведение.** Поллинг: `_poll_network_io` (`controls_tab.py:5482`) в фоновом потоке
  делает `stat`/чтение shared, применения — `_poll_network_apply` (`:5512`) через `_post_to_ui`
  (`:5207`), цикл ≈ 60 с; изменение mtime → без открытой карточки `_apply_shared_update`
  (замена списка + ненавязчивый тост, `:5377`), с открытой — `pending_shared` + диалог «Данные на
  сервере изменились» с «Обновить/Позже» (`:5341`), где «Обновить» **закрывает карточку без
  сохранения** (правки теряются); «Позже» — применение при закрытии (`:2401`).
  Индикатор «Локально / Сеть: роль · чч:мм:сс / Сеть: нет связи» (`:884`). Потеря shared: красный
  индикатор; возврат сети: merge (локальные правки дороже) + обратная публикация (`:5412`); пустой
  shared не затирает локальные данные, но `mtime` принимается (`:5537–5543`); локальный кэш
  синхронизируется, чтобы не отставать (`:708–750`). Удалённые в shared записи **воскрешаются**
  (нет tombstone, `core/controls_data.py:1170–1180`).
- **Источник.** строки выше; `docs/network_audit_report.md` §§ БАГ 1, 5, 7; «Известные ограничения» 1–5.
- **Пограничный пример.** Два админа: А открыл карточку, Б изменил тот же контроль → А видит диалог;
  «Обновить» → несохранённый текст А потерян; «Позже» → сохранение А затирает Б целиком (LWW).
- **Целевое поведение.** `GET /api/changes?since=` или `HEAD /api/revision` каждые 15–30 с +
  проверка при возврате фокуса вкладки; обновление не пересоздаёт страницу и не трогает форму; при
  конфликте — серверный 409, черновик остаётся в UI (несохранённый ввод не теряется), предлагается
  сравнить; статус связи и время последнего обновления — видимые; backoff при ошибках.
- **Намеренное отличие.** Отказ от «закрыть карточку без сохранения» в пользу сохранения черновика
  (см. `01-architecture.md`, требует подтверждения W00).
- **Этап.** W06.
- **Проверка приёмки.** E2E: изменение на клиенте 2 видно на клиенте 1 ≤ интервал+5 с; форма с
  несохранённым текстом не очищается ни при 409, ни при обрыве сети; скрытая вкладка → при фокусе
  немедленная проверка; в списке нет «воскресших» удалённых записей.

## 3. Синтетические пограничные сценарии (будущие тест-кейсы)

Все ФИО/номера вымышлены. Ожидаемый результат — «как делает legacy» (базовое поведение) и «что

### Блок «индивидуальные сроки / пункты» (S01–S06)

**S01. Чужая просрочка не красит пользователя.**
Вход: контроль `ВХ-П-101`, `due_date = сегодня−10`, пункты: п.1 `Иванов И.И.` сегодня−10,
п.2 `Сидоров С.С.` сегодня+20.
Legacy-ожидание: admin-статус «Просрочено»; у Сидорова срок сегодня+20, статус «В работе», в
алармах его нет; в списке Сидоров видит дату своего пункта, в tooltip — общий срок.
Целевое: то же, но «сегодня» серверное; в ответе API есть `myDueDate` и `myStatus`.
Источник: `controls_models.py:532–590`, `controls_tab.py:953–961`.

**S02. Свои пункты исполнены, чужие — нет.**
Вход: `ВХ-П-102`, пункты п.1/п.2 на Сидорова исполнены 5 дней назад, п.3 на Иванова просрочен,
Сидоров не в `executors` и не контролёр.
Legacy: `user_effective_due_date=None` → `user_deadline_status = IN_PROGRESS` («В работе», не
«Без срока»); контроль остаётся в его списке (признак `_mine` по пунктам); алармов нет.
Целевое: то же поведение подтверждено как норма (или изменено решением владельца).
Источник: `controls_models.py:544–563, 571–590`.

**S03. Fallback общего исполнителя.**
Вход: `ВХ-П-103`, `executors=[Иванов И.И.]`, пунктов нет, `due_date` сегодня−1, просроченная точка
milestone сегодня−5.
Legacy: админ — `OVERDUE`; Иванов (общий исполнитель) — срок = `min(due_date, дата точки)` =
сегодня−5 → `OVERDUE`; при этом у исполнителя **своим** пунктом ничего нет.
Целевое: правила «точки влияют на персональный срок или нет» — одно, зафиксированное (см. R04).
Источник: `controls_models.py:441–456, 532–563` `[выполнено: точка участвует в общем сроке и не
участвует в персональном]`.

**S04. Только «за кем контроль».**
Вход: `ВХ-П-104`, `controller = Петров П.П.`, `executors=[]`, пунктов нет, срок сегодня.
Legacy-противоречие: в списке user-редакции контроля нет (`_mine` не смотрит `controller`,
`controls_tab.py:914–936`), но аларм приходит (`control_belongs_to` смотрит, `controls_notify.py:30–41`),
и в user-экспорте строка появится, только если он в `executors`.
Целевое: одно правило видимости участника для списка, счётчиков, алармов, экспорта — **выбор
владельца**: «контролёр — участник» или «контролёр — только поле».
Источник: S04 — `[код]` + `[выполнено]`.

**S05. Схожие фамилии / опечатки.**
Вход: справочник содержит «Иванов Иван Иванович» и «Орлов Иван Юрьевич»; в пунктах записаны
«Иванова А.А.» и «Орловых П.П.» (другие люди).
Legacy: `name_matches` даёт True в обоих случаях (фамилия-подстрока/нечёткое сравнение) →
пользователь получает чужие пункты и чужие «просрочки» `[выполнено]`.
Целевое: сопоставление исключительно по `person_id`; нечёткое сравнение допускается только как
подсказка администратору при разборе справочника; для авторизации — запрещено.
Источник: `controls_models.py:69–117`.

**S06. Однофамильцы в справочнике.**
Вход: криминалист «Иванов И.И.» (роль executor по умолчанию) и добавленный `extra_people`
«Иванов С.С.» (должен быть контролёром).
Legacy: `get_all_people_names` схлопывает по фамилии → вторая запись исчезает;
`get_person_roles` применяет роли по фамилии → оба «одни и те же» `[код]`.
Целевое: две отдельные личности, разные `person_id`; столкновение фамилий требует явного решения
админа; роль — атрибут персон, не «фамилии».
Источник: `controls_data.py:388–420, 430–487`.

**S07. Колонка H комбинированная.**
Вход (строка листа): `вх. = "ИСС 12 - 34-26"`, `Дата поступления = 05.05.2026`,
`Содержание = "Распоряжение 12/34-р от 15.01.2026 Литвинов Э.А. п.3 к 05.05.2026, п. 5 к 05.09.2026"`,
`Исполнитель = "Громов С.А., Орлов И.Ю."`, `H = "05.09.2026 далее каждые 3 месяца"`,
`I = "10.05.2026"`.
Legacy-ожидание (подтверждено запуском): `control_type=periodic`, `period_days=90` (=3×30, а не
«3 календарных месяца»), `end_date=2026-09-05`, `due_date=2026-05-10`, `receive_date=2026-05-05`;
две задачи («п. 3» и «п. 5») на «Литвинов Э.А.», который добавлен в `executors`; содержание
сокращено до «Распоряжение 12/34-р от 15.01.2026» (ФИО удалено из текста).
Целевое: то же вычисление + сохранение `content_original`; периодичность остаётся «90 дней».
Источник: `controls_exporter.py:765–853`, `controls_models.py:232–305`.

**S08. Экспорт в режиме «Архив» и с активными фильтрами.**
Вход: в таблице включён режим «Архив», фильтр «Просрочено», поиск «216».
Legacy: `export(_visible_base())` → `active = [c for c in controls if not c.archived]` → **пустой
файл**; в режиме «Активные» фильтры и поиск игнорируются, сортировка не применяется, «№» — индекс
строки.
Целевое: экспорт = текущий запрос (фильтр/сортировка/страница или «все страницы» по явной опции);
экспорт архива — отдельная операция; пустой результат объясняется в UI.
Источник: `controls_tab.py:4457–4470`, `controls_exporter.py:182`.

**S09. Полный round-trip и скрытый лист.**
Вход: экспорт full → импорт того же файла без правок; в исходной паре записей одинаковый
`incoming`.
Legacy: unchanged-файл даёт «Без изменений» (значения совпадают); **но** `created_at/updated_at`
исторический лист не несёт → после импорта они = время импорта, `archived_at` теряется; дубль
номеров теряет одну запись в `full_by_incoming` `[выполнено — потеря timestamps; код — ключ по
номеру]`.
Целевое: план импорта показывает дельту по полям; идентификатор — UUID, а не номер; при отсутствии
в файле `created_at` серверное поле не подменяется; дублирующиеся номера в скрытом листе →
конфликт.
Источник: `controls_exporter.py:262–273, 611–716, 930–964`.

**S10. Устаревший предпросмотр.**
Вход: план показывает 3 обновления; до нажатия «Импортировать» админ Б меняет одну из записей.
Legacy: применение идёт «вслепую» (deepcopy-план → `_apply_row_to_existing` по живой записи);
вложения/richer-поля не теряются, но поля Б могут быть перезаписаны.
Целевое: `apply` с `expected_revision` → 409 на изменившиеся строки, план помечен «устарел»,
требуется пересборка.
Источник: `controls_tab.py:4513–4611`, `controls_exporter.py:529–609`.

### Блок «архив / периодичность» (S11–S13)

**S11. Восстановление после «Исполнен».**
Вход: контроль `ВХ-П-120` исполнен 10.08.2026 (→ `done=True`, `archived=True`,
`archive_reason=done`); пользователь жмёт «Восстановить».
Legacy: `archived=False`, `archived_at=None`, `reason=""`, но `done=True`/`done_date` сохранены →
запись активна со статусом «Исполнено», вне алармов, и штатного способа вернуть «в работу» нет.
Целевое: операция «вернуть в работу» (снимает `done`+`done_date`, пишется в аудит) либо явное
сохранение legacy-семантики — по решению владельца.
Источник: `controls_data.py:831–849`, `controls_tab.py:4350–4430`, `controls_notify.py:47`.

**S12. Периодический без автопереноса.**
Вход: `ВХ-П-121`, `periodic`, `period_days=30`, `due_date=сегодня−40`, `end_date=None`.
Legacy (подтверждено запуском): статус `OVERDUE`, `due_date` не меняется, счётчик «Просрочено» +1,
аларм повторяется каждые 24 ч (admin) / 2 ч (user); «Завершён» не наступает никогда.
Целевое: А (как legacy) или Б (серверное «закрыть период») — см. R05; выдуманного автопереноса нет.
Источник: `controls_models.py:502–530`.

**S13. «Удалить навсегда» + офлайн-админ.**
Вход: админ А удаляет навсегда `ВХ-П-122` (файлы удалены из shared); админ Б был офлайн и
сохраняет другой контроль.
Legacy: `merge_controls` union → запись Б из локального кэша возвращает удалённый контроль в
shared; файлы уже нет → карточка с «Файл вложения не найден».
Целевое: единая БД — запись физически одна; восстановление возможно только из backup (W07) и
фиксируется в аудите; вложения после hard-delete сборщиком не «вешаются».
Источник: `controls_data.py:1170–1180`, `docs/network_audit_report.md` «Известные ограничения» 1.

### Блок «файлы / повторы» (S14–S16)

**S14. Одноимённые разные файлы.**
Вход: к `ВХ-П-130` прикреплены два разных PDF с именем `Скан.pdf` (второй — из другой папки).
Legacy: `_unique_filename` даёт `Скан_1.pdf` в папке `<id>/`, оба пути в `attachments`; скачивание
показывает изменённое имя.
Целевое: один storage-key (uuid), разные `display_name`, `size`, `sha256`; одноимённые ≠ дубли,
байт-идентичные — де-дуплицируются (счётчик копий), но не сливаются «в один объект» без явного
правила.
Источник: `controls_data.py:1043–1082`, `controls_dedup.py:265–347`.

**S15. Обрыв загрузки и отмена карточки.**
Вход: (а) копирование 30 МБ прервано на середине; (б) новая карточка с прикреплённым файлом
закрыта по «Отмена».
Legacy: (а) tmp удаляется, битого файла под финальным именем нет, вложение не прикреплено, тост
«Не удалось прикрепить файл»; при `reason="error"` (сеть доступна, публикация упала) локальный
фолбэк запрещён. (б) `delete_attachment` чистит сирот.
Целевое: upload-session TTL + сборщик сирот; ошибка загрузки ≠ успех; «прерванный upload» не
считается сканом; повторное нажатие не создаёт копию.
Источник: `controls_data.py:881–1027`, `controls_tab.py:2464–2478, 3508–3617`.

**S16. Повторное событие выбора файла.**
Вход: FilePicker присылает одно и то же событие 5 раз (реальный симптом «13 фото»).
Legacy: первое обрабатывается, остальные — дубли по подписи в окне 3 с; повторный осознанный выбор
того же имени отсекается проверкой по уже прикреплённым именам; при этом «тот же файл, но
добавленный позже 3 с» — тоже пропустится по имени (намеренно).
Целевое: ключ идемпотентности на операции добавления + сравнение по содержимому (SHA256), а не по
имени.
Источник: `controls_tab.py:285–311, 361–391, 3619–3660`.

### Блок «доступ / сеть» (S17–S20)

**S17. Роль user без ФИО.**
Вход: `network_role="user"`, `network_user=""`, сетевой режим включён.
Legacy: `_visible_base()` не применяет фильтр (условие `role == "user" and network_user`) →
пользователь видит **все** контроли в списке; статусы считаются по общему правилу
(`_user_mode()` тоже False) `[код]`.
Целевое: отсутствие аутентификации = 401; «неизвестен себя» невозможно — личность берётся из
сессии.
Источник: `controls_tab.py:937–951`.

**S18. Прямой доступ по адресу/порту.**
Вход: любой хост той же LAN открывает `http://<машина-с-приложением>:8555` (web-обёртка слушает
`0.0.0.0`).
Legacy: приложение доступно без пароля (админ-ворота отключены с раунда 34,
`main.py:49–75`); выбор «кто я» — клиентский.
Целевое: HTTPS + сессия; любой API-запрос без cookie → 401; `http://` редирект или отказ;
файлы/экспорт — только через авторизованный endpoint; прямой URL на вложение не работает.
Источник: `main_web.py:73–77`, `main.py:49–75`.

**S19. Обрыв сети во время сохранения.**
Вход: сеть падает между «Сохранить» и записью shared (или БД).
Legacy: локальный `save_controls` может пройти, `write_shared_controls` → `False`, индикатор
«Сеть: нет связи»; карточка остаётся открытой (обработчик прерывается исключением из
`save_controls` при недоступном диске), тост «Сохранено» не показан; при возврате сети правки
уходят в shared через merge.
Целевое: сохранение = одна транзакция; при ошибке форма и введённые значения сохраняются, статус
«не сохранено», явная повторная отправка; никаких «локально сохранено, а на сервере нет».
Источник: `controls_tab.py:708–760, 3707–3848`, `controls_data.py:113–130, 1250–1302`.

**S20. Конфликт двух администраторов.**
Вход: оба открыли `ВХ-П-140` (одна и та же версия); А меняет содержание, Б — исполнителей.
Legacy: advisory lock-файл (`core/control_locks.py:111 acquire_lock`, stale 10 мин, touch раз в
≈60 с) мешает открыть карточку второму, **но** не проверяется при сохранении; при обходе (разные
машины, lock протух) — LWW целиком по `updated_at`, поля не сливаются
(`docs/network_audit_report.md` «Подтверждено корректным», `controls_data.py:1149–1199`).
Целевое: серверная проверка `expected_revision` → второй получает 409, свой черновик сохраняет,
показывается свежая версия; lock (если оставляем) — только подсказка UX, а не защита.
Источник: `control_locks.py:96–186`, `controls_data.py:1149–1199`.

## 4. Что в legacy не найдено (чтобы не «перенести» выдуманное)

- Авто-перенос срока периодического контроля, авто-закрытие по `end_date`, «очередь» напоминаний
  на сервере — **нет** `[код]`.
- Право пользователя менять себе роль/ФИО — есть (настройки), и это не авторизация — **не переносим**.
- Разрешение «редактировать чужой пункт»/ограничение «видеть только свои пункты» — в коде нет
  явной проверки: карточка показывает контроль целиком, включая все пункты (`controls_tab.py:2603`),
  фильтр влияет только на видимость контроля целиком `[код]` → см. `[решение владельца]` в `decisions.md`.
- Журнал действий, версионирование записей, tombstone-удаления, атомарные проверки «rev+CSRF»,
  серверная пагинация, проверка MIME — **нет** (всё это новое, W02+).
- `tools/audit_excel.py` и `core/edition.py::admin_password_*`/`ui/admin_gate.py` — живые, но
  «выключенные» механизмы; при переносе не считать их требованиями.
