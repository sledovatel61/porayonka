# Одинаковый промпт для трёх агентов Arena — этап 1 / W00

Ниже текст для копирования каждому агенту без изменений. Репозиторий должен содержать migration-web, включая этот документ. Все три агента стартуют с одного коммита, но работают в отдельных ветках/checkout. Имена веток и SHA агент определяет сам, подставлять разные задания не нужно.

---

Ты — исполнитель проекта «Порайонка: перенос Контролей в браузер». Это первый этап W00: **обследование кода и подробное проектирование. Код приложения сейчас НЕ писать.** По качеству этой работы оркестратор выберет исполнителя следующих этапов. Выполни всё задание самостоятельно; не дели работу с другими кандидатами и не используй их результаты.

## 0. Главное правило: не закрывать coding-сессию

Эта coding-сессия нужна для последующих этапов и исправлений. После передачи результата на проверку **не закрывай, не завершай и не архивируй её**, не вызывай функции finish/close/end-session и не удаляй workspace или ветку. Закончи обычное сообщение и жди следующего задания здесь же. Не начинай W01 сам. Не запускай бесконечное ожидание/keep-alive и не расходуй инструменты для удержания сессии.

Сохрани контекст в migration-web/reports/SESSION-HANDOFF.md. Если доступен идентификатор или безопасная ссылка сессии, сообщи его; иначе напиши «идентификатор сессии мне недоступен». Не выдумывай его. Если Arena автоматически закрывает сессию либо требует её завершения для передачи результата, предупреди об этом: ты не можешь гарантировать управление платформой. Завершение этапа и закрытие coding-сессии — разные вещи.

## 1. Контекст и границы

Сейчас это Python/Flet 0.23.2-приложение. Рабочий legacy находится в porayonka-app; src — отдельный React-прототип, не готовая новая система. В старой программе три вкладки. Переносим **только Контроли** и необходимые им справочники. Зональные криминалисты, их PDF и отделы пока остаются в старой программе.

Владелец выбрал браузер. Целевая схема: один центральный сервер в локальной сети, на клиентских Win7 и современных ПК только браузер. Не локальный Python/Flet-сервер на каждом компьютере. Базовое предложение — FastAPI + React/TypeScript + PostgreSQL; конкретные версии, серверная ОС и браузер пока не утверждены. Они не должны быть выдуманы агентом.

Пользователь не разработчик: краткий итог простым языком. Рабочие документы для следующих агентов должны быть точными и проверяемыми. Не переписывай существующий план другими словами: дополни его фактами из кода, примерами, mapping и критериями.

## 2. Перед началом

1. Определи абсолютный корень checkout, текущую ветку, git status и базовый SHA. Работай в выданной Arena ветке; не меняй main и чужие файлы. Не выполняй reset/checkout для очистки чужих изменений.
2. Прочитай корневой AGENTS.md, migration-web/AGENTS.md, README.md и документы 01–05. Прочитай критерии сравнения 07-agent-selection.md. Если документов нет, сообщи точный блокер: не восстанавливай их наугад.
3. Кратко изложи план обследования. В этой задаче разрешено создавать/менять только перечисленные ниже Markdown-документы в migration-web. Не создавай controls-web, не меняй исходники, зависимости, lock-файлы, сборки, корневые инструкции и исходный пакет плана.
4. Не читай рабочие APPDATA/UNC-ресурсы, не запрашивай реальные сканы/JSON и не отправляй их наружу. Используй синтетические ФИО и примеры; имеющиеся в исходниках настоящие имена не размножай в отчёте.

## 4. Обязательные результаты — семь документов

### A. migration-web/requirements-matrix.md

Раскрой все R01–R24 из 02-requirements.md. Для каждого: фактическое поведение, источник в коде, пограничный пример, целевое поведение, намеренное отличие, будущий этап реализации и конкретная проверка приёмки.

Обязательно разберись, не ограничиваясь названиями функций:

- Как выбираются общий и персональный сроки; что происходит, если свои пункты исполнены, но есть чужие; fallback для общего исполнителя и контролёра.
- Периодический контроль: period_days, конечная дата, исполнение и промежуточные сроки. Не считать месяц равным календарному месяцу, если код хранит 30 дней. Не изобретать автоматический перенос срока, если его нет.
- Архив done/deleted, восстановление флагов, окончательное и массовое удаление.
- Фильтры/счётчики/сортировки, настройки и справочники; используемая карточка против альтернативной/неиспользуемой.
- Excel H/I, оба режима, скрытые листы, preview/upsert, сохранение richer-полей, парсер пунктов, дедуп.
- Вложения и исключения скан-гарда; уведомления по срокам и новым/изменённым контролям.

Дай не менее 12 конкретных синтетических пограничных сценариев с входом и ожидаемым результатом. Хотя бы четыре — по индивидуальным срокам/пунктам, два — по Excel, два — по архиву/периодичности, два — по файлам/повторам, два — по доступу/сети. Это текстовые будущие тест-кейсы, не написание тестового кода сейчас.

### B. migration-web/field-mapping.md

Полный mapping всех полей Control, ControlTask, ControlMilestone и настроек, нужных контролям. Колонки: legacy-поле/тип/значение по умолчанию; предлагаемая сущность/поле/тип в новой системе; null/пустое значение; преобразование; валидация; проверка сохранности; источник.

Отдельно: существующие UUID; пустые/дублирующиеся ID; строки ФИО → стабильные person_id; однофамильцы; неизвестные роли/поля; timestamps и календарные даты; порядок пунктов; относительные пути файлов и одинаковые имена. Нечёткое совпадение ФИО нельзя использовать для авторизации. Не придумывай отсутствующие данные и не выбрасывай их молча.

### C. migration-web/decisions.md

Раздели уже принятые решения и предложения. Предложи конкретное разбиение модулей, сущностей и операций API на уровне документа, без реализации и DDL. Достаточно компактной таблицы: операция, кто имеет право, вход, результат, ошибки/конфликт, транзакция/идемпотентность. Покрой контроль, пункт, архив, справочник, файл, импорт/экспорт, обновления и аккаунты.

Объясни: одна серверная БД вместо SMB/union-merge; revision вместо «кто позже по часам»; серверная авторизация, включая файлы/экспорт; временная загрузка и готовый скан; личные сроки; лёгкий polling; сохранение несохранённого ввода при конфликте. Не обещай локальный доступ к скачанному файлу или надёжный звук при закрытом браузере.

Зафиксируй инфраструктурные неизвестные и короткие вопросы владельцу. Сервер, браузер, офлайн-редактирование, фоновые напоминания, границы доступа к пунктам, справочник людей и HTTPS ещё требуют решения. **Не останавливай всё обследование из-за отсутствия ответов**: закончи независимую часть, отметь «ожидает решения». W00 целиком не объявляй принятым.

### D. migration-web/ui-outline.md

Один рекомендуемый вариант интерфейса: текстовые схемы списка, карточки, импорта и конфликтов/потери сети. Русские названия, компактная читаемая тёмная тема, минимум эффектов, таблица с серверной пагинацией, сроки и связь видны. Роли admin/user, длинные тексты и небольшой экран, сохранение позиции/фильтра. Не рисуй десяток альтернатив и не создавай HTML/React-код. Пока разрешение Win7 неизвестно, размеры только как явно подписанное предложение.

### E. migration-web/risk-register.md

Конкретные риски переезда: причина, последствия, как проверить, как снизить, на каком этапе закрывается, что блокирует ввод. Обязательно: старый браузер/Win7, неподтверждённый сервер, чужие данные по прямой ссылке, конфликты правок, локальные кэши и удалённые записи, потеря вложений, неатомарность БД+файлы, обратный переход после новых записей, реальные ограничения уведомлений.

### F. migration-web/reports/W00.md

Исходный SHA, ветка, перечень исследованного/неисследованного, выводы, проверки документов и результаты. Укажи, что можно принять как результат обследования, что требует ответа владельца, и почему W01 ещё нельзя начинать при открытых блокерах. Краткий итог владельцу — до 10 строк. Не оценивай себя баллами и не выбирай победителя.

### G. migration-web/reports/SESSION-HANDOFF.md

Краткий контекст для продолжения этой же coding-сессии: этап, ветка, базовый SHA, созданные файлы, фактические проверки, решения/блокеры, следующий разрешённый шаг, доступный идентификатор сессии. Напомни: не закрывать сессию, ждать ревью, не начинать W01. Результирующий SHA сообщи в ответе после коммита, не пытайся записать в сам коммит его собственный хэш.

## 5. Ограничения и самопроверка

- Менять только семь перечисленных документов. Не переписывать статус проекта и общие правила, не помечать W00 принятым. Замечания к плану фиксировать в decisions.md.
- Только документация: никаких новых зависимостей, CI, прототипов, миграций БД, сервера и тестового кода. Без необходимости не запускай legacy, который может обратиться к сети или рабочим данным. Если запуск проверки нужен, сначала проверь её изоляцию; если не обеспечена — не запускай и честно укажи это.
- Проверь, что каждый R01–R24 раскрыт, все поля моделей сопоставлены, источники существуют, ссылки работают, факты не смешаны с предложениями. Названия полей сверить с кодом, не только с исходным планом.
- Проверь git diff --check, diff и статус: нет исходников, секретов, реальных данных или чужих изменений. Зафиксируй только свои документы в текущей ветке. Не делать merge/rebase main, force push или удаление ветки. Если обычный push своей ветки разрешён средой, опубликуй её; иначе сообщи ограничение.
- Не завышай полноту: честная выявленная неопределённость лучше выдуманного решения. Не повторяй сотни строк исходного плана ради объёма.

## 6. Как передать результат

Сообщи:

1. «Результат W00 передан на проверку; ожидаю продолжения в этой coding-сессии. Команды закрытия не выполнял». Если платформа вынуждает закрытие — вместо этого явно предупреди.
2. Точное имя ветки, базовый и результирующий SHA, доступный безопасный идентификатор/ссылку сессии.
3. Список семи файлов и фактически выполненные проверки.
4. До пяти основных выводов из кода и короткий список вопросов, блокирующих принятие.
5. Явно: код не изменял; W01 не начинал; Win7 и production не проверял, если это так.

Далее жди ревью здесь же. Оркестратор может смениться на другую модель, но твоя coding-сессия должна оставаться сессией продолжения. Не объявляй проект завершённым.
