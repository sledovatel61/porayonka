## 3. ФИО → `person_id` (справочник участников)

**Что есть в legacy.** Люди — это строки ФИО в 4 местах: `control.executors[]`,
`control_task.assignees[]`, `control.controller`, плюс «текущий пользователь» в настройках
(`network_user`) и справочник (`extra_people`, `hidden_people`, `person_roles`). Собственной таблицы
людей у вкладки «Контроли» нет: канонический список собирается из **файла зональной вкладки**
(`core/zonal_data.py:309 load_criminalists`, ФИО + числовой `id` криминалиста) и двух дефолтных
контролёров (`core/controls_data.py:18 DEFAULT_CONTROLLERS`), плюс `extra_people`
(`:388 get_all_people_names`) `[код]`.

**Правила сопоставления legacy (переносить как есть нельзя):**
- `short_name("Фамилия Имя Отчество")` → «Фамилия И.О.» (`controls_models.py:42–64`) — только
  для отображения, не для идентичности;
- `name_matches(canonical, raw)` (`:89–117`) — точное совпадение, **подстрока фамилии**, или
  расстояние Левенштейна ≥ 0.80 `[выполнено: «Иванов И.И.» ↔ «Иванова А.А.» → True]`;
- `resolve_task_assignees` (`:307–335`) принимает «голую» фамилию, только если по ней **один**
  кандидат (casefold), иначе оставляет строку;
- `get_all_people_names` схлопывает справочник **по фамилии** (`controls_data.py:388–420`);
- `person_roles` по умолчанию назначается тоже по фамилии (`:430–487`).

**Алгоритм переноса (предложение).**
1. Собрать все различные raw-строки ФИО из `executors`, `tasks[].assignees`, `controller`,
   `network_user`, `extra_people`, канонического списка — с количеством вхождений.
2. Нормализовать для **сравнения**: NFKC, `-`/`_`→пробел, схлоп пробелов, `casefold`, убрать `.`
   после инициалов, «Фамилия Имя Отчество» ↔ «Фамилия И.О.» приводить к одному виду
   (`[предложение]`; порядок операций фиксируется в тесте).
3. Точное совпадение нормализованной «Фамилия + оба инициала» с элементом справочника → авто-связка
   `person_id`, `match_method=exact`.
4. Иначе — совпадение по уникальной фамилии (ровно один кандидат) → авто-связка с
   `match_method=surname_unique`, обязательный флаг в отчёте.
5. Иначе (0 кандидатов или ≥2 — **однофамильцы**) → запись в список ручного сопоставления
   (`match_method=manual`, `person_id=NULL` до решения админа). Нечёткое сравнение (Левенштейн) для
   связки **не применяется** `[код]` — см. R08/S05; оно допускается только как подсказка
   «возможно, это…» в UI сопоставления.
6. Люди справочника становятся сущностью `person(display_name, short_name, is_active)`;
   `raw_name` каждого назначения хранится в строке связи, чтобы экспорт и список оставались
   побайтно сопоставимыми с legacy.
7. `network_user`/редакционные ФИО в целевую модель **не переносятся** — вместо них учётная запись
   с привязкой `person_id` (`[код]` см. R12).

**Однофамильцы (правило приёмки).** Для пары «Иванов И.И.» и «Иванов С.С.»:
- в legacy — одна запись справочника и общие роли `[код]`;
- в целевой системе — два разных `person_id`; сопоставление «Иванов» без инициалов → `manual`;
  в списке/фильтрах оба различимы (показываем «Иванов И.И.» / «Иванов С.С.», сокращение не должно
  приводить к коллизии — при коллизии `short_name` расширяется до «Иванов И.» / «Иванов С.»)
  `[предложение]`.

**Неизвестные роли и поля.** `person_roles` хранит список ролей; распознаются только
`executor`/`controller`, прочее игнорируется (`controls_data.py:421–430, 430–487`) `[код]` →
целевое: enum + «неизвестная роль» в отчёт миграции. Неизвестные поля контроля → `legacy_raw` (§1).

## 5. Порядок пунктов и точек

- Источник порядка — индекс массива в JSON; перетаскивания/сортировки в UI нет; при удалении
  пункта остальные сдвигаются; при сохранении карточки список пересоздаётся из черновика
  (`controls_tab.py:3770–3819`) `[код]`.
- Целевое: `position = (index + 1) * 10`; операции «переместить» — отдельный PATCH; при слиянии
  дублей порядок = canonical-массив + добавленные (`controls_dedup.py:170–263`) `[код]`.
- Проверка сохранности: для каждого контроля — последовательность `title` в legacy-массиве равна
  последовательности `ORDER BY position` в целевой системе.

## 6. Относительные пути вложений и одноимённые файлы

- Формат: `"<control_id>/<имя файла>"` (`controls_data.py:963–1027`); разрешены фактически
  `.pdf/.png/.jpg/.jpeg` (проверка в скан-гарде и фильтре диалога), `ATTACHMENT_ALLOWED_EXT`
  объявлен, но не применяется `[код]`.
- Разрешение пути при чтении: shared → локально → фолбэк «rel-путь как есть»
  (`controls_data.py:1066–1133`, `controls_tab.py:3068–3079`) — потому что исторически папка
  вложений могла принадлежать **другому** id (раунд 22) `[код]`.
- Коллизии имён: `_unique_filename` добавляет `_1/_2/…` (`controls_data.py:1043–1053`) —
  т.е. путь в модели может **не совпадать** с исходным именем файла `[код]`.
- Правила переноса:
  1. обход всех `attachments` + содержимого `controls_attachments/` (локального и общего каталога —
     предоставляет владелец; в песочнице Agent не читалось `[не проверено]`);
  2. для каждого пути: `found(local)`, `found(shared)`, `found(both, identical)`,
     `found(both, differ)` (приоритет чтения legacy = shared — фиксируем это и помечаем
     расхождение), `missing`;
  3. содержимое → `attachment(storage_key=uuid, sha256, size, mime, original_name, legacy_rel_path,
     uploaded_by=NULL, created_at)`; связь `control_attachment(control_id, attachment_id, position)`;
  4. `original_name` = **исходное** имя (в т.ч. с `_1`, как его видел пользователь? — нет: храним
     фактическое имя файла в legacy-папке в `stored_name`, а исходное — если удалось взять из
     `legacy_raw`);
  5. байт-идентичные файлы внутри одного контроля не дублируются в хранилище (SHA256), но
     сохраняются как две логические ссылки, если legacy их держал двумя путями `[предложение]`;
  6. `missing` → запись создаётся, файл помечен `missing`, в UI — «файл не найден» (как legacy при
     `resolve_attachment=None`), в отчёт — отдельным разделом;
  7. скан-гард не должен «наказать» перенесённые исторические записи: `control.content_parsed`/`migration=true`
     освобождает от требования вложения (как в legacy: только новые карточки) `[код]` R13.
- Кириллица/пробелы/длинные имена: пути сохраняем как есть (UTF-8), без транслитерации; целевой
  storage_key — uuid, поэтому «небезопасные» имена в URL не участвуют `[предложение]`.
