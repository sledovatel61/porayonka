# Mapping полей: legacy «Порайонка» → предлагаемая схема новой системы

Этап W00, агент 1. Базовый SHA: `b5f24ab58c642fafb5cca616aa8b4e16d3a3de3f`.
Источники legacy: `porayonka-app/core/controls_models.py`, `controls_data.py`, `controls_exporter.py`,
`controls_dedup.py`, `controls_notify.py`, `control_locks.py`, `backup.py`, `edition.py`,
`ui/controls/controls_tab.py`, `core/zonal_models.py`, `core/zonal_constants.py`, `core/zonal_data.py`.

Целевая схема — **предложение агента [П]**, подлежит утверждению в W02. Никаких миграций БД в W00 не создавалось.
Настоящие ФИО и внутренние сетевые адреса в документе не воспроизводятся; примеры синтетические.

## 0. Правила чтения mapping

1. **«Legacy-поле»** — ключ в JSON-файле (`%APPDATA%\porayonka\controls.json`, `controls_settings.json`,
   `zonal_criminalists.json`). Формат файла: `{"schema_version": 2, "last_saved": "<ISO>", "controls": [ {...} ]}` **[З]**.
2. **«Тип в legacy»** — фактический тип в JSON, а не объявленный в dataclass. Legacy **не валидирует и не приводит типы
   при чтении** (`Control.from_dict`, `controls_models.py:415-440`) — это подтверждено зондом:
   `period_days: "30"` остаётся строкой, `done: "yes"` остаётся строкой и **истинно**,
   `due_date: "01.05.2026"` остаётся как есть и `parse_date()` возвращает `None` (строгий ISO, 28–35) **[З: M]**.
3. **«Цель»** — колонка предлагаемой схемы PostgreSQL. Типы — `uuid`, `text`, `date`, `timestamptz`, `boolean`,
   `integer`, `jsonb`.
4. **Правило переноса** описывает, что делать с некорректным значением. Общий принцип: **ничего не отбрасывать
   молча** — каждое отклонение попадает в отчёт миграции, исходное значение сохраняется в `legacy_raw`.
5. Маркеры доказательности те же, что в `requirements-matrix.md`: **[К]** код, **[З]** зонд, **[Т]** прогон теста,
   **[П]** предложение, **[Р]** решение владельца, **[Н]** не проверено.

### Критическое правило: читать исходный JSON, а не через legacy-модель

`Control.from_dict` принимает только известные ключи: неизвестные поля **теряются**, а ближайшая запись
(`save_controls` → `to_dict`) удаляет их из файла навсегда **[З: M]**. Зонд: запись с ключами
`custom_field` и `legacy_note` после round-trip сохранила ровно 22 стандартных ключа, оба посторонних исчезли.

Следствие для W07: миграционный инструмент обязан читать **сырой JSON** (`json.load`) и сохранять
весь исходный словарь записи в `legacy_raw` (jsonb), а не опираться на `load_controls()`.
Это же правило относится к `controls_settings.json` (в нём используются ключи, отсутствующие в
`DEFAULT_SETTINGS`, — см. §5) и к `zonal_criminalists.json`.

| `card_width`, `card_height` | int 920 / 780 | `user_pref` | Персональные; clamp к новому макету |
| `refs_width`, `refs_height` | int 680 / 560 | `user_pref` | Опционально **[П]** |

**Правило сбора:** настройки лежат **локально на каждом ПК** и не синхронизируются (`_shared_dir`/`_parse_shared_path`,
`controls_data.py:1134/1201`; в shared есть только `controls.json`, `controls_attachments/`, `.locks/`, `backups/`)
**[К]**. Миграция обязана собрать `controls_settings.json` **со всех рабочих машин** и объединить
(`extra_people`/`hidden_people`/`person_roles`/`init_renames`/`hidden_init_groups`/`custom_initiators` —
объединение с разрешением конфликтов через manifest), иначе часть людей и инициаторов будет потеряна.

## 6. Вложения → `attachment` + закрытое файловое хранилище

Legacy-представление: в `Control.attachments` хранится **относительный путь** `<control_id>/<имя файла>` **[К]**.
Физические папки: локально `%APPDATA%\porayonka\controls_attachments\<control_id>\`,
в сети `<shared>\controls_attachments\<control_id>\`; чтение — `resolve_attachment` (1066): сначала shared, затем локально.

| Legacy | Цель | Правило |
|---|---|---|
| строка пути `<id>/<name>` | `attachment.original_name text`, `attachment.control_id uuid FK` | Префикс пути должен совпадать с `control.id`; при несовпадении (наследие «лечения» id, `_attachments_prefix`, 169–179) — сохранять по фактическому префиксу и **связывать с записью по manifest**, а не по префиксу; расхождение → отчёт |
| сам файл | `attachment.storage_key text` (путь в закрытом хранилище) + `sha256` + `size_bytes` + `mime_detected` | Имя в хранилище генерирует сервер (например `<attachment_id>`), исходное имя — только метаданные. Кириллица сохраняется в `original_name` |
| одинаковые имена | разные `attachment` | Legacy **блокирует** добавление второго файла с тем же именем (`_filter_new_attach_files`, 371–390 **[З]**) и переименовывает только при коллизии на диске (`_unique_filename`, 1043: `_1`, `_2`). В новой системе одноимённые разные файлы — два разных вложения **[П]** |
| побайтово одинаковые копии | одна запись в хранилище + две ссылки | Legacy при дедупликации удаляет идентичные копии (`_move_attachment_files`, `controls_dedup.py:283-347`). В новой системе — дедупликация по `sha256` на уровне хранилища, ссылки сохраняются обе **[П]** |
| отсутствие файла | `attachment.missing = true` | Не «тихо пропускать»: блокирующий отчёт или явно принятое исключение (требование W07) |
| расширения | `mime_detected` + политика допустимых типов | Legacy: `.pdf/.png/.jpg/.jpeg` (`ATTACHMENT_ALLOWED_EXT`, 47) — только для скан-гарда новой записи; фактически в папках может лежать что угодно. При миграции переносить **все** файлы, тип определять по содержимому и помечать недопустимые для нового скан-гарда |

Проверка переноса: сверка `counts` (число путей в JSON = число строк `attachment` = число файлов в хранилище),
сверка SHA256 каждого файла, отдельный отчёт по отсутствующим.

## 7. Особые правила

### 7.1 UUID: пустые, дублирующиеся, пересечения локального и сетевого набора

- **Пустой `id` контроля.** В legacy лечится при чтении: `_heal_missing_ids` (182–212) берёт id из общего
  префикса папки вложений (`_attachments_prefix`, 169–179), иначе `uuid4()`, и **немедленно сохраняет файл**
  (102–110) **[З: M]**. Для миграции это неприемлемо (неповторимость): использовать детерминированный
  UUIDv5 от (`legacy_source`, SHA256 файла, индекс записи) и фиксировать пару «старый пустой → новый id» в manifest.
- **Дублирующийся `id`.** Внутри одного файла возможны (ручная правка/старый импорт). Legacy: `dedupe_controls`
  выполняет union по `id`, побеждает запись с большим `updated_at` (`controls_dedup.py:349-400`) **[К]**.
  В новой БД PK не позволяет: правило — объединить по алгоритму `merge_duplicate_group` (170–262) **только**
  по утверждённому плану, либо сохранить вторую запись с новым id и флагом `needs_review` **[Р]**.
- **Один id в локальном и сетевом наборе, разные данные.** Legacy решает конфликтом «последняя запись победила»
  (`merge_controls`, 1170–1199; naive `updated_at` трактуется как UTC, при равенстве — локальная версия) **[З: K]**.
  Миграция обязана: (1) не объединять автоматически по `updated_at` (требование W07 — локальная запись могла быть
  удалена из shared); (2) выводить такие пары в отчёт конфликтов с обеими версиями и решением из manifest.
- **Удалённые записи.** Tombstones в legacy нет: удалённый навсегда контроль, живой в shared, возвращается
  при следующем merge **[К]**. Миграция читает каждый источник отдельно и помечает происхождение
  (`legacy_source`), а «воскрешение» предотвращается решением владельца по каждому расхождению.

### 7.2 ФИО → `person_id`

Источники строк ФИО в legacy: `executors`, `controller`, `assignees` пунктов, `extra_people`, `hidden_people`,
ключи `person_roles`, `network_user`, а также `zonal_criminalists.json` (`Criminalist.name`, `id` — **int** 1..16)
и `DEFAULT_CONTROLLERS` (жёстко зашитый список из 2 ФИО, `controls_data.py:18`) **[К]**.

Единый справочник legacy (`get_all_people_names`, 388–416) строится как:
криминалисты + `DEFAULT_CONTROLLERS` + `extra_people` − `hidden_people`, **с дедупликацией по фамилии**
(второй однофамилец молча отбрасывается) **[З: I]**.

Предлагаемый алгоритм сопоставления при миграции **[П]**, ступени применяются по порядку, каждая фиксируется в отчёте:

| Ступень | Правило | Результат |
|---|---|---|
| 1 | Точное совпадение полной строки (после NFKC/пробелы/casefold) с `person.full_name` | `person_id` установлен, `match_kind='exact'` |
| 2 | Точное совпадение с `person.short_name` («Иванов И.И.») | `match_kind='short'` |
| 3 | Совпадение «фамилия + инициалы» с единственным кандидатом в справочнике | `match_kind='initials_unique'` |
| 4 | Совпадение фамилии при **единственном** человеке с такой фамилией | `match_kind='surname_unique'` |
| 5 | `name_matches` (`controls_models.py:89-117`: подстрока фамилии, похожесть ≥ 0.80) при единственном кандидате | `match_kind='fuzzy'` + **обязательное ручное подтверждение** |
| 6 | Совпадений нет или несколько | `person_id = NULL`, `needs_review = true`, строка в блокирующем отчёте |

**Однофамильцы.** `name_matches` даёт `True` для «Иванов Иван Иванович» ↔ «Иванов Пётр Сергеевич»
и даже для «Иванов И.И.» ↔ «Иванова Мария Петровна» (подстрока «иванов» входит в «иванова») **[З: A4/A5]**.
Поэтому:
- в рантайме новой системы `name_matches` **не используется** для прав доступа и для «свой/чужой» —
  только `person_id`;
- в миграции ступени 4–5 применяются только при единственном кандидате, иначе — отчёт;
- справочник людей новой системы **не** дедуплицирует по фамилии (исправление D-10);
- при необходимости различать однофамильцев добавляются необязательные поля `position`/`department` **[Р]**.

**Неизвестные роли и неизвестные люди.** Строка ФИО, которой нет ни в одном источнике справочника
(например, ушедший сотрудник или «голая» фамилия из Excel), создаёт `person` с `origin='legacy_unknown'`,
`is_active=false`, `needs_review=true`; назначение сохраняется (не теряется), но в UI помечается как
«не сопоставлено». Роли из `person_roles` переносятся дословно; отсутствие роли не означает «исполнитель»
автоматически — дефолт наследуется из источника (криминалист → `executor`, `DEFAULT_CONTROLLERS` → `controller`,
`extra_people` → `executor`, `controls_data.py:430-487`) **[К]**.

### 7.3 Даты против timestamps

| Поля | Legacy-тип | Цель | Комментарий |
|---|---|---|---|
| `receive_date`, `due_date`, `end_date`, `done_date`, `task.due_date`, `task.done_date`, `milestone.date` | строка `YYYY-MM-DD` (только строгий ISO парсится) | `date` | Без времени. Отображение `DD.MM.YYYY`. Нераспознанные строки → `NULL` + `legacy_raw` + отчёт |
| `created_at`, `updated_at`, `archived_at` | строка `datetime.now().isoformat()` — **naive, локальные часы** | `timestamptz` | Часовой пояс источника неизвестен; предложение — Europe/Moscow **[Р]**. В legacy сравнение naive-значений выполняется как UTC (`merge_controls`), из-за чего расхождение часов клиентов напрямую влияло на результат merge **[З: K]** |
| `notify_log`, `alarm_log` (значения) | `YYYY-MM-DD` / ISO datetime | `notification.shown_at timestamptz` | История показов; полнота не гарантируется (обрезка 30 дней) |
| `manifest.json` снапшотов | ISO + SHA256 | `backup_run` | Версия схемы, состав, размеры, хэши (`backup.py:115-139`) |

Правило **[П]**: все «сегодня/сейчас» в новой системе считает **сервер** в одном часовом поясе;
клиентские часы не участвуют ни в статусах, ни в конфликтах.

### 7.4 Порядок пунктов и дубликаты

- Порядок = индекс в JSON-массиве → `position`. Перетаскивания в legacy нет (иконка декоративна) **[К]**.
- Дубли `id` пунктов внутри контроля возможны **[З: M]** → см. §3.
- При объединении дублей контролей пункты сливаются «union по id, затем по (title, due_date, is_done)»
  (`merge_duplicate_group`, 200–240) **[К]**; тот же алгоритм применять в миграционном слиянии по плану.

### 7.5 Относительные пути вложений и одинаковые имена

См. §6. Дополнительно **[К]**: `attachment_abs`/`resolve_attachment` допускают, что путь уже содержит
префикс другого контроля (после «лечения» id или ручного переноса папок) — такие записи попадают в отчёт
«путь вложения не совпадает с id контроля» и связываются по manifest.

## 8. Проверки полноты mapping (для W07/W08)

| Проверка | Метод |
|---|---|
| Все 22 поля `Control` перенесены | сверка списка колонок `control` с §2 (22 + служебные) |
| Ни одна запись не потеряна | `count(JSON) == count(control)` по каждому источнику; отдельный подсчёт архивных |
| Ни одно значение не изменено молча | выборочная сверка 100 % полей для 5 % записей + полная сверка `legacy_raw` (JSON-эквивалентность) |
| Некорректные значения видны | отчёт по категориям: «дата не распознана», «тип не из enum», «bool как строка», «period_days не int», «пустой id», «дубль id», «неизвестное ФИО», «путь вложения не совпадает», «отсутствует файл», «неизвестное поле JSON» |
| Неизвестные поля сохранены | `legacy_raw` содержит исходный словарь записи (проверка на синтетическом файле с `custom_field`) |
| Люди не потеряны | `count(person) >= count(уникальных ФИО во всех источниках)`; каждая нераспознанная строка — в отчёте |
| Вложения не потеряны | сверка SHA256 всех файлов; отчёт по отсутствующим |
| Настройки со всех машин собраны | manifest с перечнем машин/файлов и их SHA256 |
| Миграция воспроизводима | повторный прогон на том же входе даёт тот же результат (никаких `uuid4()`/`now()` без manifest) |
