## 5. Основные выводы из кода (до пяти)

1. **Права и роли определяются вариантом сборки, а не учётной записью.** В admin-сборке значение
   `network_role="user"` не ограничивает ни просмотр, ни запись: кнопки «Добавить контроль», «Импорт Excel»,
   «Справочники» остаются доступны, а `_persist` пишет в общую папку (`controls_tab.py:478, 709-716,
   5152-5170`; подтверждено зондом тулбара). Пользователь с ролью `user` и пустым ФИО видит **все** контроли
   (`_visible_base`, 937; подтверждено зондом UI). Парольный шлюз отключён, а его хеш —
   `base64(sha256(соль|пароль))` с жёстко зашитой солью (`edition.py:538-571`). Переносить эту схему нельзя;
   права должны стать серверными.
2. **Идентичность людей — строка ФИО с фамильным совпадением.** `name_matches` (`controls_models.py:89-117`)
   даёт True для однофамильцев и даже для «Иванов» ↔ «Иванова» (подстрока), а единый справочник
   дедуплицирует людей **по фамилии**, молча теряя второго однофамильца (`controls_data.py:409-414`).
   Личные сроки и уведомления построены на этом же сопоставлении — значит в новой системе идентичность
   обязана быть по `person_id`, а `name_matches` может служить только инструментом миграции.
3. **Данные legacy не валидируются при чтении, а «лечение» меняет их на месте.** Пустой id заменяется новым
   UUID при каждом чтении (`_heal_missing_ids` предпочитает префикс папки вложений), неизвестные поля JSON
   теряются при первом же сохранении, `done: "yes"` остаётся истинной строкой, `period_days: "30"` — строкой,
   дата `01.05.2026` не парсится и превращает контроль в «Без срока» (подтверждено зондом M).
   Миграция обязана читать сырой JSON, сохранять `legacy_raw` и работать детерминированно.
4. **Синхронизация — это слияние «последняя запись победила» без следов удаления.** `merge_controls`
   (1170–1199) сравнивает naive-время как UTC, удалённые записи возвращаются из общей папки,
   lock-файлы имеют гонку и stale 10 минут, а при обновлении данных из сети открытая карточка закрывается
   **без сохранения** введённого текста (`_apply_pending_on_close`, 2401–2436). Новая система должна заменить
   это версионированием (`revision`/409), серверной БД и сохранением ввода.
5. **Браузерный потолок Win7 несовместим со стеком прототипа `src/`.** Chrome/Edge 109 — последние версии
   для Windows 7, Firefox 115 ESR — последний (обновления до марта 2027) **[В]**; Tailwind CSS v4 требует
   Chrome 111+/Safari 16.4+/Firefox 128+ **[В]**, а дефолтный `build.target` Vite 7 в релизных заметках
   соответствует Chrome/Edge 107, Firefox 104 (в действующей документации Vite тот же ключ уже chrome111/firefox114)
   **[В]**. Прототип в `src/` (React 19.2.3, Vite 7.2.4, Tailwind 4.1.17, `vite-plugin-singlefile`,
   target не задан) при этом описывает вкладку «Следственные отделы», а не «Контроли» (слово «контрол»
   в `src/App.tsx` не встречается). Значит основу фронтенда нужно собирать заново с явным браузерным минимумом.

## 8. Почему W01 нельзя начинать сейчас

1. **Нет подтверждённого сервера, ОС и PostgreSQL** (В-01…В-03). Этап W01 по определению
   (`03-stage-prompts.md`) завершается только подтверждением владельца на реальном Win7 по сетевому адресу;
   разворачивать негде.
2. **Неизвестен точный браузер Win7** (В-04). От него зависят `build.target`, список запрещённых API/CSS
   и сама осуществимость сборки. Потолок проверен по внешним источникам, но фактическая версия на рабочих
   машинах не подтверждена. План прямо требует: «Если нет сервера/браузера — STOP, не строить всё на догадке».
3. **Не утверждён один вариант интерфейса** (выбор владельца по `ui-outline.md` §9) — иначе возникнут
   параллельные редизайны, запрещённые заданием W00.
4. **Не приняты решения по правам user внутри карточки, периодичности и уведомлениям** (В-05, В-09, В-13) —
   без них W02/W03 будут строить правила на догадке.

Независимая часть обследования при этом завершена: документы готовы к ревью, открытые вопросы помечены
«ожидает решения», W00 **целиком принятым не объявляется**.
