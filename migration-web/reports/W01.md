### 1.1 Инцидент среды: история git сбрасывается между ходами

Песочница Arena пересоздаёт checkout между ходами: в начале этого хода `HEAD` снова указывал на базовый
`b5f24ab58c642fafb5cca616aa8b4e16d3a3de3f`, коммит W00 `8b25631…` локально отсутствовал
(`fatal: Not a valid commit name`), а семь документов W00 лежали в рабочем каталоге как неотслеживаемые файлы.

Восстановление выполнено без потери данных и без перезаписи истории:
1. `git fetch origin arena/01a0a90c-porayonka` → `FETCH_HEAD` = `8b25631d…`;
2. побайтовая сверка: `git hash-object` каждого из семи локальных файлов совпал с blob-SHA того же файла
   в `FETCH_HEAD` (вывод: `ИДЕНТИЧНО`);
3. копии сохранены в `/tmp/w00backup/` (страховка), неотслеживаемые дубликаты удалены;
4. `git merge --ff-only FETCH_HEAD` → fast-forward своей ветки до своего же опубликованного коммита.

`--force` не использовался, `main` не сливался и не менялся (`main` = `origin/main` по содержимому W00-ветки
не затрагивался; `origin/main` = `d2e48c4…`), чужие изменения не откатывались.
**Вывод для следующих этапов:** после каждого хода проверять `git log --oneline -3` и при расхождении
восстанавливать историю тем же способом (fetch → сверка hash-object → ff-only).

## 10. Требуемые измерения (протокол, выполняется после развёртывания стенда)

Параметры среды, фиксируемые до измерений: сервер (ОС, версия, CPU, RAM, диск, тип хранилища), PostgreSQL
(версия, настройки), клиент (ОС, модель ПК, CPU, RAM, разрешение, масштаб), браузер (название, точная версия,
разрядность), сеть (тип, задержка до сервера, наличие прокси), объём данных (число записей/вложений, SHA сборки),
время и дата прогона, имя проводившего.

| Метрика | Как измерять | Норма/ориентир | Повторы |
|---|---|---|---|
| Холодное открытие списка | Первый запрос после очистки кэша браузера до отрисовки первой страницы (50 строк); тайминг в браузере + серверный лог | ориентир из `04-acceptance-and-cutover.md`; уточняется по `V-03` | ≥ 30, p50/p95 |
| Поиск | Запрос с синтетическим термином по 10 000 записей до отрисовки результата | то же | ≥ 30, p50/p95 |
| Открытие карточки | Клик по строке → полная отрисовка карточки (включая метаданные вложений) | то же | ≥ 30, p50/p95 |
| Пагинация | Переход на страницу 2, 10, 200 (по 50 строк) | то же | ≥ 30, p50/p95 |
| Память | Память вкладки браузера после холодного открытия и после 200 переходов по страницам (утечка) | рост не более согласованного порога | 3 серии |
| Отзывчивость прокрутки | Прокрутка списка на 1 000 видимых строк: пропуски кадров/задержки (по инструментам браузера) | без видимых рывков; фиксируется число кадров | ≥ 10 |
| Серверная сторона | Время ответа API (p50/p95), загрузка CPU, потребление RAM процесса, число соединений | фиксируется как факт | ≥ 30 запросов |
| Файлы | Загрузка и скачивание синтетического PDF с кириллицей: время, совпадение SHA256, корректность имени | SHA256 совпадает, имя читается | ≥ 10 |

Правила: современная автоматическая проверка (актуальный браузер + HTTP-тесты) выполняется отдельно и
**не заменяет** ручную проверку на настоящем Win7; при отсутствии Win7-стенда статус — «ожидает проверки»,
а не «совместимо».

### 10.1 Черновик инструкции владельцу для ручной проверки с Win7

Выдаётся после развёртывания стенда по варианту A или C (сейчас выдавать нечего — стенда нет). Шаги:
1. На Win7-машине открыть браузер и зафиксировать версию («О программе»/`chrome://version`), разрешение и масштаб экрана.
2. Открыть адрес стенда `https://<имя стенда>/` (или `http://<ip>:<порт>/` до включения HTTPS).
3. Убедиться, что список открылся, в шапке видны счётчики и строка состояния связи.
4. Ввести синтетический поисковый термин, дождаться результата, отметить время «на глаз» и по секундомеру.
5. Перейти по 3–5 страницам по 50 строк, прокрутить список, отметить плавность.
6. Открыть карточку записи: проверить кириллицу в содержании, ФИО, датах и статусе.
7. Скачать приложенный синтетический PDF, открыть его, проверить кириллицу и имя файла.
8. Загрузить свой синтетический PDF с кириллическим именем, убедиться, что он сразу виден в карточке.
9. Записать: браузер и версию, RAM/разрешение, адрес стенда, дату/время, что получилось и что нет
   (сообщения об ошибках — дословно), приложить скриншоты списка и карточки.
10. Ничего из рабочих данных не загружать: только синтетические записи стенда.

## 12. Что разблокирует W01

Достаточно коротких письменных ответов (числа/да/нет/имена), реальные данные и сканы не нужны:

1. **B-01**: хост/адрес, ОС и версия, способ доступа, ответственный, есть ли интернет и право ставить пакеты/службу.
2. **B-02**: PostgreSQL — версия, кто предоставляет, способ развёртывания, где хранятся копии.
3. **B-03**: браузер Win7 (название, точная версия, разрядность), RAM и разрешение слабого ПК, масштаб, число машин.
4. **B-04**: какой вариант UI утверждён (по `ui-outline.md`) и подтверждение «без офлайн-редактирования».
5. **B-05**: сетевой доступ Win7-машин к стенду и возможность HTTPS.
6. **B-06**: если сервера пока нет — разрешить ли вариант B (стенд в песочнице) для функциональной части
   с сохранением статуса «ожидает проверки» по Win7.
7. **B-07/B-08**: выводы сравнения W00 (если существуют) и подтверждение имени ветки.

После получения пунктов 1–4 (и 5 для Win7-протокола) реализация W01 начинается в этом же сеансе без
дополнительных уточнений: последовательность команд и состав проекта уже подготовлены (§8, §9).
