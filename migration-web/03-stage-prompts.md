# Этапы W00–W09: задания исполнителям Arena

## Порядок

W00 → W01 → W02 → W03 → W04 → W05 → W06 → W07 → W08 → W09.

W00 — подтверждение требований; W01 — проверка платформы на Win7; W02–W07 — новая система; W08 — испытания и репетиция; W09 — пилот и переключение. Не начинать следующий этап, пока предыдущий не принят. Если агент не помещает этап в один сеанс, передаёт продолжение в той же ветке с честным статусом, а не выдаёт заглушки за результат.

Определи абсолютный корень checkout, проверь git status, ветку и базовый SHA, сообщи расхождения. Не трогай чужие изменения и рабочие данные.
>
> Новый код только в controls-web; отчёты и уточнения плана в migration-web. Старый porayonka-app и React-прототип src не менять без отдельного задания. Не переносить Flet, SMB-синхронизацию, локальные web-серверы и Win7 DLL. Сервис центральный, на Win7 только браузер. Находящийся в корне стек не менять. Новые инструменты устанавливать только в изолированном окружении новой системы после утверждения стека.
>
> До работы перечисли план и прочитай соответствующие legacy-источники. Следуй утверждённым решениям и контрактам предыдущих этапов. Не выдумывай недостающие бизнес-правила. Если блокирует неизвестный сервер, браузер, доступ или решение владельца — опиши блокер; не обозначай его выполненным.
>
> Данные для разработки синтетические. Не отправляй реальные JSON, сканы и ФИО во внешние сервисы. Не допускай публичного доступа к файлам и API. Все пользовательские тексты на русском. Не добавляй незапрошенные функции и тяжёлые UI-библиотеки.
>
> Реализуй полностью перечисленный объём без TODO вместо функций. Добавь автоматические тесты и выполни их, отдельно перечисли непроверенное. Верни ветку, SHA, diff-summary, команды и результаты, ограничения и отчёт migration-web/reports/WNN.md. Не сливай main, не принимай свой этап и не переключай production. Обнови migration-web/reports/SESSION-HANDOFF.md. Не переходи к следующему этапу сам и не делай искусственных keep-alive циклов. Если платформа закрывает сессию автоматически или требует завершения для передачи результата, предупреди — не обещай невозможного.

## W00 — паспорт проекта и окончательные решения

**Цель:** до кода устранить вопросы, из-за которых переезд может снова превратиться в бесконечные переделки.

**Вход:** текущий legacy, весь пакет плана, ответы владельца. Допустимы только документы в migration-web.

**Задание:**

1. Снять карту поведения по R01–R24: источник/функция, вход, результат, пограничный случай. Изучить не только модель, но сохранение/исполнение/архив/фильтры в UI и Excel. Отделить используемую карточку от мёртвого кода.
2. Для каждого поля составить mapping legacy → предлагаемая схема, включая настройки, личности, timestamps, некорректные значения. Описать правила восстановления и периодичности, видимость пунктов и массовые операции.
3. Согласовать с владельцем сервер, ОС, ответственного за сервер, браузер Win7, RAM/разрешение, число одновременных пользователей, объём записей/файлов, сеть и возможность HTTPS. Реальные данные в Arena не запрашивать.
4. Отдельно получить решения: без офлайн-редактирования; ограничения уведомлений; вход по аккаунту; границы доступа внутри карточки; кто администрирует справочник людей после отделения от зональных.
5. Утвердить стек из 01-architecture или представить одну обоснованную альтернативу при блокере. Не начинать реализацию альтернативы без согласования.
6. Подготовить эскизы списка, карточки, импорта и ошибок. Дизайн: читаемая тёмная тема без тяжёлых эффектов, компактная таблица, удобная прокрутка, видимые сроки и статус связи. Минимальная целевая ширина определяется реальным Win7-монитором. Владелец выбирает один вариант; не делать несколько редизайнов параллельно.
7. Создать `migration-web/decisions.md`, `migration-web/field-mapping.md`, `migration-web/requirements-matrix.md` и отчёт W00 с нерешёнными вопросами. Требованиям назначить ID и этап проверки.

**Проверки:** полнота mapping всех полей моделей; у каждого R есть критерий; отдельно перечислены намеренные отличия. Значения «неизвестно» допустимы в черновике, но блокирующие неизвестные не допускаются при принятии.

**Готово когда:** владелец принял условия работы, сервер/браузер определены, стек и макет утверждены. Если нет сервера/браузера — STOP, не строить всё на догадке.

## W01 — минимальная работающая версия и испытание Win7

**Цель:** доказать пригодность платформы до переноса функций.

**Вход:** принятый W00. Разрешены controls-web и migration-web.

**Задание:**

1. Создать независимый проект с backend/frontend/tests/docs, AGENTS.md, README, отдельными lock/requirements и настройками без секретов. Зафиксировать версии, поддерживаемую серверную ОС и браузерный минимум. Записать почему выбранные версии пригодны.
2. Минимальный сквозной путь: сервер → PostgreSQL с синтетическими контролями → постраничный список в браузере → карточка чтения. Это технический стенд, не рабочая система; доступ ограничить тестовой сетью, не загружать рабочие данные до W02.
3. Сборка фронтенда для точной версии целевого браузера. Никаких CDN, внешних шрифтов и обязательных новых browser API. Поднять собранный интерфейс, не только dev-режим.
4. Пробный выбор/загрузка/скачивание синтетического PDF с кириллицей. Временные endpoints стенда не оставить публичными в принятом W02.
5. Добавить воспроизводимое наполнение 10 000 синтетических записей, страницы по 50 и тест поиска. Это исходный испытательный объём, W00 может увеличить его по реальной нагрузке.
6. Настроить первичный CI: установка из lock, backend-тесты, frontend-проверки типов, production build, smoke HTTP; секреты отсутствуют.
7. Дать владельцу короткую инструкцию проверки с реального Win7 по сетевому адресу: открыть, искать, прокручивать, открыть карточку, загрузить/скачать PDF, убедиться в кириллице.

**Проверки:** современный браузер автоматически + настоящий Win7 вручную. Измерить холодное открытие, поиск, карточку, память и отзывчивость прокрутки; приложить сервер/клиент/браузер/объём/сетевые условия. Ориентиры из 04-acceptance-and-cutover уточнять только явным решением.

**Готово когда:** владелец подтвердил скорость и внешний вид на Win7, браузер не даёт ошибок, сервер запускается по воспроизводимой инструкции. Без реального Win7 остаётся «ожидает проверки», дальнейший полный перенос не разрешён.

## W02 — база, аккаунты, права и контракт API

**Цель:** безопасный фундамент; никакой бизнес-логики в одном UI-файле.

**Вход:** W01 и field-mapping. Разрешены controls-web и migration-web.

**Задание:**

1. Реализовать схему и версионируемые миграции: люди, аккаунты, роли, контроли, назначения, пункты, milestones, метаданные файлов, настройки, аудит. UUID legacy сохраняются. Валидация/индексы/foreign keys согласно mapping.
2. Определить и документировать HTTP-контракты: вход/выход/current-user, список/карточка/операции, справочники, файлы, импорт/экспорт, проверка обновлений. Реализовать операции этого этапа; будущие endpoints описать, но не делать фиктивный успешный ответ.
3. Ввести серверные cookie-сессии, CSRF, безопасные пароли, ограничение попыток, создание первого администратора штатной командой без пароля в Git, отключение пользователя и завершение сессий.
4. Единая политика доступа применяется к ORM-запросам и отдельным объектам. Обычный пользователь не выбирает свою личность/роль запросом. Сопоставление по person_id, не похожей фамилии.
5. Зафиксировать revision/409, формат ошибок и ключи идемпотентности, пагинацию и ограничение размера страницы, сортировку со стабильным tie-breaker, часовой пояс. Применить к уже существующим операциям.
6. Закрыть или убрать все тестовые endpoints W01. Настроить same-origin, безопасные заголовки, production debug-off и логи без секретов. Добавить health/readiness без утечки конфигурации.

**Проверки:** чистая установка БД и повтор миграций; вход/выход/неверный пароль/заблокированный аккаунт; CSRF; user не получает чужую карточку прямым запросом; недопустимые назначения/параметры не обходят права; тесты на реальном PostgreSQL.

**Готово когда:** приняты схема и контракт, безопасность не зависит от скрытых кнопок, воспроизводимы создание БД и администратора.

## W03 — правила контролей и серверные операции

**Цель:** сохранить правильные правила старой программы без Flet.

**Вход:** W02, матрица R01–R12/R19/R23/R24 и подтверждённые решения W00.

**Задание:**

1. Перенести чистую логику дат, пунктов, milestones, статусов и индивидуальных сроков в отдельные модули без импорта legacy runtime. Если копируется чистая функция, добавить тест и указать источник.
2. Реализовать создание/изменение/исполнение пунктов и контроля, архив/восстановление/окончательное удаление, подтверждённые массовые действия. Скан-гард серверный; полноценная загрузка появится W04, до неё тесты используют внутреннюю фикстуру готового файла, не публичный обход запрета.
3. Реализовать справочники/роли людей, фильтры/сортировки/счётчики. Список/экспорт в будущем должны использовать общую политику выборки и расчётов.
4. Транзакция, revision и аудит для каждой изменяющей операции. Два администратора с одной исходной версией: только один успешен, второму конфликт. Повтор запроса создания не дублирует контроль.
5. Дубликаты номера диагностировать; не применять автоматическое слияние в обычном сохранении. Разрушительное объединение только по явно принятому плану.

**Проверки:** табличные тесты с фиксированными датами для R01–R12; частичные/все исполненные пункты, отсутствие дат, end_date вчера/сегодня/завтра, границы месяца/года, все роли. Конкурентные HTTP-запросы и rollback при исключении, права на массовые операции. Новые правила не зависят от часов клиента.

**Готово когда:** серверная матрица закрыта тестами, конфликт не теряет данные, новые контроли без скана нельзя создать через API.

## W04 — рабочий интерфейс и вложения

**Цель:** пользователь выполняет основной рабочий цикл в браузере.

**Вход:** W03, утверждённый макет и файловый контракт.

**Задание:**

1. Реализовать список/фильтры/счётчики/постраничность, карточку, пункты, milestones, справочники, исполнение и архив. Администратор и user получают различный набор действий; сервер остаётся решающим.
2. Сохранять фильтры и позицию при возврате; показывать загрузку, пустой список, ошибку, недоступный сервер. Нет вложенных диалогов выбора людей. Даты можно ввести клавиатурой и очистить; длинный текст/ФИО и маленький экран не ломают форму.
3. Реализовать файлы: временная загрузка с прогрессом, ограничение размера/типа, проверка содержимого, публикация перед связью с контролем, компенсация сбоев, очистка сирот. Владелец upload и контроль проверяются сервером.
4. Готовое вложение сразу видно. Двойной клик/повтор ответа не создают копии. Прерванный upload не считается сканом. Чужой upload нельзя присвоить. Старые записи без сканов редактируются.
5. Скачивание защищено; кириллица/одноимённые разные файлы/безопасный Content-Disposition. UI различает просмотр серверной копии и скачивание, не притворяется, что знает локальную папку пользователя.
6. При конфликте формы сохранить введённые значения, показать свежую версию и предложить заново применить правки. При переходе с несохранённой формой предупредить. Не размещать чувствительный черновик в постоянном browser storage по умолчанию.

**Проверки:** браузерный E2E «войти → PDF → новый контроль → пункт → исполнение → архив → восстановление»; user read-only и прямые запросы; отмена, обрыв, повторы, потеря сети, два админа, два открытых контроля. Загрузка 1/20/50 МБ в рамках согласованного лимита. Плохой путь/подмена типа/чужой ID не проходят. Повторная проверка Win7.

**Готово когда:** владелец выполняет основной цикл на тестовом Win7 без помощи разработчика; тесты файлов и конфликтов проходят. Excel/уведомления пока явно помечены отсутствующими, не имитируются.

## W05 — Excel и безопасный импорт

**Цель:** сохранить рабочий обмен таблицами и не потерять данные при повторном импорте.

**Вход:** W04, R15–R19, legacy exporter и примеры из тестов.

**Задание:**

1. Перенести два режима экспорта и round-trip, включая H/I, персональные сроки и подсветку. Контракт выборки един со списком. Скрытые листы не обходят права.
2. Реализовать загрузку Excel → анализ → preview категорий → подтверждение → применение. План имеет владельца, срок действия, хэш файла и версии затрагиваемых записей. Изменившиеся записи вызывают пересчёт/конфликт, не молчаливое перетирание.
3. Сохранить существующие ID, attachments, богатые поля, видимые колонки поверх скрытых; распознавание пунктов по R18. Дедуп не объединяет пустые номера, неоднозначности в отчёте. Excel освобождён от скан-гарда, обычный API этим не обойти.
4. Перед применением использовать проверяемый snapshot БД+файлов (первичная реализация механизма восстановления, расширяемая W07). Если backup не удался — применение не начинается. Импорт транзакционный, повтор подтверждения идемпотентен.
5. Лимиты XLSX, защита от чрезмерного распакованного объёма и формул из пользовательского текста в экспорте; ошибки строк без утечки чужих данных. Экспорт доступен только авторизованному получателю.

**Проверки:** export→import без изменений; изменение видимого листа; конфликты; отсутствие скана; неверные даты; богатые поля; повтор; user + admin с фильтром; большие таблицы; повреждённый XLSX; восстановление snapshot на отдельной БД.

**Готово когда:** контрольные синтетические таблицы сравниваются автоматически, повтор импорта не плодит записи, предимпортный backup реально восстанавливается.

## W06 — обновления и напоминания

**Цель:** понятная свежесть данных вместо старого неявного merge.

**Вход:** W05 и принятое ограничение фоновых уведомлений.

**Задание:**

1. Реализовать авторизованный лёгкий polling по серверной версии/курсору изменений. Список событий не раскрывает чужих ID/названий. Права перепроверяются после изменения назначений.
2. Новые, изменённые, архивные, удалённые записи отражаются без F5. При отзыве доступа карточка и данные очищаются. Устаревший курсор приводит к безопасному обновлению доступной выборки.
3. Не пересоздавать таблицу целиком и не затирать форму, фокус, поиск или прокрутку. Для изменившейся открытой карточки — индикатор новой версии, не автоматическая перезапись.
4. Индикация связи и последнего успешного обмена; backoff и восстановление после ошибок/перезапуска сервера; при возврате фокуса проверка актуальности. Одна цепочка опроса на вкладку, без накопления обработчиков.
5. Серверный журнал уведомлений, интервалы user 2 часа/admin 24 часа и правила только своих overdue/today; сценарии новых/изменённых из W00. Атомарное подтверждение показанного уведомления уменьшает дубли нескольких вкладок. Не считать напоминание показанным только от формирования серверного списка.
6. Звук после явного действия пользователя, настройка отключения; закрытый/уснувший браузер не обещает доставку. Доступный журнал показывает пропущенное после возвращения.

**Проверки:** два браузера/несколько вкладок; смена назначений; удаление/архив; отключение сети/рестарт сервера; неверные часы клиента; переход полуночи; чужой просроченный пункт; интервалы; длительный сеанс без роста обработчиков и памяти. Win7 с открытой и фоновой вкладкой проверяется отдельно.

**Готово когда:** владелец видит, когда данные свежие и когда сохранение не произошло; обновления не теряют ввод; ограничения напоминаний отображены честно.

## W07 — перенос legacy и эксплуатационная готовность

**Цель:** безопасно перенести данные и подготовить восстановление/обновление сервера.

**Вход:** W06, mapping, сохранённые legacy-копии (на Arena только синтетические).

**Задание:**

1. Реализовать отдельную миграционную команду dry-run/apply/verify. Источники только read-only копии shared и нужных локальных кэшей с происхождением и SHA256. Не объединять всё автоматически по updated_at: локальная запись могла быть удалена из shared.
2. Вывести конфликты версий/ID/номеров/ФИО/файлов/дат и unknown-поля. Подготовить детерминированный manifest решений. Применение только утверждённого плана в пустую/специально подготовленную БД; повтор не дублирует сущности.
3. Перенести все поля, людей и файлы, сохранить ID и исходные значения. Для одинаковых имён разных файлов не потерять ни один. Сверка counts по категориям, ID, назначений, дат, архивов, хэшей вложений. Отсутствующие файлы — явный блокирующий отчёт или отдельно принятое исключение.
4. Реализовать согласованный backup БД+файлов+manifest схемы/версий/хэшей. Резервирование минимум ежедневно и до миграции/обновления/опасного импорта; retention исходно 30 успешных суточных копий. Частичный сбой не помечается успехом. Копия вне основного диска по согласованной инфраструктуре.
5. Восстановление на отдельном экземпляре, проверка входа/данных/файлов. Конкурентные сохранения/удаления во время backup не нарушают согласованность: документировать maintenance-window или snapshot-стратегию.
6. Подготовить воспроизводимые install/start/stop/upgrade/rollback под выбранную серверную ОС, службу автозапуска, HTTPS, firewall, права каталогов, журналы и ротацию, контроль свободного диска, readiness. Ни Python dev-server, ни запуск под администратором ОС по умолчанию не являются production-планом.
7. Краткая инструкция администратору: где адрес, как выдать аккаунт, проверить backup, перезапустить и вызвать ответственного. Секреты передавать защищённо вне репозитория.

**Проверки:** повтор миграции; повреждённый/пустой источник; коллизии; path traversal в legacy-пути; недоступный файл; обрыв и повтор; нехватка места; restore после уничтожения тестовой БД; обновление с предыдущей схемы; backup при активных клиентах либо доказанная блокировка записи.

**Готово когда:** миграция на синтетических наборах воспроизводима, backup реально восстановлен, production-развёртывание повторено на чистом стенде. Реальные источники пока не переключаются.

## W08 — независимая приёмка и репетиция

**Цель:** до рабочего запуска найти регрессии и подтвердить готовность.

**Вход:** W07. Желателен независимый агент-аудитор, не автор основного кода.

**Задание:**

1. Проверить каждый R и этап с привязкой к тесту/результату. Запустить весь новый контур с чистой БД и production-сборкой, не доверять прежним отчётам.
2. Аудит доступа: IDOR, список/счётчики/экспорт/скрытые листы/файлы/курсоры, CSRF, XSS, загрузки, лимиты входа, сессии, утечки в логах, секреты и зависимости. Не тестировать атаки против рабочего сервера.
3. Конкурентная нагрузка: исходно 5 администраторов и 20 читающих пользователей, 10 000 записей; согласовать с W00. Уничтожение соединения после commit, повторы запросов, одновременные edits/import, обрыв загрузки, рестарт, backup/restore.
4. Производительность и долговременный сеанс по 04-acceptance-and-cutover; без нового большого редизайна. Найденные дефекты оформить с воспроизведением и severity; исправления отдельными коммитами, повторять соответствующий контур.
5. Подготовить пакет для владельца: короткие ручные сценарии Win7 и современного ПК. Оркестратор организует локальную репетицию на защищённой копии настоящих данных; в репозиторий возвращаются только обезличенные итоги сверки.
6. Провести репетицию переключения и отката с измерением времени, включая запрет двух источников записи. Согласовать допустимую потерю данных/время восстановления и момент no-go.

**Проверки:** все из 04; Win7 не заменять современным headless Chromium. Важно проверить успешный restore, не только создание архива.

**Готово когда:** нет открытых дефектов потери данных/доступа/блокировки основных сценариев; все исключения письменно приняты владельцем; миграционная сверка и ручной Win7-протокол подписаны. Иначе W09 запрещён.

## W09 — пилот и управляемое переключение

**Цель:** перейти на новую систему без двойного ведения и потери правок.

**Вход:** W08, решение владельца, выбранное окно и ответственный. Агент готовит инструменты/инструкции, не выполняет production-операции самостоятельно.

**Задание:**

1. Зафиксировать конкретные релизные SHA, версии схемы/зависимостей, адрес, ответственных, окно запрета записи, backup и критерии отката.
2. Пилот на копии: небольшая группа, реальные рабочие сценарии без записи в production legacy. Подтвердить удобство; изменения пилота не считаются рабочими и не смешиваются автоматически с финальным переносом.
3. Выполнить локально утверждённый runbook: остановить запись контролей в legacy на всех компьютерах, собрать финальные кэши, сделать и проверить backup, dry-run/решения/apply/verify, открыть новую систему. Отделы/зональные могут оставаться в legacy, но запись старых контролей должна быть реально заблокирована согласованным способом.
4. Выдать аккаунты и ярлыки URL вместо четырёх установщиков. Проверить HTTPS на Win7, права, файлы, поиск, Excel, изменения на втором ПК и первую рабочую резервную копию.
5. Наблюдение не менее пяти рабочих дней (либо согласованный срок): ошибки, скорость, успешность backup, обращения пользователей. Принять решение о завершении пилота; не удалять legacy-архив и исходные копии сразу.
6. Подготовить передачу следующему оркестратору/администратору: принятый релиз, что где работает, команды проверок, резервные копии, нерешённые некритичные вопросы и отдельный будущий backlog. Перенос зональных/отделов не включать незаметно.

**Откат:** до первой новой рабочей записи можно вернуться к замороженной legacy-копии. После новых записей простое восстановление старого JSON теряет работу: остановить обе системы, сохранить новую БД/файлы/аудит, выполнить заранее испытанную обратную выгрузку и сверку либо согласованное ручное перенесение новых изменений. До такого плана и согласия владельца legacy-запись не открывать.

**Готово когда:** владелец подтвердил работу, backup/restore проверен, старые контроли не принимают новые правки, назначен ответственный. Финальное принятие только оркестратором и владельцем.
