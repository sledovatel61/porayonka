# Правила переезда и передачи работы

## 1. Роли и границы

Владелец выбрал браузерную версию. Оркестратор планирует, пишет задания, проверяет и внедряет результаты Arena. Самостоятельная реализация кода оркестратором не входит в согласованный порядок. Эта сессия создаёт только документы.

Владелец не разработчик. Ему сообщать коротко: что готово, что он должен проверить, есть ли риск, какое решение требуется. Подробные команды и доказательства хранить в репозитории.

Новая программа создаётся отдельно, в будущем каталоге `controls-web` в корне репозитория. Старые `porayonka-app`, `src`, сборки и данные не заменять. Старый `src` — отдельный React-прототип, не готовая новая система. Никакого импорта Flet или запуска старой программы из нового сервера.

Правила корневого AGENTS.md продолжают действовать для legacy. Версию Flet и старые requirements не менять. Новые зависимости разрешать и фиксировать отдельно после W00. После создания `controls-web` агент W01 добавляет туда AGENTS.md с новыми правилами: инструкции из этой папки автоматически не распространяются на соседний каталог.

## 2. Старт каждого оркестратора

1. Читать README, все пять номерных документов и корневой AGENTS.md.
2. Получить git status и последние коммиты. Не откатывать незакоммиченные изменения владельца. Использовать отдельный worktree/клон для проверки агентских веток.
3. Проверить фактическую ветку и SHA. Записи агентов «всё прошло» не считать доказательством.
4. Найти первый НЕпринятый этап в `05-status.md`; проверить зависимости.
5. Перед выдачей задания записать исходный SHA и допустимые файлы. Абсолютный корень репозитория определить на машине агента; локальные пути владельца туда не переносить.
6. Спросить только действительно блокирующие сведения из W00. Не придумывать сервер, браузер или доступы.

## 3. Выдача задания Arena

Передать общий промпт из `03-stage-prompts.md` плюс полный блок нужного этапа. Агент обязан прочитать весь пакет, а не только свой блок. Ветку назвать `arena/web-wNN-<topic>` либо использовать выданную Arena ветку и сообщить её точное имя. Указать базовый SHA.

Один агент выполняет один назначенный этап за раз; это НЕ означает новую coding-сессию на каждый этап. Для первого W00 владелец назначил конкурс: три агента получают одинаковое задание и одинаковый базовый SHA в изолированных ветках/checkout. Они делают полную одинаковую работу, не делят её на части. После сравнения выбирается один победитель; последующие этапы выполняются в его существующей coding-сессии. Не выдавать несколько параллельных задач, меняющих общую модель, миграции, авторизацию или контракт API. Внедрение — последовательно.

### Сохранение coding-сессии — обязательное правило

- После каждого этапа агент передаёт промежуточный результат на проверку и ждёт следующего сообщения В ТОЙ ЖЕ coding-сессии. Не инициирует finish/close/end-session, архивирование, удаление workspace/ветки или новую сессию. Обычное завершение сообщения не должно трактоваться как разрешение закрыть сессию.
- Оркестратор не закрывает три конкурсные сессии до проверки результатов и выбора победителя. Сессию победителя сохраняет между этапами и исправлениями; не предлагает запускать новый конкурс без причины.
- Правило явно повторяется в каждом следующем промпте. Агент не начинает следующий этап сам, не выполняет бесконечный цикл ожидания и не расходует инструменты ради искусственного удержания сессии.
- Агент сообщает доступный идентификатор/ссылку сессии (если не видит — честно указывает это), ветку, SHA и сохраняет `migration-web/reports/SESSION-HANDOFF.md`: выполненное, проверки, блокеры, решения и следующий разрешённый шаг. Ссылка на сессию не должна содержать секретных токенов.
- Платформенное автоматическое закрытие/таймаут агент гарантированно предотвратить не может. Если Arena требует завершить сессию для выдачи результата или использует такой режим, сначала предупредить владельца. Не утверждать, что сессия сохранена, если это не проверено в интерфейсе Arena. Отключение автозавершения, если доступно, выполняет владелец.
- Смена модели оркестратора в этом чате не означает смену coding-сессии исполнителя. Следующий оркестратор сначала читает статус и handoff победителя.

Никаких секретов, настоящих ФИО, рабочих JSON, сканов, сетевых паролей и резервных копий в GitHub/Arena. Тестовые данные синтетические. Обезличивание должно охватывать текст документов, имена файлов и метаданные. Реальную миграцию выполняют локально уполномоченные лица.

## 4. Что должен вернуть агент

- Ветка, исходный и конечный SHA; коммиты не должны включать чужие файлы.
- Перечень сделанного и известные ограничения.
- Изменённые файлы, команды запуска и проверки.
- Фактические результаты с кодами возврата; отдельно skipped и не проверенное.
- Доказательства критериев своего этапа; скриншоты на синтетических данных для UI.
- Изменения схемы и инструкция отката, если применимо.
- Отчёт `migration-web/reports/WNN.md` и предложение обновления статуса. Создать reports при первом этапе.

Агент не объявляет этап принятым, не сливает main и не переключает рабочую систему.

## 5. Приёмка оркестратором

Проверить diff, отсутствие секретов и непрошеных изменений. В чистом окружении установить закреплённые зависимости и повторить тесты этапа плюс предыдущих зависимых этапов. Новое хранилище тестировать на PostgreSQL, не подменять SQLite. Проверить реальные HTTP-запросы и браузер, а не только заглушки компонентов.

Проверять особенно: пользователь не может получить чужие данные по прямой ссылке; конкурентное сохранение не теряет правки; вложение действительно существует; повтор запроса не дублирует данные; ошибка не показывается как успех.

Браузерная автоматизация на современной машине НЕ подтверждает совместимость с Win7. Без ручного протокола Win7 этап W01 не закрывать. Если машины нет, статус «ожидает проверки», а не «готово».

Если затронут legacy — выполнить обязательный контур корневого AGENTS.md, включая три stress-прогона после правок синхронизации. При изолированной новой разработке достаточно нового контура и проверки отсутствия legacy-diff; не запускать старую программу против живого APPDATA только ради формальности.

Принимать только после выполнения критериев. Иначе выдать короткое задание на исправление этого этапа, не маскировать долг новым этапом. После принятия внести SHA, проверки и решения в `05-status.md`.

## 6. Управление решениями

Смена стека, схемы доступа, правил сроков, офлайн-поведения, браузерного минимума или границ переноса требует решения владельца и записи в журнале `05-status.md`. Агенту запрещено молча «улучшать» правила.

При расхождении документа с кодом — зафиксировать пример и выбрать поведение явно. Старый код является источником фактического поведения, но старые баги не становятся требованиями автоматически.

Никаких production-изменений без W09. До переключения старая программа — единственный источник рабочих правок. После переключения — новая. Двустороннюю синхронизацию двух систем не создавать.
