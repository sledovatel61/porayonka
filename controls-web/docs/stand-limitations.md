# Ограничения стенда W01 (читать перед использованием результатов)

## Что этот стенд доказывает

1. Сквозной путь работает: HTTP → FastAPI → **настоящий PostgreSQL 16.14** → постраничный список (50 строк)
   → карточка чтения.
2. 10 000 синтетических записей наполняются воспроизводимо (seed 20260917, digest сверяется с БД).
3. Пагинация не теряет и не повторяет записи: полный проход по 200 страницам даёт ровно 10 000 уникальных id.
4. Поиск по кириллице работает, спецсимволы LIKE экранируются.
5. Синтетический PDF с кириллицей генерируется, загружается, скачивается побайтово идентично,
   имя файла с кириллицей сохраняется и корректно передаётся в заголовке (RFC 5987).
6. Production-сборка фронтенда обслуживается **с того же origin**, внешних ресурсов нет.
7. В сборке отсутствуют API и CSS-возможности новее согласованного порога (проверяется тестом).
8. Серверные времена измерены: 30 повторов, p50/p95 (см. `measurements-w01-sandbox.md`).

## Чего этот стенд НЕ доказывает

| Ограничение | Почему важно |
|---|---|
| **Win7 не проверялся** | Стенд поднят в песочнице Arena; доступа с реальной Win7-машины нет. Статус совместимости — «ожидает проверки» |
| **Это не целевой сервер** | Песочница: 2 ядра, ~3.9 ГБ RAM, эфемерный диск. Производительность целевого сервера не измерена |
| **PostgreSQL из npm-пакета** | В песочнице недоступны apt-зеркала Debian (http и https) и Docker, поэтому взят `@embedded-postgres/linux-x64` (PostgreSQL 16.14). На сервере нужен PostgreSQL из пакета ОС; приложение проверено на 16.x и не использует версионно-специфичные возможности (требуется ≥ 14) |
| **Нет HTTPS** | Локальный стенд работает по HTTP. TLS/сертификаты, cookie-флаги `Secure`, HSTS — задача W07 |
| **Нет авторизации** | Роль, личность, права доступа не реализованы (W02+). Все записи видны всем, кто открыл стенд |
| **Нет редактирования** | Только чтение; бизнес-операции, офлайн-режим, импорт Excel, архив, уведомления, polling — не реализованы (W02+) |
| **Временные endpoints** | `/api/w01-test/*` (загрузка/скачивание PDF, генератор примера) — временные; должны быть удалены или закрыты до передачи W02. Флаг `CONTROLS_WEB_ENABLE_TEST_ENDPOINTS=0` отключает их вместе с `/api/docs` и `/api/openapi.json` |
| **Один процесс без пула соединений** | Соединение с БД создаётся на запрос. Пул, число работников и systemd-служба — W07 |
| **Нет миграций схемы** | Схема применяется идемпотентным `schema.sql`. Инструмент миграций выбирается в W02 |
| **Песочница сбрасывается** | Между ходами сессии каталоги `.venv`, `node_modules`, `dist`, `.pgdata` не сохраняются: стенд разворачивается заново скриптом `scripts/provision_stand.sh`. Источник истины — ветка git |
| **Данные синтетические** | Реальные контроли, сканы, ФИО, входящие номера и UNC-адреса в стенд не загружались и не могут быть загружены |

## Найденные при подъёме стенда дефекты (исправлены)

1. **Кириллица в заголовке `Content-Disposition`** приводила к 500: starlette кодирует заголовки в latin-1.
   Исправлено percent-encoding по RFC 5987. Правило для W02+: любые не-ASCII значения в HTTP-заголовках
   только в percent-encoded виде (имена файлов, темы писем, названия).
2. **Доверие к заявленному `Content-Type`** при загрузке: файл с типом `application/pdf`, но без сигнатуры
   `%PDF` принимался. Добавлена проверка сигнатуры → 415. Для W02+ это означает: тип вложения
   определять по содержимому, а не по заголовку клиента.
3. **HEAD-запросы к API** перехватывались статическим mount и возвращали 404 — внешний мониторинг
   получал ложный отказ. Для `/api/health` HEAD разрешён явно; для остальных маршрутов поведение
   задокументировано (мониторинг должен использовать GET).

## Наблюдения по производительности (требуют решения в W02/W03)

| Наблюдение | Факт (песочница, 10 000 записей) | Что делать |
|---|---|---|
| Глубокая пагинация через OFFSET | страница 1: p50 ≈ 8 мс; страница 100: ≈ 40 мс; страница 200: ≈ 76 мс | При росте объёма перейти на keyset-пагинацию (`WHERE (receive_date, incoming_number, id) < (...)`) — решение W03 |
| Поиск `ILIKE '%термин%'` по 6 колонкам | p50 ≈ 60–150 мс, последовательное сканирование | Индекс `pg_trgm` (GIN) или полнотекстовый поиск; проверить доступность расширения на целевом сервере — W02/W03 |
| Соединение с БД на каждый запрос | ~1–3 мс накладных | Пул соединений (`psycopg_pool`) — W07 |
| Сводные счётчики одним запросом | p50 ≈ 11 мс | Кэширование или материализованные счётчики при росте объёма — W03 |
