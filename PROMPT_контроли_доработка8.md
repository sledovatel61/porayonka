### БАГ 1. «Прочие» содержит действующих сотрудников

**Симптом:** Макаренко Р.А. (и, видимо, другие реальные сотрудники вроде Ченакал Ю.А., Кудрявцев В.А., Толстолуцкий С.А.) попадают в «Прочие», хотя должны быть в списке фильтра «Исполнители».

**Причина:** канонический справочник `get_controller_names()` = 16 криминалистов + Потемкин + Чашин. Он не включает всех людей, которые реально встречаются в данных как исполнители/ответственные.

**Что сделать:**
1. Проанализировать реальные данные пользователя (`%APPDATA%\porayonka\controls.json`) и составить полный список ФИО, которые встречаются в `executors`, `assignees`, `controller`.
2. Расширить канонический справочник исполнителей/контролёров так, чтобы действующие сотрудники (Макаренко, Ченакал, Кудрявцев, Толстолуцкий и др.) попадали в фильтр как отдельные пункты, а не в «Прочие».
3. Варианты реализации на выбор:
   - **Вариант A (предпочтительный):** сделать канонический справочник редактируемым через настройки (добавить/удалить ФИО), хранить в `controls_settings.json`. По умолчанию — 16 криминалистов + Потемкин + Чашин + автоматически добавленные distinct-ФИО из данных (сгруппированные по фамилии).
   - **Вариант B:** автоматически строить канонический список из всех distinct-ФИО в данных, кластеризуя по фамилии (fuzzy) — тогда «Прочие» почти всегда пустое, а фильтр содержит всех реальных людей.
   - **Вариант C:** оставить текущий справочник, но добавить недостающих людей в дефолтный список (не гибко, но быстро).
4. Рекомендуется вариант A или B, чтобы при появлении новых сотрудников не править код.
5. Проверить: Макаренко, Ченакал, Кудрявцев, Толстолуцкий и другие реальные исполнители видны в фильтре «Исполнители» как отдельные пункты, а не в «Прочие». «Прочие» должен содержать только действительно мусорные/неопознанные записи.

### БАГ 2. Кластеризация инициаторов выглядит странно

**Симптом:** в фильтре «Инициаторы» видны записи вроде «ГУК СК ГУК ЮФО» (несколько инициаторов склеены в один пункт), «ГСУ ГУК» и т.п. Это выглядит как ошибка кластеризации или отображения.

**Что сделать:**
1. Проверить логику `canonical_initiator_group()` и `initiator_filter_options()`.
2. Убедиться, что каждый пункт фильтра — это осмысленный канонический инициатор (например, «ГУК», «СУ», «ГУК ЮФО», «СК РФ», «ПСК», «ОКРИМ»), а не склейка нескольких.
3. Если инициатор в данных записан как «ГУК СК, ГУК ЮФО» — это может быть два разных инициатора или один составной. Решить: либо разбивать на отдельные каноны, либо оставлять как есть, но отображать понятно.
4. Проверить на реальных данных: фильтр должен быть коротким, понятным, без странных склеек.

### БАГ 3. Ресайз колонок работает не везде + нет видимых границ

**Симптом:** курсор-стрелки появляется только между некоторыми колонками (№/вх, вх/дата, дата/инициатор, инициатор/содержание, тип/срок, срок/статус), но НЕ появляется между «Содержание»/«Исполнители», «Исполнители»/«За кем», «За кем»/«Тип», «Статус»/«Действия». Пользователь не понимает, что колонки можно двигать.

**Что сделать:**
1. Сделать **все** границы колонок в заголовке перетаскиваемыми.
2. Добавить **видимые границы**:
   - в заголовке — вертикальные разделители между колонками (тонкие, например `1px #26ffffff`);
   - в строках таблицы — тонкие вертикальные разделители между ячейками (того же цвета или слабее, например `#12ffffff`);
   - при наведении на границу заголовка — подсветить её (например, `#4f8cff`) и показать курсор `RESIZE_HORIZONTAL` (или стрелки).
3. Убедиться, что drag работает на всех границах, ширина сохраняется в `controls_settings.json.col_widths`.
4. Не сломать layout: границы не должны увеличивать ширину колонок, использовать `border` или отдельные `Container` шириной 1 px.

### БАГ 4. Hover всё ещё с задержкой

**Симптом:** при быстром движении курсора по строкам подсветка запаздывает/пропускает строки. Изменение раунда 7 (только bgcolor, без border) не помогло.

**Что сделать:**
1. Найти **реальную** причину задержки. Гипотезы:
   - `_safe_update()` всё ещё дорогой;
   - Flet 0.23.2 не успевает обрабатывать частые `update()`;
   - hover-обработчик вызывается слишком часто или реже, чем нужно;
   - `Control.update()` на контейнере строки с множеством детей медленный.
2. Попробовать альтернативы:
   - обновлять только `bgcolor` без `_safe_update` (с проверкой `if control.page is not None`);
   - использовать `page.update()` вместо `control.update()` (если это быстрее);
   - уменьшить количество детей в строке (упростить ячейки);
   - использовать `ft.Stack` с оверлеем-подсветкой, который двигается за курсором (сложнее, но может быть быстрее);
   - временно отключить hover и вернуть его после оптимизации.
3. Цель: при проведении курсором по 10 строкам за ~0.5 сек все 10 должны подсветиться последовательно без пропусков.
4. **Не использовать** `traceback.print_exc()` в hover-обработчике (AGENTS.md §36.2).

## Технические ограничения (обязательно)

- Flet **строго 0.23.2**, новых зависимостей не добавлять.
- `ft.icons.*` вместо emoji; `print()` в консоль — только ASCII; UI-текст — русский.
- Hex с прозрачностью — только `#AARRGGBB`.
- Внутри `Column(scroll=AUTO)` запрещены: `expand=True` (кроме горизонтальных спейсеров в Row), `wrap=True`, `animate*`, `shadow`, `gradient` на мелких контейнерах.
- Все `.update()` контролов — через `_safe_update()` (кроме, возможно, hover — если найдёшь более быстрый безопасный способ).
- Вложенные `AlertDialog` запрещены; подтверждения — через `page.open()/page.close()`.
- Не ломать вкладки «Следственные отделы» и «Зональные», сетевую синхронизацию, уведомления, архив, импорт Excel, вложения, удаление всех.
